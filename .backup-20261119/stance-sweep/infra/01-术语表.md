## 一、Spring Boot 装配：为什么会有 starter

### 1.1 starter

没有 starter 的年代，你想用一个 Redis 客户端，得自己写配置类、自己 new 连接池、自己在 XML 里登记 bean。同一套配置在十个项目里抄十遍，版本还各不相同。

**starter 就是把这套东西打包进库自己的 jar 里**——你在 pom 加一行依赖，配置自动到位。

所以它不是什么新技术，只是一个打包约定：一个 jar，里面多了一个 `@Configuration` 类，再加一份"我在这里"的声明清单。知道这些就够用了。

本项目有 **31 个**自定义 starter，都在 `S-starter` 目录下，名字统一 `S-xxx-starter`。比如 `S-datasource-stable-starter` 管 stable 库的装配，`S-log-starter` 管日志，`S-pii-starter` 管字段加密。

一句话：**starter = 库自带的「安装说明书 + 安装程序」。**

> 👉 想彻底搞懂（拆开 `S-job-starter` 逐文件看），读 [[04-starter 是什么]]。

### 1.2 自动装配 / AutoConfiguration

有了 starter，Spring Boot 又多了个麻烦：启动时它得知道哪些 jar 里有装配逻辑、该不该装。总不能把所有 jar 里的 `@Configuration` 全扫一遍——那会把用不着的东西也装上。

解法是让每个 jar 自己声明。装配类放在固定位置，Spring Boot 只读这些声明，再用条件注解筛一遍。

本项目的装配类叫 `XxxDruidMyBatisAutoConfig` 这种名字，声明位置见下一条。

一句话：**自动装配 = jar 自己报菜名，Spring Boot 挑着上菜。**

### 1.3 `spring.factories` / `AutoConfiguration.imports`

一个 jar 里的装配类写在哪个包，Spring Boot 无从得知。所以需要一个固定路径的清单文件，让每个 jar 自己来登记。

写法有两种。老的用 `META-INF/spring.factories`，键值对形式，一个文件还能顺带声明别的扩展点。新的用 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`，一行一个类名，更简陋也更干净。Boot 2.7 两种都支持，3.0 起 `spring.factories` 里的自动装配声明被移除。

✅ 本项目实测：5 个按域 starter（stable / base / intra / it / stable-r）**都有** `spring.factories`，而骨架 `S-datasource` **故意没有**——它靠主应用的组件扫描生效，详见 [[09-Dao 与 Entity 设计]] §三。

一句话：**它就是一份「我家有哪些装配类」的清单**，放在 jar 的固定位置。

### 1.4 `@Conditional` / `@ConditionalOnBean`

清单里列了装配类，但"这个项目到底该不该装"得按现场情况判断。数据源就是典型例子：没配数据库的服务，不该装数据源。

条件注解干的就是这件事——给装配类加一个开关。`@ConditionalOnBean(X.class)` 的意思是 "容器里有 X 这个 bean 才装我"。

✅ 本项目的数据源配置上就是 `@ConditionalOnBean(DruidDataSourceProperties.class)`，效果是**没配数据源的服务，数据源自动配置直接不生效**，不会因为"引了依赖"就报错。这是好设计。

一句话：**条件注解 = 装配类的「门禁」**，条件不满足就不进。

### 1.5 Bean / IoC 容器 / 依赖注入

不用容器的时候，对象之间互相 `new`：A 要 B，B 要 C，最后谁也测不了，谁也换不掉。

容器把这件事接了过去——对象的创建权归容器，用的人只声明"我需要一个 X"，容器负责给。这就是 IoC（控制反转）。而"容器把 X 塞给你"这个动作，叫依赖注入（DI）。

✅ 本项目里最漂亮的一处用法是 `@Autowired private List<CvmEvent> eventList;`—— 一行把**所有**实现类收进来，策略分发靠它（见 [[12-设计模式、最佳实践与设计缺陷]] §2.1）。

一句话：**Bean = 容器管的对象；IoC = 你别自己 new，跟容器要。**

### 1.6 父子容器 / Bootstrap Context

这里有个鸡生蛋的问题：配置要从远程（Nacos）拿，可"连远程的地址"本身就写在配置里。于是需要**一个更早的、独立的容器**，先把配置拉回来。

Spring Cloud 的解法是起一个**父容器**（Bootstrap Context）。它有自己的 `Environment`，只干一件事：拉远程配置。拉完之后，主容器作为子容器**继承**这份 Environment，轮到建 bean 时配置已经就绪。

✅ 本项目 `S-ServiceConfig/pom.xml` 引了 `spring-cloud-starter-bootstrap`，所以走的是**老 bootstrap 机制**，不是 Boot 2.4+ 的 `spring.config.import`。完整时序见 [[05-服务是怎么启动的]]。

一句话：**先有个「只干一件事：拿配置」的父容器，主容器才有配置可用。**

### 1.7 Environment / PropertySource

一个应用的配置可能来自十几个地方：命令行、环境变量、`application.properties`、`bootstrap.properties`、Nacos、JVM 参数……而且后面的能覆盖前面的。

`Environment` 就是这些来源的统一视图。每个来源是一个 `PropertySource`，按优先级排成一个列表，取值规则是"从上往下找，找到就用"。

✅ 想验证配置到底从哪来，最可靠的办法是开 `--debug` 启动，日志会一条条打印 `Located property source: ...`（[[05-服务是怎么启动的]] §七）。

一句话：**Environment = 所有配置来源叠成的一摞纸，上面的盖住下面的。**

### 1.8 profile

同一份代码要跑在 dev / test / prod，差异只有地址和开关。profile 就是给配置打标签：`bootstrap-<profile>.properties` 只在对应 profile 激活时才加载。

⚠️ 本项目有 **6 个 profile**（dev / test / prod / prodhnd / clouddnsprod / clouddnsdev），但**环境是编译时写进 jar 的**——靠 Maven 占位符 `@activatedProperties@`，`test` 是默认值。它不是启动时选的，这是个很反直觉的点，详见 [[05-服务是怎么启动的]] §三。

一句话：**profile = 配置的「环境标签」；本项目把它焊死在编译产物里。**

## 二、Nacos：配置中心 + 注册中心

### 2.1 Nacos 这个名字

微服务需要两样东西：**配置**要能集中改，**服务地址**要能自动发现。以前这是两个系统，比如 Apollo 管配置、Eureka 管发现。

Nacos 把两件事塞进同一个进程。名字就是 **Na**ming **and** **Co**nfiguration **S**ervice 的缩写—— 既是配置中心，也是注册中心。

✅ 本项目本地跑在 `127.0.0.1:8848`（容器 `infra-nacos`），公司内网是 `10.78.128.115:8848`。

一句话：**Nacos = 配置中心 + 注册中心 二合一**。

### 2.2 8848 / 9848 两个端口

Nacos 1.x 全靠 HTTP 短连接轮询，服务一多，光心跳就能把服务端压垮。 2.x 换成了 **gRPC 长连接**，而 gRPC 的端口约定是主端口 **+1000**，所以 8848 旁边必须有 9848。

⚠️ 这是容器化最常见的坑：**只映射 8848 不映射 9848，客户端就是连不上**，而且报错通常看不出跟端口有关。本项目本地的 `stack-up.sh` 两个都映射了。

一句话：**9848 = 8848 + 1000，是 gRPC 长连接端口，少映射一个就连不上。**

### 2.3 namespace / group / dataId（三层寻址）

一个 Nacos 里要装几百份配置、几千个服务，必须能精确指到某一份。可"环境""业务域""用途" 是三种不同的分类维度，一个层级装不下，于是有了三层寻址——像"省 / 市 / 街道门牌"：

| 层 | 项目里叫什么 | 作用 | 本项目实例 |
|---|---|---|---|
| 最粗 | **namespace** | 租户级隔离，**跨 namespace 默认不可见** | `public` / `74b75ca6…` / `529be423…` |
| 中间 | **group** | 同一 namespace 内再分组 | `TEST_GROUP` / `DEV_GROUP` / `SHARED_GROUP` |
| 最细 | **dataId** | 具体一份配置的文件名 | `datasource.properties` |

🔑 这里最容易搞错的一点：本项目**三个 namespace 是三种用途，不是三套环境**。

```
public      → 配置（26 份，靠 group 分环境）
74b75ca6…   → Spring Cloud 服务发现（acl / dgw）
529be423…   → Dubbo 接口注册（providers:com.didi.dubbo.IDubboDgwService::）
```

一句话：**namespace 分「用途」，group 分「环境」，dataId 指「哪份文件」。**

> 📌 `tenant` 是老版本 API 里对 namespace 的叫法，HTTP 接口参数里还叫 `tenant=`。

### 2.4 配置中心 vs 注册中心

初学者最容易把两者混为一谈，因为 Nacos 一个进程全包了。但它们的职责完全不同：

| | 配置中心 | 注册中心 |
|---|---|---|
| 存什么 | **配置文件内容**（键值对） | **服务实例地址**（IP:端口） |
| 谁写 | 人 / 发布系统 | 服务自己（启动时注册、心跳续约） |
| 谁读 | 所有服务 | 需要调用别人的服务 |
| 变了怎么办 | 推送 + `@RefreshScope` 热更新 | 订阅者收到地址变更 |

✅ 本项目中同一个 Nacos 进程，两个功能**用不同的 namespace 隔开**，见 2.3。

一句话：**配置中心存「参数」，注册中心存「地址」。**

### 2.5 extension-configs

一个服务要读十几份配置——数据源、Kafka、Redis、任务调度……如果每份都单独写代码加载，实在太啰嗦。

所以在 bootstrap 里列一个清单，Nacos 客户端**批量拉取**，每项还能单独设 `refresh=true`。

📌 本项目 dev 有 **72** 项、test 有 **75** 项 `extension-configs`。 ⚠️ 一个文件里 75 项，**没人能审查**——这是 [[12-设计模式、最佳实践与设计缺陷]] §4.12 记的债。

一句话：**extension-configs = 「我要这几份配置」的清单。**

### 2.6 服务发现 / `@EnableDiscoveryClient`

服务实例的 IP 会变——扩缩容、重启、漂移。调用方不能把 IP 写死在配置里。

服务发现的思路反过来：服务启动时**把自己注册**到注册中心（服务名 → IP 列表），调用方按**服务名**查地址，顺带还能做客户端负载均衡。

✅ 本项目 `AclApplication` 上有 `@EnableDiscoveryClient`，所以 `acl` 会出现在 `74b75ca6` 这个 namespace 里。

一句话：**服务发现 = 「按名字找地址」，而不是「按地址找服务」。**

## 三、Dubbo：RPC 与它的两个动作

### 3.1 RPC / Dubbo

服务之间如果都用 HTTP + JSON 调用，问题一堆：序列化开销大、客户端要手写、超时重试限流没有统一治理。

RPC 的思路是让远程调用**看起来像本地方法调用**。Dubbo 是阿里开源的 Java RPC 框架，把网络通信整个藏在接口背后，调用方只看见接口。

✅ 本项目用 Dubbo **3.2.5**，注册中心仍是 Nacos。契约模块 19 个，都在 `S-DubboApi`。

一句话：**RPC = 调远程方法像调本地方法；Dubbo 是干这事的框架。**

### 3.2 provider / consumer

RPC 一定有两端，分清谁提供服务、谁使用服务，是理解后面一切的前提。

**provider（提供者）**实现接口，把服务**暴露**出去。**consumer（消费者）**只拿接口，**订阅**地址，然后发起调用。

✅ 本项目里 `@DubboService` 标在实现类上（provider），`@DubboReference` 标在字段上（consumer）。

一句话：**provider 挂招牌，consumer 找招牌。**

### 3.3 暴露（export）/ 订阅（subscribe）

光有注解不够，框架得在**正确的时机**把服务信息写进注册中心、把别人的地址拉下来。

**暴露（export）**是把"我这个接口在哪个 IP:端口、用什么协议"写进注册中心。**订阅（subscribe）**是从注册中心拿到对方的地址列表，并在内存里维护——地址变了要跟着更新。

🔑 这两个动作发生在**主容器 refresh 的收尾**，不是一个独立阶段。所以看到 `Started AclApplication` 那行日志时，它们已经完成了（[[05-服务是怎么启动的]] §五）。

一句话：**暴露 = 上报自己；订阅 = 拉取别人。都在启动末尾完成。**

### 3.4 契约模块（`S-DubboApi`）

provider 和 consumer 必须共用**同一份接口定义**，否则连签名都对不上。

办法是把接口单独打成一个 jar，双方都依赖它。本项目还多做了一步：**服务之间不互相依赖实现 jar，只依赖契约 jar**。

📌 本项目有 19 个契约模块。实测 38 个服务模块里**只有 1 个**被别的 pom 引用—— 所以"服务互相独立"这个结论是成立的。但数据库不独立，那是另一回事，见 [[12-设计模式、最佳实践与设计缺陷]] §4.1。

一句话：**契约 jar = 双方共用的「接口说明书」，只含接口不含实现。**

### 3.5 序列化

Java 对象要变成字节能过网络，对方再还原回来。

Dubbo 默认用 **hessian2**，快，跨语言能力一般，也可以换 JSON 或 Protobuf。 ⚠️ 但这要求被传输的类**必须可序列化**，而且字段类型要稳定。

✅ 本项目的 DTO 都在契约模块里。改字段时要想到**老版本的 consumer 还在跑**，所以契约变更必须向后兼容。

一句话：**序列化 = 对象 ↔ 字节；契约变了要向后兼容。**

## 四、持久化层：Dao / Entity / Mapper 到底是什么关系

### 4.1 Entity / POJO / DTO / VO（一堆 XO）

同一个业务概念，在不同层需要不同的"形状"：数据库里是一行数据，接口返回是 JSON，页面展示又是另一种视图。于是有了一堆以 O 结尾的名字：

| 名字 | 全称 | 对着谁 | 本项目 |
|---|---|---|---|
| **POJO** | Plain Old Java Object | 无，就是个普通类 | 泛称 |
| **Entity** | 实体 | **数据库表**（一字段一列） | `S-Entity`，634 个 |
| **DTO** | Data Transfer Object | **跨进程传输** | 契约模块里 |
| **VO** | View Object | **前端展示** | 少量 |
| **Dao** | Data Access Object | **不是数据，是「访问数据的对象」** | `S-Dao` |

📌 本项目 `S-Entity` 有 **634 个** POJO（132+412+72+18），按 4 个子模块分域。

一句话：**Entity 是「表的样子」，DTO 是「传输的样子」，Dao 是「干活的对象」。**

### 4.2 Dao / Mapper

业务代码不该写 SQL 拼接，也不该管连接。得有一层专门负责"怎么读写数据库"。

**Dao** 是这一层的抽象概念——数据访问对象。**Mapper** 是它在 MyBatis 里的具体形式：一个接口，配一份 XML（或注解）写的 SQL。接口没有实现类，SQL 就是它的实现。

📌 本项目 `S-Dao` 模块里有 **175 个 java / 139 个 xml**，其中 **165 个 `*Mapper.java`**。

一句话：**Dao 是「这一层叫什么」，Mapper 是「MyBatis 里它长什么样」。**

### 4.3 MappedStatement / SqlSession

MyBatis 得把"XML 里的一段 SQL"变成可执行的东西，还要顺带管事务和缓存。

**MappedStatement** 是一条 SQL 的完整描述：id、SQL 文本、参数映射、结果映射。**SqlSession** 是一次数据库会话，负责执行 SQL 并管理事务。

✅ 本项目 `DataChangeLogInterceptor` 拦的是 **`Executor`**（SqlSession 内部的执行器），所以它能看见所有 SQL。

一句话：**MappedStatement = 一条 SQL 的档案；SqlSession = 一次会话。**

### 4.4 `#{}` 和 `${}`（SQL 注入的分界线）

SQL 里总要放变量，而直接做字符串拼接会被注入——`' or 1=1 --` 就是这么来的。

`#{name}` 会被编译成 **`?` 占位符 + 预编译赋值**，安全。`${name}` 是**原样字符串拼接**，危险，只在不得不"拼结构"时用，比如表名和排序字段。

⚠️ 本项目 **116 个 XML** 用了 `${}`，其中 `${criterion.condition}` **848 次**—— MBG 生成的 `Example` 靠它拼 WHERE。详见 [[12-设计模式、最佳实践与设计缺陷]] §4.8。

一句话：**`#{}` 是「传值」，`${}` 是「拼字符串」——能不拼就不拼。**

### 4.5 MBG / Example / selectByExample（第一代风格）

手写 CRUD 又长又重复，2000 年代流行"用工具生成"。

MBG 是 **MyBatis Generator**：读数据库表结构，生成 `Xxx`（实体）、`XxxMapper`（接口）、`XxxMapper.xml`（SQL），外加一个 **`XxxExample` 条件构造器**。所谓 `selectByExample(example)`，就是"按 Example 里攒的条件去查"。

📌 本项目 165 个 Mapper 里 **51 个**是这种风格。另外注意 **117 个 `*Example` 放在 `S-Entity`**，不在 `S-Dao`——只在 Dao 目录里翻会漏掉它们。

一句话：**MBG = 老一代「按表结构生成代码」，Example 是它的条件拼装器。**

### 4.6 MyBatis-Plus / BaseMapper / Wrapper（第二代风格）

MBG 的 `Example` 太笨重了，一个查询要写一长串 `createCriteria().andXxxEqualTo()`。

MyBatis-Plus 换了个思路：`BaseMapper<T>` **继承就自带** CRUD，查询用链式 `Wrapper`，比如 `new QueryWrapper<T>().eq("name", x)`，完全不用生成 XML。

📌 本项目 **58 个** Mapper `extends BaseMapper`，版本 **3.2.0**。另有自研的`ExtLogicSqlInjector` 扩展它的 SQL 注入器（[[09-Dao 与 Entity 设计]] §四）。

一句话：**MyBatis-Plus = 新一代「继承就够用」，Wrapper 是它的条件拼装器。**

> ⚠️ 两代并存的代价：新人要学两套，同一个功能有两处实现。
> 这就是 [[09-Dao 与 Entity 设计]] §五 说的"历史包袱"。

### 4.7 TypeHandler

Java 的 `Date` 和 MySQL 的 `datetime`，时区和精度都对不齐；枚举存字符串还是存数字也得定下来。这些转换如果散在业务代码里，就再也收不回来了。

MyBatis 留了**类型转换钩子**：`setParameter`（Java → DB）和 `getResult`（DB → Java）时由它接管。

✅ 本项目用 `DateTypeHandler` / `DateTimeTypeHandler` / `CalendarTypeHandler` 三个集中处理，配合 JDBC URL 上的 `serverTimezone=Asia/Shanghai`。

一句话：**TypeHandler = 「Java 类型 ↔ 数据库类型」的翻译官，要集中放。**

### 4.8 动态数据源 / 路由 / `AbstractRoutingDataSource`

一个服务要连多个库（intra / stable / base……），但**同一个 Mapper 方法**在不同场景要连不同的库。

Spring 提供了 `AbstractRoutingDataSource`：它本身是一个 `DataSource`，内部有一张路由表，外加一个钩子 `determineCurrentLookupKey()`。拿连接时，按钩子返回的 key 去表里挑真实连接池。

✅ 本项目手写了 13 行的 `DynamicDataSource extends AbstractRoutingDataSource`， key 取自 `ThreadLocal` 里的栈。完整链路见 [[09-Dao 与 Entity 设计]] §二。

一句话：**它就是「数据源的分发器」：拿连接那一刻才决定去哪个库。**

### 4.9 读写分离 / 主从 / `STABLE_R`

写少读多，一个库扛不住。经典做法是一个主库负责写、多个从库负责读，中间靠主从复制同步。

读走从库、写走主库，扩容读能力的成本极低。 ⚠️ 代价是**主从有延迟**：刚写完立刻查可能查不到，需要"写后读主"兜底。

✅ 本项目 `DataBaseType` 里的 `STABLE`（主）和 `STABLE_R`（从）就是这么分的—— **没用框架，只是多加了一个枚举值**。

一句话：**读写分离 = 读从写主；延迟是它的固有代价。**

### 4.10 连接池 / Druid

每个请求都新建数据库连接的话，TCP 握手加认证的开销巨大。

连接池预先建一批连接反复用。**Druid** 是阿里开源的池，额外带**监控和 SQL 统计**。

✅ 本项目用 Druid 做连接池，`DruidCollector`（86 行）+ `DruidMetricsConfiguration`（49 行）把池指标采集出来上报。

一句话：**连接池 = 连接复用；Druid 额外送监控。**

### 4.11 `@MapperScan` / `@Primary`

这里有两个不同的"找不到"问题。MyBatis 要知道哪些接口是 Mapper，否则不会给它们生成代理；容器里有多个 `DataSource` bean 时，注入方又不知道该用哪个。

`@MapperScan("com.didi.dao")` 让 MyBatis 扫这个包下的接口并生成代理。`@Primary` 则在多个候选里指定**默认选我**——本项目标在路由数据源上。

⚠️ `@MapperScan` 的包名在 5 个 starter 里**各不相同**（`com.didi.dao` / `com.didi.**.dao` / `com.didi.*.infrastructure.mapper` / `com.didi.message.mailsend`）。**"Mapper 为什么没扫到"是最常见的启动期问题**。

一句话：**`@MapperScan` 告诉 MyBatis「去哪找接口」；`@Primary` 告诉容器「默认选谁」。**

### 4.12 事务 / 传播行为

一组写操作要么全成功要么全失败。而方法互相调用时，"要不要加入别人的事务"又是另一个问题。

`@Transactional` 把方法包进事务。**传播行为**决定嵌套时的语义：`REQUIRED` 是默认值，表示加入现有事务；`REQUIRES_NEW` 则新开一个。

🔑 这一条和切库强相关：**切库必须早于事务**。否则事务已经绑定了连接、切库才发生，结果是**切库静默失效**——不报错，但数据写进了错误的库。这就是切面 `@Order(-9)` 的意义（[[12-设计模式、最佳实践与设计缺陷]] §2.6）。

一句话：**事务管「要么全成要么全败」；切库必须发生在事务之前。**

## 五、AOP 与横切

### 5.1 AOP / 切面 / 切点 / 通知 / 织入 / 代理

日志、审计、鉴权、事务这些逻辑，几十个方法里都要有，可它们跟业务本身毫无关系。靠复制粘贴的话，必然有人漏掉一处。

AOP 的做法是把这堆逻辑**挪到一个"面"上**，再声明"哪些方法要套它"。行话是这几个词：

| 词 | 意思 | 类比 |
|---|---|---|
| **切面 Aspect** | 这堆横切逻辑本身（一个类） | 一张"透明贴纸" |
| **切点 Pointcut** | "贴在哪"（表达式匹配方法） | 贴纸的位置 |
| **通知 Advice** | "什么时候贴"（Before/After/Around） | 贴的时机 |
| **织入 Weaving** | 生成代理、把逻辑插进去的动作 | 贴的动作 |
| **代理 Proxy** | 实际被调用的那个"假对象" | 贴了贴纸的原件 |

✅ 本项目 5 个 `XxxDataBaseAspect`（切库）、事务、Dubbo 全靠 AOP。`@Aspect @Order(-9)` 的意思是"这张贴纸贴在最里层、最先执行"。

一句话：**AOP = 把「每个方法都要做的事」抽出来，用代理统一套上。**

### 5.2 横切关注点

有些需求不属于任何一个业务，而是"横着切过所有业务"。

给它起个名字（横切关注点）是有用的，因为这样才谈得上"它该放哪"。典型的横切有：日志、审计、鉴权、事务、限流、加密、监控。

✅ 本项目的三个典型横切都做在**基础设施层**而不是业务代码里，这是对的做法：审计用 `DataChangeLogInterceptor`，加密用 `PiiInterceptor`，指标用 `DruidCollector`。

一句话：**横切 = 不属于某个业务、但每个业务都要有的东西。**

### 5.3 `@Order`

多个切面套在同一个方法上，谁先谁后**必须确定**，否则行为随机、且难以复现。

`@Order` 的规则是**数值越小越先执行**，也越靠"外层"。负数常用于"我必须跑在框架之前"。

✅ 本项目的切库切面是 `@Order(-9)`——必须早于事务，也就是比 `@Transactional` 的默认最低优先级还早。

一句话：**`@Order` 数字越小越先跑；切库要抢在事务前面。**

### 5.4 拦截器 / 责任链 / 插件链

框架的某个环节需要被"可插拔地"扩展，但又不能去改框架源码。

解法是**责任链**：一串处理器依次过，每个可以"处理完继续传"，也可以中断。 MyBatis 的 `Interceptor` 就是插件链，包在 `Executor` / `StatementHandler` 外面。

✅ 本项目全项目只有 **2 个** `@Intercepts`——审计和 PII 加密。

一句话：**插件链 = 一层层包住核心，每层都能插手。**

## 六、并发与上下文

### 6.1 ThreadLocal

多个线程要共享"当前请求的信息"——用户是谁、traceId 是什么、这次请求要走哪个库。可如果用参数一路往下传，要改几十个方法签名。

ThreadLocal 的办法是给每个线程一份**独立副本**，像"每个线程自己的储物柜"。写用 `set`，读用 `get`，线程之间互不干扰。

✅ 本项目有两个：`DataBaseContextHolder`（切库）和 `MysqlChangeContext`（审计主体）。

一句话：**ThreadLocal = 线程自己的储物柜，不用改方法签名就能传上下文。**

### 6.2 为什么用**栈**（`Deque`）而不是单值

假设 A 方法切到 intra 库，里面调 B 又切到 stable 库。B 返回之后，**必须回到 intra**。

单值存不下这个信息——它会被覆盖，回不去。所以要用**栈**，`ThreadLocal<Deque<String>>`：进入时 `addFirst`，退出时 `removeFirst`。

✅ 本项目 `DataBaseContextHolder` 就是这个结构（[[09-Dao 与 Entity 设计]] §2.2）。

一句话：**栈支持嵌套返回，单值不支持——这是选 Deque 的唯一理由。**

### 6.3 上下文丢失 / 线程池 / `TaskDecorator`

ThreadLocal 是**线程私有**的。把任务丢给线程池后，**执行它的是另一个线程**，储物柜里的东西自然就没了。

所以上下文要**手动搬**：提交任务时把上下文抓出来，在池线程里重新 `set`，执行完 `remove`。 Spring 的 `TaskDecorator` 就是这个搬运钩子。

⚠️ 本项目这两个 ThreadLocal **都没有做透传**。后果是异步线程里 "审计 operator 为空"，以及"偶发连错库"。这是 [[12-设计模式、最佳实践与设计缺陷]] §4.9 记的缺陷。

一句话：**ThreadLocal 过不了线程池的边界，必须手动搬。**

### 6.4 内存泄漏（ThreadLocal 版）

线程池的线程**不会销毁**，会被反复复用。如果 `set` 进去的值没有 `remove`，它会一直挂在这个线程上——而线程还活着，所以 GC 也收不掉。

这一条没有"解决"，只有纪律：**`try { set } finally { remove }`**。

⚠️ 本项目切面里必须保证弹栈和清理，否则一次请求就能污染整个池线程。见 [[09-Dao 与 Entity 设计]] §七的坑清单。

一句话：**线程池 + ThreadLocal 不清理 = 慢性内存泄漏 + 数据串号。**

## 七、日志：MDC 与 traceId

### 7.1 MDC

日志里想带上"这次请求的 traceId、用户、IP"。可如果每个 `log.info` 都手写`log.info("traceId={} user={} ...", ...)`，几十万处都要改，而且一定会漏。

MDC 全称 **Mapped Diagnostic Context**，本质是**一个 ThreadLocal 的 Map**。你 `put` 一次，之后**日志框架在输出时自动把整个 Map 拼进每一行**，业务代码完全不用管。

📌 本项目用了 **7 个 key**（18 个常量定义在 `MysqlRecordContanst` 等类里），在 HTTP / Dubbo / Redis 三个入口处手动 `put` 和 `clear`。

一句话：**MDC = 「给这个线程的每行日志自动加前缀」的储物柜。**

### 7.2 traceId / spanId / cspanId

一次请求跨 5 个服务，日志散在 5 台机器上。你需要把同一批日志**串起来**，还得知道**谁调的谁**。这是链路追踪的通用模型：

| 字段 | 规则 | 作用 |
|---|---|---|
| **traceId** | **全链路不变** | 把这 5 个服务的日志筛出来 |
| **spanId** | **每跳都变**（新生成） | 标识"这一步" |
| **cspanId** | = **上一跳的 spanId** | 标识"我爹是谁"，还原调用树 |

✅ 本项目三个字段都放在 MDC 里，靠 HTTP header 和 Dubbo attachment **手动透传**。

一句话：**traceId 认「同一次请求」，spanId 认「这一步」，cspanId 认「上一步」。**

### 7.3 Appender / Pattern

日志要落到不同地方（控制台、文件、Kafka），每个地方的格式还可能不一样。这两件事分别由 Appender 和 Pattern 管。

**Appender** 是输出的**目的地**，一条日志可以同时给多个 Appender。**Pattern** 是输出的**格式模板**，比如 `%d %X{traceId} %msg%n`。

⚠️ 本项目有两个落盘 Appender（`app-log` / `error-log`）加一个 `async-log` 异步包装。问题在于 `Pattern` 把 MDC 的 7 个字段**拍平成一整行文本**，下游 logstash 再用 grok 正则拆回来——一拆一合全靠正则对齐，很脆弱（[[08-日志治理]]）。

一句话：**Appender 管「写到哪」，Pattern 管「写成什么样」。**

### 7.4 异步 Appender / 装饰器

同步写盘会阻塞业务线程，日志一多就直接拖慢接口。

`AsyncAppender` 把日志丢进队列，让**另一个线程慢慢写**。它是个**装饰器**：包住已有的 Appender，加上"异步"这一层能力，不改输出格式。

✅ 本项目 `async-log` 包住 `app-log`。 ⚠️ 代价是**队列满会丢日志**，进程崩溃时队列里剩下的日志也会丢。

一句话：**异步 Appender = 给 Appender 套一层「先排队」，用丢日志的风险换性能。**

### 7.5 grok / logstash

日志是一行文本，想按字段检索（比如"找 traceId=abc 的"），就得先把字段解析出来。

**grok** 是 logstash 的正则方言，用 `%{TIMESTAMP_ISO8601:time}` 这种可读写法从一行文本里抠字段。抠出来存进 ES，才能按字段查。

⚠️ 本项目的链路是 `Pattern` 输出 → logstash grok 解析 → ES，**两边的格式必须严格对齐**。改一个字段顺序就可能让全链路解析失败（[[08-日志治理]] 记的设计债）。

一句话：**grok = 「从一行日志里抠字段」的正则模板。**

## 八、分布式模式

### 8.1 outbox（事务性发件箱）

业务写库和发消息是两个系统，天生无法原子。先写库再发消息，发消息失败，消息就丢了；先发消息再写库，写库失败，消息就是脏的。两头都不对。

outbox 的办法是：别直接发到消息队列，先把记录写进自己库里的 `outbox` 表。它跟业务写在同一个事务里，要么都成，要么都不成。然后由后台任务轮询，把 outbox 里的记录投递出去。本质上是把「两个系统的原子性」降级成「一个库的一次事务」。

✅ 本项目用 `rack_metric_outbox`，后台任务轮询投递（[[10-指标上报链路]]）。

一句话：**outbox = 先把「要发什么」写进自家账本，再慢慢发。**

### 8.2 幂等 / 幂等键

网络会重试，消息会重复投递。同一个操作执行两次，不能变成"扣两次钱"。

办法是给操作一个**唯一标识**，重复执行时发现"这个标识处理过了"就直接返回。

🔑 本项目的幂等键是**业务内容的 SHA256**，不是 UUID。好处是同样内容算两次必然相等，数据库唯一索引就能自动兜底，不依赖调用方守规矩（[[10-指标上报链路]]）。

一句话：**幂等 = 做一次和做十次结果一样；键要用「内容哈希」而不是随机 ID。**

### 8.3 租约（lease）/ CAS

多实例要抢同一个任务，但又不想引入 Redis 或 ZK 的分布式锁——锁超时和锁释放都是坑。

**CAS**（Compare-And-Swap）用"带条件的 UPDATE 返回影响行数"实现互斥：`UPDATE ... SET owner=? WHERE status=? AND lease_expire<now()`，返回 1 行才算抢到。**租约**给这个抢到的状态一个**有效期**，到期自动可被抢，于是**进程崩了也不用人工清理**。

✅ 本项目用在 `rack_metric_job` 的状态机迁移上（[[10-指标上报链路]]）。

一句话：**能用「一条带条件的 UPDATE」表达互斥，就别上分布式锁。**

### 8.4 状态机

一条数据会经过多个阶段：待处理 → 处理中 → 已发布 → 失败。如果代码里到处写 `if (status == 1) ... else if (status == 2)`，很快就乱了。

状态机把"允许的迁移"写在一处（枚举 + 迁移表），非法迁移直接拒绝，而且能用 CAS 保证并发下只有一个成功。

✅ 本项目 `MetricPipelineService`（**1084 行**）把整条流水线的状态迁移收在一个类里。 ⚠️ 类确实很大，但这种"大"是**内聚**，和"什么都干"的上帝类不是一回事（[[12-设计模式、最佳实践与设计缺陷]] §4.3 给了区分方法）。

一句话：**状态机 = 把「谁能变成谁」写成一张表，而不是散落的 if-else。**

### 8.5 最终一致 / 补偿

跨服务、跨库的强一致（2PC）性能差、可用性差，中间件一挂全都挂。

现实做法是接受"短暂不一致"，靠**重试、对账、补偿**让系统**最终**一致。本项目大量采用这套思路：outbox + 轮询、状态机 + 重试。

✅ [[10-指标上报链路]] 里的"发布前可见性断言"就是最终一致思路—— 不假设"发了就成功"，而是**回读确认**。

一句话：**最终一致 = 允许暂时不一致，靠重试和对账收敛。**

## 九、存储与数据流

### 9.1 OLTP / OLAP / 列存

有两种查询形态，方向完全相反。"查张三的订单"是行级、高频、小量； "统计上个月各省用量"是整列扫描、低频、海量。用同一套存储伺候这两种，必然有一头很难受。

于是分成两类：**OLTP**（联机事务）用 MySQL，按行存，适合单条增删改查；**OLAP**（联机分析）用 StarRocks 或 ClickHouse，**按列存**，适合聚合扫描。

⚠️ 本项目 MySQL 扛 OLTP，**StarRocks** 扛分析。注意它的连接串是`jdbc:mysql://10.79.31.30:9032/cx`——**用 MySQL 协议连 StarRocks**，所以看起来像 MySQL，其实完全不是。

一句话：**行存适合查一条，列存适合扫一片。**

### 9.2 分域 / 分库分表 / 冷热分离

单表几亿行，索引再快也扛不住；单库的连接数和磁盘同样有上限。这里有三招，经常被混为一谈：

| 招 | 解决什么 | 本项目 |
|---|---|---|
| **分域** | 按业务把表分到不同库 | 8 个逻辑库：intra/stable/base/it/mds/metric/stable_r… |
| **分表** | 一张大表按规则拆成 N 张 | 部分表按时间/ID 拆 |
| **冷热分离** | 老数据搬到便宜存储 | 快照表 |

⚠️ 但这 8 个逻辑库**只落在 6 个物理库上**，`dev46` 一个 schema 被 **3 个域共用**—— 所以本项目的"分域"只做到了逻辑层（[[12-设计模式、最佳实践与设计缺陷]] §4.1）。

一句话：**分域按业务、分表按数据量、冷热按时间——三件事。**

### 9.3 物化视图 / 快照

每次查询都现场聚合几千万行，太慢。

办法是**提前算好存起来**。物化视图是数据库帮你维护的"预算好的结果表"；快照则是定时把某一刻的状态整份存下来。

✅ 本项目指标链路里，"快照"和"指标"是两条不同的产物—— **快照走物化视图思路**，指标是时序数据（[[11-数据存储与分层]]）。

一句话：**物化视图 / 快照 = 「用存储换查询时间」。**

### 9.4 时序数据库 / VictoriaMetrics

监控指标是"时间戳 + 数值"的海量追加写。用 MySQL 存这个，又慢又贵。

时序数据库专门为"按时间范围聚合"做了优化，压缩率高、写入快。本项目指标上报的终点之一就是 VictoriaMetrics（[[10-指标上报链路]]）。

一句话：**时序库 = 为「时间 + 数值」专门优化的库。**

### 9.5 Codis

单机 Redis 的内存和吞吐都有上限，而 Redis 官方集群方案早期并不成熟。

Codis 是豌豆荚开源的 **Redis 集群代理**：客户端连代理，代理帮你分片和路由，客户端代码一行都不用改，当单机用。

✅ 本项目用的就是公司内部这套 Redis 方案（在 `S-redis-starter` 里对接）。

一句话：**Codis = Redis 的「分片代理」，客户端当单机用。**

## 十、工程化与评价用语

### 10.1 多模块 / aggregator / `-pl` / `-am`

一个仓库几十个模块，你得能"只编译其中一部分"，同时还得自动带上它依赖的那些模块。

- **aggregator（聚合 pom）**：根 `pom.xml` 用 `<modules>` 列出子模块，本身不产出代码
- **`-pl`**：project list，指定编译哪几个
- **`-am`**：also make，**连带编译它们依赖的模块**

✅ 实测 `mvn install -pl S-ServicesNet/S-acl-service -am` 会拉入 **23 个模块**，耗时 **49.4 秒**。**不加 `-am` 就会因为找不到依赖而失败**——这是新手最常撞的一堵墙。

一句话：**`-pl` 挑模块，`-am` 顺带把它的依赖也编上。**

### 10.2 BOM / dependencyManagement

同一个库在不同模块里写了不同版本，运行时就冲突，报 `NoSuchMethodError`。

办法是**在一个地方统一版本号**（`dependencyManagement` 或 BOM），子模块只写 `groupId` + `artifactId`，不写 `version`。

✅ 本项目根 pom 统一管理 Spring Boot 2.7.17、Spring Cloud 2021.0.7、Dubbo 和 MyBatis-Plus 3.2.0。

一句话：**BOM = 「版本号只写一遍」的地方。**

### 10.3 SNAPSHOT

开发中的模块要互相依赖，但还没到发版的时候。

Maven 的"快照版本"就是给这个阶段的：**每次 install 都会覆盖**，依赖方拉到的永远是最新。 ⚠️ 代价是**构建不可重现**——今天和明天编出来的东西可能不一样。

✅ 本项目所有模块都是 `1.0-SNAPSHOT`。

一句话：**SNAPSHOT = 「会变的最新版」，方便联调但不可重现。**

### 10.4 EOL（End of Life）

软件有维护周期，过了就不再修安全漏洞。

EOL 是判断"该不该升级"的客观依据，不是个人喜好问题。

⚠️ 本项目的 Java **1.8** 和 Spring Boot **2.7.17** 都已过主流支持期。升到 Boot 3.x 需要 **Java 17 加上 `javax`→`jakarta` 全量改包名**，是件大工程。

一句话：**EOL = 官方不管了；不是"能不能跑"，是"出了漏洞有没有人修"。**

### 10.5 12-Factor（十二要素）

2011 年 Heroku 总结的"什么样的应用才好部署"，后来成了云原生的事实标准。

它一共 12 条原则，和本项目最相关的是两条：**Ⅲ. Config** 要求配置放**环境变量**、不放进代码或构建产物；**Ⅴ. Build, release, run** 要求构建和运行严格分离。

⚠️ 本项目**违反了第 Ⅲ 条**——环境（`spring.profiles.active`）被 Maven 编译进 jar，同一份代码要出 6 个包（[[05-服务是怎么启动的]] §三）。

一句话：**12-Factor 的核心一句：配置跟着环境走，不要跟着代码走。**

### 10.6 fail-open / fail-fast

出问题时有两个方向：**继续跑**（可能带错），还是**立刻停**（可能影响可用性）。

**fail-fast** 是发现问题立刻报错，把问题暴露在开发期。**fail-open** 是降级继续跑，把问题潜伏到生产。

⚠️ 本项目的切库是 **fail-open**：方法上没写注解时**不报错，静默走默认库**。开发以为在读 A 库，实际读的是 B 库，数据看起来还"对"，错误能潜伏很久。

一句话：**能用 fail-fast 就别 fail-open；静默降级是 bug 的温床。**

### 10.7 上帝类 / 技术债 / 分布式单体

这三个词都是**评价用语**，用来描述"规模失控"的三种形态：

| 词 | 意思 | 本项目实例 |
|---|---|---|
| **上帝类** | 一个类干了太多事，几千行 | `PackagePublishServiceImpl` **3775 行** |
| **技术债** | 为短期交付做的妥协，未来要还 | 两代 Mapper 并存、37 份重复配置 |
| **分布式单体** | **部署上分了、数据和变更上没分**，改一处要一起发 | 42 个服务共享 `dev46` 这个 schema |

详见 [[12-设计模式、最佳实践与设计缺陷]] §四。

🔑 判断"上帝类"要看**内聚性**，不能只看行数：`MetricPipelineService`（1084 行）是**内聚的大**，`PackagePublishServiceImpl` 是**杂糅的大**——两者不该用同一句话评价。

一句话：**分布式单体 = 「长得像微服务，改起来像单体」。**

### 10.8 DDD / 限界上下文 / 防腐层 / 仓储

业务复杂到"一个 Service 类装不下"时，需要按**业务边界**切分，而不是按技术分层切。

| 词 | 意思 | 类比 |
|---|---|---|
| **限界上下文** | 一个**词义自洽**的边界（"订单"在售后和财务里含义不同） | 一个部门 |
| **防腐层** | 隔离外部系统的翻译层，别让外部模型污染自己 | 前台/翻译 |
| **仓储 Repository** | 像"集合"一样访问领域对象，屏蔽数据库细节 | 仓库管理员 |
| **DTO / 领域对象** | 传输用 / 业务用，两回事 | 快递单 / 实物 |

⚠️ 本项目 `S-dns-order` 用了 DDD 分层（`adapter/application/domain/infrastructure`），但**三代包树并存**（`workorder/` `subdomain/` `domain/`），而且 14 个上下文塞在一个服务里—— **分层做了，边界没做**（[[12-设计模式、最佳实践与设计缺陷]] §4.2、§4.5）。

一句话：**DDD 的价值在「边界」，不在「四层目录」。**

## 十一、还常见但你可能会问的

剩下这些词，知道一句话就够，遇到再回来看：

| 词 | 一句话解释 |
|---|---|
| **acl** | **Access Control List（访问控制列表）**。代码实证：`AclApplyController`（申请）/ `AclDeployService`（下发）/ `AclDelService`（删除）/ `SecDomainController`（安全域）/ `RiskRuleController`（风控规则）——**是网络层「安全域之间能不能通」的防火墙策略工单**，不是登录鉴权 |
| **dgw** | `S-dgw-service`。代码实证：13 个控制器全是 `LoadBalance*`（CIDR / Tree / Region / NLB / DTM / DSI / Dubbo / StarVip）——**是负载均衡（VIP）配置管理服务**。缩写含义代码里没有注释，**不要硬猜** |
| **CMDB** | Configuration Management Database，配置管理数据库——**本项目的主体业务**（管服务器/网络设备/IDC） |
| **IDC** | Internet Data Center，机房 |
| **CVM** | Cloud Virtual Machine，云主机（腾讯云叫法） |
| **GTM** | Global Traffic Manager，全局流量管理（DNS 层调度） |
| **BPM** | Business Process Management，业务流程管理（审批流） |
| **xxl-job** | 开源分布式任务调度平台，本项目用它跑定时任务（本地化时是启动报错源之一） |
| **Kafka topic** | 消息的"频道名"；生产者和消费者按 topic 对接 |
| **Codis** | 见 §9.5 |
| **PII** | Personally Identifiable Information，个人可识别信息（手机号/身份证等）。本项目用 `PiiInterceptor` + 国密 SM4 做字段级加解密 |
| **SM4** | 国密对称加密算法，本项目用它做字段级加密 |
| **Druid** | 见 §4.10 |
| **H2** | 纯 Java 内存数据库，测试用（`MODE=MySQL` 可模拟 MySQL 语法） |
| **`S-` 前缀** | 本项目所有模块的统一前缀，无技术含义 |
| **`S-ServicesNet`** | 网络域服务组（7 个）：`acl` `cidr` `dgw` `line` `nat` `net-console` `qos`——都是网络基础设施 |
| **`S-exception-reslove-starter`** | 项目自带的拼写错误（应为 `resolve`）。同类还有 `insetCount`（应为 `insertCount`）——**看代码时别以为是自己眼花** |
| **`@RefreshScope`** | 标在配置类上，Nacos 配置变更时**热更新**这个 bean，不用重启 |
| **`@DubboService` / `@DubboReference`** | 见 §3.2 |
| **GraalVM / AOT** | 与本项目无关，但 Boot 3 话题里常出现，先知道名字即可 |
