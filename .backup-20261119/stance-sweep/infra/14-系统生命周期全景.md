# 14 · 系统生命周期全景：从构建到关闭

> 🧭 **阅读顺序 14 / 14 · 最后一篇** ｜ ⬅️ [[13-Nacos 面试题设计与评分卡]]

> 「**先拿到配置，才能建数据源**」这条因果不是孤立的知识点——
> 它是整个系统生命周期的**第 4 阶段**的一条约束。看懂它在整条线上的位置，
> 就能解释"为什么 `bootstrap.*` 不能换成 `application.*`"这类问题的**全部**变体。
>
> 本文用 `acl` 的**真实启动日志**（`target/logs/start.out`）逐毫秒对上，不是理论推演。

## 🎯 要点

1. **生命周期有 7 个阶段**，但**第一个阶段发生在进程启动之前**（构建期）。
   所以"运行期的行为"有一半在 `mvn package` 那一刻就定死了——这就是 [[05-服务是怎么启动的]] §三 讲的"环境被焊进 jar"。
2. **`bootstrap.*` 与 `application.*` 的区别不是"哪个文件"，而是"谁先被读"**。
   数据源 Bean 需要配置才能创建，所以配置必须**比 Bean 工厂更早**到位。 Spring Boot 为此专门开了一个"**父容器**"，在它里面把配置拉回来。
3. **端口打开 ≠ 服务就绪**。✅ 实测：`Tomcat started` 在 `11:10:05.602`，
   而 `Started AclApplication` 在 `11:10:11.217`——**中间有 5.6 秒，端口已经在收流量，但应用还没"就绪"**。这就是滚动发布时那段 503 窗口的来源。

> 📖 术语见 [[01-术语表]] · 启动细节见 [[05-服务是怎么启动的]] · 怎么跑起来见 [[06-启动与部署]]

> 这段时间内进来的请求，会碰到"Bean 都在但还没完全就绪"的边界状态。

## 二、阶段 0：构建期（进程还不存在）

这是最容易被跳过、但影响最大的一段。

```
mvn package -P test
   ↓
Maven 把 pom 里的 profile 值填进资源文件的占位符
   ↓
bootstrap.properties 里 spring.profiles.active=@activatedProperties@
   ↓ 被替换成
bootstrap.properties 里 spring.profiles.active=test
   ↓
打进 acl.jar 的 BOOT-INF/classes/
```

🔑 **后果**：这个 jar **只能跑 `test` 环境**。想跑 dev，必须重新编译。**环境不是运行时参数，是构建产物的一部分。** 详细动机与证据见 [[05-服务是怎么启动的]] §三。

📌 顺便看清 jar 的两个入口（✅ 实测 `unzip -p acl.jar META-INF/MANIFEST.MF`）：

| 项 | 值 | 含义 |
|---|---|---|
| `Main-Class` | `org.springframework.boot.loader.PropertiesLauncher` | 真正被 `java -jar` 执行的类 |
| `Start-Class` | `com.didi.AclApplication` | **你的** `main()`，由 Launcher 反射调用 |

⚠️ 为什么是 `PropertiesLauncher` 而不是常见的 `JarLauncher`？因为启动脚本用了`-Dloader.path=$MOD/target/libs`（见 `svc.sh:103`）——**把 jar 外面的 `libs` 目录也加进 classpath**。`JarLauncher` 不支持 `loader.path`，只有 `PropertiesLauncher` 支持。

## 三、阶段 1：JVM 启动 → `main()`

```bash
java -Xms512m -Xmx2g \
     -Dloader.path=.../target/libs \
     -Dlog.home=.../target -Dapp.name=acl \
     -jar acl.jar \
     --server.port=8074 \
     --spring.cloud.nacos.config.server-addr=127.0.0.1:8848   # ← 12 个覆盖参数
```

`java -jar` 的实际执行链：

```
java -jar acl.jar
  → PropertiesLauncher.main()
  → 建立 classpath（BOOT-INF/classes + BOOT-INF/lib + loader.path 外部目录）
  → 反射调用 Start-Class 的 main()
  → AclApplication.main()
  → SpringApplication.run(AclApplication.class, args)
```

🔑 **从这一刻起，Spring 接管了**。后面的所有阶段都是 `SpringApplication.run()` 内部的。

## 四、阶段 2：bootstrap 父容器——**你问的那条因果就在这里**

### 4.1 一句话原理

> **Bean 需要配置才能创建；配置需要 Environment 才能装；Environment 在容器创建时就定稿。**
> 所以"拉配置"这件事必须发生在"建 Bean"**之前**——而它自己又需要一个容器来承载。

Spring Cloud 的解法：**单独开一个父容器，专门干"拉配置"这一件事**。

```
                    ┌──────────────────────────────────────────┐
阶段 2（父容器）     │  BootstrapApplicationContext              │
                    │  ① 只读 bootstrap.*（本地文件）           │
                    │  ② 拿 bootstrap.* 里的 Nacos 地址去连    │
                    │  ③ 把 75 个 dataId 拉回来                 │
                    │  ④ 塞进父容器的 Environment              │
                    └────────────────┬─────────────────────────┘
                                     │ Environment 被继承
                    ┌────────────────▼─────────────────────────┐
阶段 3（主容器）     │  ApplicationContext                      │
                    │  ⑤ 建 DataSource bean ← 要用 ③ 里的配置   │
                    │  ⑥ 建 MyBatis / Dubbo / 线程池 ...        │
                    └──────────────────────────────────────────┘
```

### 4.2 为什么 Nacos 连接信息**只能**写在 `bootstrap.*`

展开讲：

| 如果写在 | 会发生什么 |
|---|---|
| **`bootstrap.properties`** ✅ | 阶段 ② 读它 → 拿到 Nacos 地址 → 去拉配置 → 阶段 ③ 拿到完整配置 → 建 Bean 成功 |
| **`application.properties`** ❌ | 阶段 ② 时**还没读** `application.properties`（它属于主容器） → 不知道 Nacos 在哪 → **拉不到任何配置** → 建 DataSource 时 `url` 是 null → 启动失败 |

⚠️ **报错长这样**（bootstrap 阶段就挂，比 Bean 创建更早）：

```
com.alibaba.nacos.api.exception.NacosException: failed to req API:/nacos/v1/cs/configs
  ...
Caused by: java.net.ConnectException: Connection refused
```

📌 **本质是"读文件的顺序"，不是"文件的地位"**。`bootstrap.properties` 之所以特殊，唯一的原因就是**它先被读**。

> 🔑 现代 Spring Boot（2.4+）用 `spring.config.import=nacos:` 把这套机制换掉了（不再需要父容器）。
> 但本项目用的是**旧的 bootstrap 机制**——判据是 `S-ServiceConfig/pom.xml` 里有
> `spring-cloud-starter-bootstrap` 这个依赖。**有它 = 老机制，必须写 `bootstrap.*`。**

### 4.3 实测：那 75 个配置源到底叫什么

✅ 日志里 `Located property source:` 后面跟的完整清单（节选），这就是**配置解析的真实结果**：

```
bootstrapProperties-acl-test.properties,  DEFAULT_GROUP    ← 服务名 + profile
bootstrapProperties-acl.properties,       DEFAULT_GROUP    ← 服务名
bootstrapProperties-acl,                  DEFAULT_GROUP    ← 服务名（无后缀）
bootstrapProperties-report.properties,    SHARED_GROUP     ← 共享配置
bootstrapProperties-line.properties,      TEST_GROUP       ← 依赖服务的配置
bootstrapProperties-monitor.properties,   TEST_GROUP
bootstrapProperties-idcOps.properties,    SHARED_GROUP
bootstrapProperties-omsOps.properties,    SHARED_GROUP
bootstrapProperties-serverLife.properties, SHARED_GROUP
...（共 75 个）
```

🔑 **三个维度同时起作用**：`dataId`（谁）+ `group`（哪一类）+ `namespace`（哪个环境）。**同一个 dataId 在不同 group 下是不同的配置**——这就是为什么 `line.properties` 出现在`TEST_GROUP` 而不是 `DEFAULT_GROUP`（详见 [[05-服务是怎么启动的]] §四）。

⚠️ 日志里那几行 `Ignore the empty nacos configuration` 不是错误—— 是"这个 dataId 在 Nacos 里不存在或为空，跳过"。**75 个里有几个是空的，属于正常。**

## 五、阶段 3：主容器建 Bean

```
11:09:56.146  [DUBBO] Dubbo Framework[1] is created     ← 第一个大 Bean 开始
11:09:58.705  Tomcat initialized with port(s): 8074     ← Web 容器初始化
11:09:58.825  Root WebApplicationContext: initialization completed in 3535 ms
```

这一阶段是**耗时主体**（18.8 秒里占了约 10 秒）。它在做：

- 扫描 `@Component` / `@Service` / `@Configuration`（42 个服务的代码量在这里体现）
- 执行 31 个 starter 的自动装配（每个都要过 `@Conditional` 关卡，见 [[04-starter 是什么]] §六）
- 创建 `DynamicDataSource`（**这里就是"要用第 5 步配置"的地方**，见 [[09-Dao 与 Entity 设计]]）
- 初始化 MyBatis（解析 139 个 XML、注册 Mapper 代理）
- 建 Dubbo 的 `FrameworkModel`、`ApplicationModel`

🔑 **为什么它慢**：`Root WebApplicationContext initialization completed in 3535 ms`只统计了 Web 部分；剩下的时间在 Dubbo/MyBatis/DB 连接池初始化。

## 六、阶段 4：refresh 尾部——对外"宣告"

Spring 容器 `refresh()` 的最后几步，是**对外可见性**的关键：

```
11:10:05.602  Tomcat started on port(s): 8074            ← ① 端口打开，能收 HTTP 了
11:10:05.658  nacos registry, DEFAULT_GROUP acl ...:8074 ← ② 注册到服务发现
11:10:10.839  Export dubbo service ...                   ← ③ Dubbo 暴露
11:10:11.217  Started AclApplication in 18.809 seconds   ← ④ 就绪
```

### 6.1 ⚠️ 这四步之间不是原子的

| 时间窗 | 状态 | 会发生什么 |
|---|---|---|
| `05.602` ~ `05.658` | 端口开了，**还没注册** | 直连 IP 能打进来；通过服务发现找不到它 |
| `05.658` ~ `10.839` | 已注册，**Dubbo 还没暴露** | HTTP 能通；RPC 调用方会报 `No provider available` |
| `10.839` ~ `11.217` | 都好了，`Started` 还没打 | 监控/健康检查可能判为"未就绪" |

🔑 **这就是"发布时的 503 / 找不到 provider"的真实机理**—— 不是"服务没起来"，而是**"起来了但还没宣告完"**。总窗口约 **5.6 秒**（实测）。

📌 三个可操作的结论：
1. **健康检查要绑 `Started` 之后**，不能只看端口通不通。
2. **滚动发布要留够 6 秒**，否则新实例还没宣告完就被打流量。
3. **Dubbo 调用方要配重试**，否则在窗口期会失败一次。

## 七、阶段 5：运行期——一次请求的完整穿越

服务就绪后，一次 `GET /acl/xxx` 的路径（把前面的文档全串起来）：

```
① Tomcat 线程池取一个线程
      ↓
② Filter 链（编码/鉴权…）
      ↓
③ Spring MVC DispatcherServlet 路由到 Controller
      ↓
④ AOP 切面（@Order(-9) 的审计切面在这里，往 MysqlChangeContext 塞 operator）
      ↓
⑤ Controller：参数校验 → 调 Service
      ↓
⑥ Service：业务逻辑（唯一允许写 if/for 的层）
      ↓
⑦ Mapper（动态代理）→ 决定连哪个库（DataBaseContextHolder 的 ThreadLocal 栈）
      ↓
⑧ Druid 借连接 → MySQL（10.74.0.30:8088）
      ↓
⑨ 结果集 → 映射回 POJO
      ↓
⑩ 返回；切面在 @After 里写审计（Kafka → MySQL → 邮件，三级降级）
```

**贯穿全程的两条"隐形线"**：

| 隐形线 | 在哪设置 | 在哪体现 |
|---|---|---|
| **MDC**（traceId 等 7 个字段） | 请求入口的 Filter | 每一行日志的 `[traceId]`，异步线程靠 `MdcTaskDecorator` 透传 |
| **指标**（耗时/成功率） | Druid + 切面 | 上报链路见 [[10-指标上报链路]] |

详见 [[08-日志治理]]（MDC 那一条）与 [[09-Dao 与 Entity 设计]]（路由那一条）。

## 八、阶段 6：运行期的后台线程（不随请求）

服务"在跑"不等于"只在处理请求"。同时活着好几条后台线程：

| 线程 | 干什么 | 实测证据 |
|---|---|---|
| **xxl-job 注册线程** | 每 60 秒向调度中心上报"我还活着" | `11:10:33.186` 首次失败，之后每 60s（6 小时 337 次） |
| Dubbo 心跳 | 维持 provider 存活 | `[DUBBO] ... registry` |
| Nacos 配置监听 | 长轮询，配置变了推过来 | `@RefreshScope` 生效 |
| 指标上报 | 攒批上报 | 见 [[10-指标上报链路]] |
| Kafka 消费者 | 消费 `cmdb_operate_log` 等 | 见 [[08-日志治理]] |

🔑 **理解这一层，才能解释"为什么服务没人访问也在打日志/占 CPU"**。 ⚠️ 本项目 `xxl-job` 那条线程在本地是个负面案例：地址不可达 → 每 60 秒一条错误日志 → 25 MB。

## 九、阶段 7：关闭——本项目最弱的一环

```
kill <pid>  /  docker stop
      ↓
SIGTERM
      ↓
JVM ShutdownHook
      ↓
Spring context.close()
      ↓
@PreDestroy / destroyMethod  ←── 例如 XxlJobSpringExecutor 的 destroy()
      ↓
Dubbo unexport + 注销
      ↓
Nacos 注销实例
      ↓
JVM 退出
```

### ⚠️ 但本项目**没有配置优雅停机**

✅ 实测：`S-ServiceConfig` 的所有 `*.properties` 与 Nacos 配置里，**找不到 `server.shutdown=graceful`**。

**后果**：

| 场景 | 会发生什么 |
|---|---|
| 发布时旧实例被 kill | **正在处理的请求直接被切断**（默认 `immediate`），客户端收到连接重置 |
| Dubbo 提供方被 kill | 调用方在**注销生效前**（最长一个心跳周期）仍会路由过来 → 报错 |
| 数据源连接 | Druid 有 `destroy`，但**没等业务线程结束**就关了 |

🔑 **这是 [[00-总览与学习地图]] 里"能跑但不够生产级"的一个具体证据**。**修法只要一行**（在任一共享配置里）：

```properties
server.shutdown=graceful
spring.lifecycle.timeout-per-shutdown-phase=30s
```

📌 对照 [[12-设计模式、最佳实践与设计缺陷]] §四 的缺陷清单——**"关闭"这一侧整个项目是缺位的**：启动有 18.8 秒的精心编排，关闭却是一刀切。

## 十、七个阶段 ↔ 前面各篇的对照表

生命周期是骨架，前面 14 篇是挂在骨架上的肉。

| 阶段 | 时间占比 | 主要机制 | 详见 |
|---|---|---|---|
| **0 构建期** | — | Maven profile → 占位符替换 → 环境焊进 jar | [[05-服务是怎么启动的]] §三 |
| **1 JVM 启动** | ~1 s | `PropertiesLauncher` → `Start-Class` → `SpringApplication.run` | [[06-启动与部署]] §三 |
| **2 父容器拉配置** | ~4 s | `bootstrap.*` → Nacos → 75 个 PropertySource | 本文 §四 · [[05-服务是怎么启动的]] §四 |
| **3 建 Bean** | ~10 s | 自动装配、starter、DynamicDataSource、MyBatis、Dubbo | [[04-starter 是什么]] · [[09-Dao 与 Entity 设计]] |
| **4 宣告** | ~5.6 s | Tomcat → 注册 → Dubbo 暴露 → 就绪 | 本文 §六 |
| **5 请求处理** | 稳态 | AOP、路由、MDC、审计 | [[08-日志治理]] · [[09-Dao 与 Entity 设计]] |
| **6 后台线程** | 稳态 | xxl-job、Kafka、指标 | [[10-指标上报链路]] |
| **7 关闭** | <1 s | ❌ 未配置优雅停机 | 本文 §九 · [[12-设计模式、最佳实践与设计缺陷]] |

📌 **一句话**：**启动被精心设计过，关闭被完全忽略了。** 这是一个很典型的"只关注上线、不关注下线"的系统。
