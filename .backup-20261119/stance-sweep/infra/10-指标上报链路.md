# 10 · 指标上报链路

> 🧭 **阅读顺序 10 / 14** ｜ ⬅️ [[09-Dao 与 Entity 设计]] ｜ ➡️ [[11-数据存储与分层]]

> 配套 [[00-总览与学习地图]] 的横切主线，接在 [[07-技术TODO]] 的 L7 之后阅读。
> 与 [[08-日志治理]] 同类：**讲一条数据怎么从产生端一路可靠地走到底**——只不过日志那条走的是 traceId，这条走的是 IDC 资源指标。
> 核心一句话：**把"要发的消息"当成业务数据写进数据库，用一个带租约的状态机保证它最终且仅一次地出现在 ES 里。**

---

> 📖 **术语看不懂？** → [[01-术语表]]（每个词都写了「前因 → 解决什么 → 项目里什么样 → 一句话」）

## 🎯 要点

1. **outbox 把"发消息"降级成"写数据库 + 轮询投递"**，把每个分布式难题拆成"能用单机数据库原子性解决的小问题"。
2. **幂等键 = 业务内容的 SHA256**，不是 UUID——同样内容重发天然去重。
3. **抢任务用 CAS + 租约 token，发布前要回读 ES 核对摘要**，"发了"不等于"能查到"。

---

## 一、它解决什么问题

IDC 机房的机柜资源（容量、占用、分配结果）需要定期采集，汇总成可查询的指标，供容量规划、分配效果分析使用。

朴素做法是"采集端算完直接写 ES / 发 Kafka"，但这在分布式下会连续踩到四个坑：

| 坑 | 表现 |
|---|---|
| 重复 | Dubbo 超时重试、采集端重跑，同一条事实上报两次 |
| 丢失 | 写完库、发消息前进程挂了 |
| 半成品可见 | 一个批次只到齐一半，查询却读到了不完整结果 |
| 并发 | 两个实例同时处理同一批次，互相覆盖 |

这套链路的几乎所有设计，都是在显式地回答这四问。**这才是它真正值得学的地方**——不是用了什么框架，而是把边界条件当成一等公民。

**四张表**（`S-report-service/db/idc/metrics.sql`，MySQL 5.7）：

| 表 | 一句话职责 |
|---|---|
| `rack_metric_receive_record` | 上报事实的**归档**（幂等键 + 正文摘要） |
| `rack_metric_job` | 计算/发布**任务状态机**（含租约、冻结的输入/输出清单） |
| `rack_metric_outbox` | 待发送消息的 **outbox**（同事务写入，独立投递） |
| `rack_metric_scope_version` | 统计范围当前的**代次与发布序号**（乐观锁） |

**三个任务族**（`family`）：`CAPACITY`（资源容量）、`ALLOCATION`（业务分配事实）、`ALLOCATION_DAILY`（业务日报）。

## 三、接收端：先归档，且天然幂等

**入口是一组 Dubbo 服务**（`S-DubboApi/S-report-dubbo-api`）：

- `IDubboRackResourceReportService` — 资源快照：`reportResourceSnapshotPage` / `...Complete`（另有 stream 变体）
- `IDubboRackAllocationReportService` — 业务事实：需求清单 / 尝试 / 结果 / 状态 / 评估

两个实现类都在 report-service，且都带这个注解（`DubboRackResourceReportServiceImpl.java:20`）：

```java
@ConditionalOnProperty(prefix = "idc.metrics", name = "enabled", havingValue = "true")
```

> **要点：整条链路是 opt-in 的。** 不配置 `idc.metrics.enabled=true`，服务照常启动，只是这些 Bean 和任务处理器都不装配。生产上开关就能灰度。

两个实现类**几乎不含逻辑**——它们只做一件事：把请求交给 `MetricReceiveService.receiveReport(kind, request)`。真正的机制在接收服务里。

### 3.1 分页 + 完成清单（两阶段）

采集端不是一次把整代数据发过来，而是：

1. 逐页 `reportResourceSnapshotPage(...)`，每页带 `pageNo`
2. 最后 `reportResourceSnapshotComplete(...)` 发送**结束清单**——声明"本批次应收哪些页、覆盖哪些机柜"

接收端不会在收到页时就认为数据完整，而是**等完成清单到齐后，用它来核对页是否收全**。`DubboRackResourceReportServiceImpl` 的注释写得很清楚：

> 清单是后续完整性核对的依据，收到它不代表所有数据页已经到齐。

> **设计收获**：把"数据传输"和"数据传输完毕"拆成两个显式动作。没有这个"完成"信号，接收端永远无法区分"还没发完"和"发完了但丢了一页"。这是所有流式/批量导入协议的通用套路。

### 3.2 幂等来自内容，不来自时间

每条归档记录的主键是：

```sql
UNIQUE KEY uniq_metric_receive_identity (environment, receive_key)
```

`receive_key` 是 **SHA-256 摘要**（表注释："接收幂等键（SHA-256）"），由业务身份（环境、来源应用、批次、kind、页号等）推导。另存 `body_hash` 校验正文。

于是：**同一份事实重传多次，只落一条**;补传必须发送"原固定分片"，正文和摘要都不变（否则摘要对不上，会被拒绝，而不是静默覆盖）。

> **设计收获**：幂等键要由**业务身份**推导，别用 `UUID.randomUUID()` 或时间戳——那等于没有幂等。这条在第五节还会再出现一次。

## 四、Outbox：库与消息的一致性

这是整套设计里最值得反复看的一环。

**问题**：任务算完要发 Kafka。先发消息再写库 → 写库失败消息就指向不存在的数据；先写库再发消息 → 发完崩了消息永久丢失。**数据库事务管不到 Kafka。**

**解法**：把"要发的消息"当成业务数据，写进同一个数据库事务。

`MetricOutboxService.java:33`：

```java
/** 在任务事务内归档计算结果或发布标记；提交后由发送任务投递 Kafka。 */
public MetricOutbox enqueue(JSONObject document, String generation, String family) {
```

写进 `rack_metric_outbox` 后，由**独立的轮询任务**负责投递（`MetricPipelineService.publishOutbox()`）：

```java
for (MetricOutbox row : metricOutboxMapper.findDue(...)) {
    String token = UUID.randomUUID().toString();
    if (metricOutboxMapper.claim(environment(), row.getId(), token, leaseUntil(now), now) != 1) continue;
    ...
    metricOutboxMapper.markBrokerAcked(environment(), row.getId(), token, completed);  // 回调里改状态
}
```

关键性质：

- **数据库是唯一真相来源**，Kafka 投递降级成一个可重试的副作用
- 投递是 **at-least-once**（可能重复发），但因为有 `document_key` 唯一约束 + 下游幂等，重复无害
- Kafka 回调**只改这一行状态**，不碰任务进度（`MetricPipelineService.java:807` 注释：*"回调不接触数据库或任务进度"*）

> **设计收获**：任何时候你"既要改库、又要对外发消息"，先想 outbox。这一条经验能省掉大量线上事故。`rack_metric_outbox` 表就是教科书级的 outbox 表——`status` / `attempts` / `next_retry_at` / `lease_token` / `error_code` 一应俱全。

## 五、任务状态机：租约 + CAS

### 5.1 状态流转

```
RECEIVING ──▶ SENDING ──▶ TRANSFER_COMPLETE ──▶ PUBLISHING ──▶ PUBLISHED
    │            │
    └────────────┴──▶ FAILED（永久失败，需显式 retry）
```

由 xxl-job 轮询驱动（`MetricPipelineService.processJobs()` → `metricProjectionJobHandler`），另有 `outbox/runOnce`、`projection/runOnce` 等运维入口挂在 `MetricStatusController`。

### 5.2 抢任务：把判断写进 UPDATE

```sql
UPDATE rack_metric_job SET lease_token=#{leaseToken}, lease_until=#{leaseUntil} ...
WHERE environment=#{environment} AND job_id=#{jobId} AND status=#{expectedStatus}
  AND (lease_until IS NULL OR lease_until <= #{now})
```

调用处 `if (... != 1) continue;` —— **只有受影响行数为 1 才算抢到**。

> **设计收获**：并发安全的关键是"把判断和修改合并成一个原子操作"。`affected rows == 1` 是 Java 后端最常用的原子性武器，比任何分布式锁都简单可靠。

### 5.3 Fencing token：让"睡醒的旧持有者"失效

每次抢到任务生成一个 `lease_token`（UUID），后续所有写操作都带：

```sql
AND lease_token=#{leaseToken} AND lease_until > #{now}
```

设想：A 抢到任务，因 GC 停顿 30 秒，租约过期，B 抢到并接着干。A 醒来后继续写——**它的写操作会因为 token 不匹配全部失败**，不会污染 B 的成果。`assertOwner()`（`MetricPipelineService.java:1056`）就是这个检查。

> **设计收获**：分布式里"以为还持有锁"比"没拿到锁"危险得多。**fencing token 让过期持有者的写操作自动作废**，这是比单纯租约更硬的一道保险。

### 5.4 用异常类型表达重试语义

任务循环的捕获块（`MetricPipelineService.java:205`）非常值得抄：

```java
catch (LeaseLost ignored)                 { /* 别人接管了，静默退出，不改任何状态 */ }
catch (Pending | NotReady pending)        { release(job, token, job.getStatus(), ...); }  // 依赖未就绪，保持原状态重试
catch (IllegalArgumentException invalid)  { release(job, token, "FAILED", ...); }          // 校验失败，永久失败
catch (RuntimeException transientFailure) { release(job, token, job.getStatus(), "PIPELINE_RETRY"); }
```

三个自定义异常 `LeaseLost` / `Pending` / `NotReady` 把"该怎么办"编码进了**类型**里。

> **设计收获**：`catch (Exception e)` 一把梭是新手最常见的坏习惯。让异常类型本身携带处置语义，代码可读性立刻上一个档次。

## 六、幂等的基础设施：稳如磐石的 JSON 摘要

`MetricJson.java` 是整条链路的"底座"。它做了三件事：

**1. 规范化（canonical）** —— 把 JSON 所有 map key **排序**后再序列化：

```java
public static String canonical(Object value) {
    Object tree = read(write(value), READER.constructType(Object.class));
    return JSON.toJSONString(sorted(tree), SerializerFeature.WriteMapNullValue);  // sorted() 用 TreeMap
}
```

同一份逻辑数据，无论字段顺序如何，`canonical()` 的输出**逐字节相同**。

**2. 摘要** —— 对 canonical 结果取 SHA-256：

```java
public static String hash(Object value) { return sha256(canonical(value)); }
public static String key(Object... parts) { return hash(Arrays.asList(parts)); }
public static String hashText(String json) { return hash(read(json, ...)); }
```

**3. 身份** —— 所有幂等键都由它推导：

```java
String key = MetricJson.key(environment, documentId, indexTime);   // outbox 主键
String identity = MetricJson.key(environment, source, isSimulation, kind, orderId, ...);  // 事实身份
```

**还有一处很讲究**：`MetricOutboxService.checkSameContent()`——如果 `document_key` 相同但 `payload_hash` 不同，**直接抛 `OUTPUT_CONFLICT`**，不静默覆盖：

```java
private static void checkSameContent(MetricOutbox existing, MetricOutbox candidate) {
    if (!existing.getPayloadHash().equals(candidate.getPayloadHash())) {
        throw new IllegalArgumentException("OUTPUT_CONFLICT");
    }
}
```

> **设计收获**：同一个业务身份产生不同内容，是**真 bug**，必须炸出来。静默覆盖会让问题潜伏到很久以后。

## 七、发布前断言：broker ack ≠ 数据可见

这是我认为**最见功力**的一点。

Kafka 回调返回成功，只代表消息进了 broker 队列，**不代表已经落入 ES、能被查询到**。中间还有 Flink 转存等环节，有延迟。

所以这套代码在把任务标记为 `PUBLISHED` 之前，**真的去 ES 查一遍**（`MetricPipelineService.visible()`）：

```java
SearchResponse response = esMetricClient.search(entry.getKey(),
        new SearchSourceBuilder().size(ids.size() + 1)
                .query(QueryBuilders.termsQuery("documentId", ids)));
if (response == null || response.isTimedOut() || response.getFailedShards() != 0 || ...)
    throw new Pending("ES_INCOMPLETE_SEARCH");
if (response.getHits().getTotalHits() > ids.size()) throw new Pending("ES_DUPLICATE_DOCUMENT");
...
if (!row.getPayloadHash().equals(hashes.get(row.getDocumentId()))) { missing = true; ... }
if (missing) throw new Pending("ES_VISIBILITY_PENDING");
```

逐条比对 `documentId` + 正文摘要，**全部命中才允许发布**。缺的记下来重投，未确认的抛 `Pending` 下轮再来。

而且权威性来源被明确钉在 SQL 上（`MetricJobMapper.java:113`）：

```java
/** Published SQL versions are authoritative; ES visibility alone never publishes a version. */
```

> **设计收获**：**"发送成功" ≠ "消费成功" ≠ "可被查询"**，这是三层不同的事实。异步管道里把"确认"当成"可见"，是最隐蔽的一类 bug——数据没丢，但用户查不到，还查不出原因。

### 附加：等值比较的精细处理

ES 会把 `6600.00` 读成 `6600.0`，直接比摘要必然对不上。`esSourceHash` / `restoreArchivedRepresentation`（`MetricJson.java:133`）在比较前**按等值恢复原刻度**，并注释明确"只接受精确等值，不容忍舍入或字符串转换"：

```java
if (actual instanceof Number && archived instanceof BigDecimal
        && ((BigDecimal) archived).compareTo(new BigDecimal(actual.toString())) == 0) return archived;
```

> **设计收获**：浮点数/`BigDecimal` 参与摘要或相等判断时，必须显式定义"什么算相等"。`compareTo` 而不是 `equals`，是这里的关键。

## 八、查询侧：SQL 版本才是权威

查询面挂在 `MetricQueryController`（`/rackAllocation/metrics/*`：summary / trends / hierarchy / reasons / details / dailyReports ...）和 `MetricPageController`。

一个值得注意的设计是**按时段选版本**：同一统计范围会有很多个代次，查询要选"**在请求的截止时间点之前，既已被观察到、又已发布**"的那个（`publishedAsOf` / `publishedBusinessPeriods`）：

```sql
AND COALESCE(CAST(JSON_EXTRACT(input_manifest,'$.asOfAt') AS UNSIGNED),
             UNIX_TIMESTAMP(created_at)*1000) <= UNIX_TIMESTAMP(#{asOfAt})*1000
AND updated_at <= #{asOfAt}
```

> **设计收获**：历史报表查询必须"**用当时的知识回答当时的问题**"（as-of 语义），不能拿今天修正过的数据去重算三个月前的报表，否则口径会漂移。这是数仓/报表领域的核心概念。

## 九、配置与运维入口

配置前缀 `idc.metrics`（`MetricProperties.java`），`@Validated` + `@Min`/`@Size` 让**配错就启动失败**：

| 配置 | 默认 | 作用 |
|---|---|---|
| `idc.metrics.enabled` | `false` | **总开关**（opt-in，同时控制 Bean 装配与调度） |
| `idc.metrics.environment` | — | 环境标识，用于 SQL 身份与查询隔离 |
| `...allocation-topic` / `capacity-topic` | `rack-allocation-metric-event-v1` / `rack-capacity-metric-event-v1` | 目标 Kafka topic |
| `...allocation-index` / `capacity-index` | `cn_rack_allocation_outcome` / `cn_rack_capacity_snapshot` | 目标 ES 索引 |
| `...lease-seconds` | 120 | 任务租约时长 |
| `...max-attempts` / `retry-base-seconds` / `max-retry-seconds` | 12 / 5 / 1800 | 重试策略（**指数退避**，封顶 30 分钟） |
| `...max-payload-bytes` | 524288 | 单条消息上限 |

**Kafka 生产者**（`KafkaMetricSender`）走**自建 `KafkaProducer`**（SASL_PLAINTEXT/SSL + PLAIN 认证），不用公共 starter —— 这样投递策略和公共连接解耦。`acks` 默认 `all`，且显式拒绝 `acks=0`（没有有效 offset，无法满足回读契约）。

### 实际生效的配置（Nacos）

这些配置不在代码里，而在 Nacos 的 `SHARED_GROUP/report.properties`。**这是验证第 79 行"opt-in"说法的地方**：

```properties
idc.metrics.enabled=true                    # 开关确实是显式打开的
idc.metrics.environment=test
idc.metrics.capacity-topic=rack-capacity-metric-event-test      # 注意 -test 后缀
idc.metrics.allocation-topic=rack-allocation-metric-event-test
idc.metrics.capacity-index=cn_rack_capacity_snapshot
idc.metrics.allocation-index=cn_rack_allocation_outcome
idc.metrics.kafka.server=...                # 专用 Kafka（与公共集群不同）
idc.metrics.kafka.cluster-id=287
idc.metrics.local-scheduling-enabled=true   # 本地调度开关，不走 xxl-job 也能跑
idc.metrics.outbox-delay-ms=60000           # outbox 投递间隔
idc.metrics.page.report-base-url=...        # 页面查询跳转地址
idc.metrics.page.idc-base-url=...
```

> **三点值得注意**：
> ① **topic 带 `-test` 后缀**，而 `MetricProperties` 的默认值是 `-v1`——**说明代码默认值只是兜底，真实环境靠 Nacos 覆盖**。
> ② **`idc.metrics.page.*`**（页面跳转地址）在 `MetricProperties.java` 里**没有对应字段**——它被 `MetricPageController` 直接以 `@Value` 读取，不走配置类绑定。
> ③ **`local-scheduling-enabled` / `outbox-delay-ms` 在代码中不存在**——这两个配置项目前是**冗余的**（配置有、无人读）。
> 这也印证了 [[11-数据存储与分层]] §六 的方法论：**配置项存在 ≠ 有人在用**。

```
                     outbox(待发送) ──轮询──▶ Kafka ──▶ Flink ──▶ ES
                            │                                │
                            └──── 回读 ES 核对摘要 ◀───────────┘
                                      │  全部命中
                                      ▼
                              PUBLISHED（SQL 权威）
                                      │
                                      ▼
                            查询：按时段选"当时已发布"的版本
```

**一句话总结这套设计**:把"发消息"降级成"写数据库 + 轮询投递"(outbox)，把"抢任务"降级成"带 token 的 CAS"，把"发布"降级成"回读核对"。**每一个分布式难题都被拆成了一个可以用单机数据库原子性解决的小问题。**
