## 一、这是个什么项目

滴滴内部的基础设施管理平台，管的是服务器、网络设备、机房这类物理和云上资源。底座是一套 2021 年前后定型的 Spring 全家桶：

| 组件                   | 版本       | 角色               |
| -------------------- | -------- | ---------------- |
| Spring Boot          | 2.7.17   | 应用容器 + 自动装配（按依赖自动装好组件）      |
| Spring Cloud         | 2021.0.7 | 服务发现（按服务名查地址）的统一抽象           |
| Spring Cloud Alibaba | 2021.1   | Nacos 集成         |
| Dubbo                | 3.2.5    | RPC 远程调用         |
| Nacos                | —        | 配置中心（存参数）+ 注册中心（存服务地址），二合一 |
| MyBatis + Druid      | —        | 数据访问 + 连接池（复用数据库连接）       |
| Logback + MDC        | —        | 日志治理基座           |

规模上，它由 16 个顶层模块组成，里面有 42 个带 `main` 方法（程序入口）的服务、31 个自定义 starter（自带装配说明的依赖包）、19 个 Dubbo API 契约模块（只放接口定义、供调用双方共用的包），Java 代码约 45 万行。

## 二、模块分层：三类模块，只有一类能启动

初学最容易误判的一点：点开一个模块发现里面没有 `main` 函数，怀疑自己找错了地方。其实没找错——项目里的模块分三类。

```
┌─────────────────────────────────────────────────────────────┐
│ ① 可启动服务 (42 个) —— 有 XxxApplication.java，有 main      │
│    S-ServicesNet/S-acl-service                              │
│    S-ServicesCmdb/S-idc-ops-service                         │
│    S-WrokOrder/S-dns-order ...                              │
├─────────────────────────────────────────────────────────────┤
│ ② 库模块 —— 无 main，只被依赖，打进 ~/.m2 当 jar            │
│    S-Core          公共工具 (Result/Page/Utils)             │
│    S-Dao/*   (4)   MyBatis DAO 层                           │
│    S-Entity/* (4)  POJO 实体                                │
│    S-DubboApi/* (19) Dubbo 接口契约                         │
│    S-starter/* (31) 自定义 Spring Boot starter              │
│    S-ServiceConfig  bootstrap 配置                          │
├─────────────────────────────────────────────────────────────┤
│ ③ 聚合模块 —— 只有 pom.xml (packaging=pom)，无 main         │
│    S-ServicesNet / S-ServicesCmdb / S-starter ...           │
│    作用：用 <module> 聚合下面的子模块，只是父 pom           │
└─────────────────────────────────────────────────────────────┘
```

判断一个模块属于哪一类，看 `pom.xml` 的 `<packaging>` 就够了：

- `pom` 就是聚合模块，只是父 pom，不产出代码包
- `jar` 且有 `*Application.java` 就是可启动服务
- `jar` 但没有 main 就是库模块，打进 `~/.m2` 供别人依赖

所以看到 `S-ServicesNet` 这种目录名，不用急着找 main。它本身是聚合模块，真正的服务在它下面的子目录里。

## 四、一个服务启动时：两个阶段 + 一个收尾动作

顺序就三步，括号里是 `acl` 本机启动的真实时刻。**17 步真实日志逐毫秒对照见 [[14-系统生命周期全景]]§一，父子容器机制见 [[05-服务是怎么启动的]]§二**：

```
① 拉配置   bootstrap 父容器连 Nacos，拉回 75 个配置填进 Environment   (11:09:53 → 11:09:55)
② 建 Bean  主容器继承 Environment；31 个 starter 受 @Conditional 约束装配 (11:09:56 → 11:10:11)
③ 宣告     Dubbo 暴露/订阅 + Nacos 注册——长在 ② 的 refresh 收尾处，不是独立阶段 (11:10:05 → 11:10:11)
```

这里有一条因果贯穿全局：**② 建 Bean（容器管理的对象）时用到的配置，全部来自 ① 装好的 Environment（汇总所有配置来源的对象）**。

所以 Nacos 的连接信息只能写在 `bootstrap.*`，不能写在 `application.*`。后者属于主容器，在阶段一根本还没被读到，写了等于没写。

报错会长这样—— `NacosException: failed to req API:/nacos/v1/cs/configs`，而且发生在任何 Bean 创建之前，很容易误判成"Nacos 挂了"。

📌 本项目引 `spring-cloud-starter-bootstrap`，符合 Spring Cloud 当年默认机制。✅ 规范：Boot 2.4+ 用 `spring.config.import=nacos:` 替代 bootstrap 父容器。

📌 顺序就三句话：**先拉配置（①），再建 Bean（②），最后宣告（③）**。

## 五、日志治理全景（详见 `08-日志治理`）

一个请求从进来到落盘，要过四道关卡：

```
请求进来
  │
  ▼
[HTTP 层] LogMvcTraceFilter (Spring MVC HandlerInterceptor)
  │  读 header: Didi-Header-Rid / Didi-Header-Cspanid
  │  没有就生成 traceId → 塞进 MDC
  │
  ▼
[业务层] 业务代码 log.info(...)
  │  logback Pattern 从 MDC 取值拼进日志行
  │
  ▼
[Dubbo 层] LogDubboTraceFilter (Dubbo Filter)
  │  消费端：把 MDC 里的 traceId/CspanId 塞进 RpcContext attachment
  │  提供端：从 attachment 取出塞进自己的 MDC
  │
  ▼
[定时任务] XxlJobAspect (AOP Around)
  │  进方法前生成新 traceId 塞 MDC，出方法时 clear
  │
  ▼
[落盘] logback AsyncAppender → app-log / sql-log 文件
  │
  ▼
[采集] filebeat → logstash (grok 解析) → Elasticsearch
```

核心机制是 **MDC**（Mapped Diagnostic Context）——一个 ThreadLocal（线程私有的储物柜）里的 map，日志的 Pattern（输出格式模板）用 `%X{key}` 从里面取值。所谓"全链路追踪"，说到底就是把 traceId 一路塞进各个服务的 MDC 里。细节见 [[08-日志治理]]。

## 七、阅读顺序

编号就是顺序，`00` 到 `14` 顺着读即可。如果只想按目的走捷径：

| 目的 | 读法 | 大约 |
|---|---|---|
| **只想把它跑起来** | `00` → `06-启动与部署` | 半小时 |
| **系统学一遍**（推荐） | `00` → `01` → … → `14` 顺读 | 几天 |
| **准备面试** | `00` → `01 术语` → `02 模块` → `05 启动` → `09 持久化` → `12 设计取舍` → `13 面试题` | 一天 |

读完 `05` 想看全景，可以跳到 [[14-系统生命周期全景]]——它把 7 个阶段串成一条时间线，并且回答"为什么配置必须写在 `bootstrap.*`"。放最后当复盘可以，`05` 之后先跳过去也可以。

`07-技术TODO` 是另一份课表：L0 认路到 L8 数据流转，九层，每层带验收标准和记录位。而 `00~06` 是把 07 里最前面几层单独展开成"能读懂"的版本，读完再回去对号入座。

整条路径的原则一句话：**从看得见的现象到看不见的原理，从单个服务到多服务协作，横切关注点（日志、鉴权这类每个业务都需要的公共逻辑）放最后。** 其中 L2（自动装配，见 `04`）、L4（Dubbo）、L5（日志治理，见 `08`）是主菜，时间要舍得花。

有两点是刻意安排的。一是 L1 之后插了一层 L★「跟一条工单走」，先看 `POST /domain/apply` 全链路，让后面每一层都有具体问题可回答。二是启动排得很靠前，不是"最后一做"——它只要 5 分钟，却能让你看见真实日志和真实端口，见 [[06-启动与部署]] §三。
