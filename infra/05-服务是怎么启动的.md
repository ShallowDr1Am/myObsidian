# 05 · 服务是怎么启动的：两个阶段 + 一个收尾动作

> 🧭 **阅读顺序 05 / 14** ｜ ⬅️ [[04-starter 是什么]] ｜ ➡️ [[06-启动与部署]]

> ⏭️ **想看完整的「从构建到关闭」生命周期**（本文只讲启动），见 [[14-系统生命周期全景]]。

> 📖 **术语看不懂？** 查 [[01-术语表]]：每个词都先讲前因，再说它解决什么、项目里什么样，最后用一句话收尾。

## 🎯 要点

1. **启动是「两个阶段 + 一个收尾动作」**：
   先 ① 拉配置（bootstrap 父容器，一个更早启动、专管拉配置的容器），再 ② 建 Bean（容器管理的对象，在主容器里），最后 ③ 收尾（Dubbo 暴露 + 服务注册）。**③ 不是独立阶段**——它长在 ② 的 refresh（容器刷新，即初始化流程）尾巴上。三件事是**串行**的，不是并列的。
2. **Nacos 地址只能写 `bootstrap.*`，这不是"规定"，是鸡生蛋**：拉配置需要地址，
   而地址本身也在配置里。所以"连哪儿"必须来自配置之外的地方（`bootstrap.*` / 命令行 / 环境变量）。
3. **3 个命名空间是 3 种用途，不是 3 套环境**：
   配置在 `public`（靠 **group**（配置分组）分环境）、Spring Cloud 服务在 `74b75ca6`、Dubbo 接口在 `529be423`。**一个服务会注册两次，进两个不同的命名空间。**

---

## 一、先用一个比喻把三件事串起来

把启动一个服务想成**开一家店**：

| 阶段 | 比喻 | 技术上的对应 |
|---|---|---|
| **①** 拉配置 | 先去**物业**拿钥匙、拿户型图、拿水电账户 | 建一个"父容器"，连 Nacos 把配置拉进 Environment（汇总所有配置的对象） |
| **②** 建 Bean | 按图纸**装修**：装水电、摆货架、招人 | 按配置建 `DataSource`（数据库连接池）/ `RedisTemplate`（Redis 操作工具）/ 各种 Bean |
| **③** 挂牌营业 | 装修完在**门口挂牌**、在**商会登记** | 把本服务注册到 Nacos，让别人能发现你 |

🔑 **关键就在这个比喻里**：你**不可能**把"物业的地址"写在"物业给你的户型图"上—— 因为户型图是要去物业才能拿到的。**这就是 `bootstrap.*` 存在的唯一理由。**

⚠️ 而且注意：**"挂牌"（③）是装修（②）干完之后才做的事**。所以它压根不是"第三个独立阶段"，而是第二阶段收尾时的一个动作。

---

## 二、为什么必须先拉配置：父子容器机制

这不是"约定"，是 Spring Cloud 的实现方式。📌 本项目引入了 `spring-cloud-starter-bootstrap`（`S-ServiceConfig/pom.xml:24`），走**老的 bootstrap 机制**，符合 Spring Cloud 当年默认。✅ 规范：Boot 2.4+ 用 `spring.config.import=nacos:`（无需父容器）。

```
┌─────────────────────────────────────────────┐
│  阶段①  Bootstrap 容器（父）                 │
│  ├─ 读 bootstrap.properties                  │
│  │    spring.profiles.active=test            │
│  ├─ 读 bootstrap-test.properties             │
│  │    nacos.server-addr=10.78.128.115:8848   │  ← 只有这里能写
│  │    discovery.namespace=74b75ca6...        │
│  │    config.extension-configs[0..74]        │
│  ├─ 连 Nacos，按 dataId+group 拉 75 份配置    │
│  └─ 把结果放进自己的 Environment  ★          │
└──────────────────┬──────────────────────────┘
                   │ 父 Environment 被继承
                   ▼
┌─────────────────────────────────────────────┐
│  阶段②  主容器（子）                          │
│  ├─ 扫描 starter 的自动配置（@Conditional）   │
│  ├─ 建 DataSource：需要 spring.datasource.*  │ ← 这时才读得到
│  │     ↑ 这些值刚从 Nacos 拉下来              │
│  ├─ 建所有 Bean、AOP 代理、事务管理器         │
│  └─ refresh 收尾【③】：Dubbo 导出/订阅 + 注册 │ ← ③ 在这里
└─────────────────────────────────────────────┘
```

🔑 **一句话**：① 的产物是**一个装满了配置的 Environment**；② 的输入正是它。所以顺序不是"设计得好"，是**语法上不可能反过来**。

### 反证：把 Nacos 地址写进 `application.properties` 会怎样

启动会失败，报类似 `no server address` / `NacosException: failed to req API`。

原因：**主容器读到 `application.properties` 时，拉配置那一步早就该做完了**—— 它在父容器里执行，那时它还不知道地址。

⚠️ **这就是那条铁律的来源**：凡是"用来取配置的配置"，都只能放在 `bootstrap.*`、命令行参数、环境变量这三个地方。

## 三、必须"提前知道"的三样东西

只有三样，记住这三样就够了：

| 必须先知道 | 为什么 | 本项目在哪 |
|---|---|---|
| **Nacos 地址** | 不然连不上，拉不到任何配置 | `bootstrap-<env>.properties` 的 `nacos.server-addr` |
| **当前是哪个环境** | 决定加载哪个 `bootstrap-<env>.properties` | ⚠️ **见下：不是启动时选的** |
| **命名空间 + 分组 + dataId（一份配置的文件名）** | 决定"拉哪几份" | `discovery.namespace` + `config.extension-configs[i].group` |

### ⚠️ 机制易误判点：环境不是启动时选的，是**编译时写进 jar 的**

这是本项目一个很关键、也很反直觉的设计。📌 已核实：

```properties
# S-ServiceConfig/src/main/resources/bootstrap.properties  第 1 行
spring.profiles.active=@activatedProperties@     ← Maven 占位符，不是真值
```

```xml
<!-- 根 pom.xml：6 个 profile，test 是默认 -->
<profile><id>test</id>  <activation><activeByDefault>true</activeByDefault></activation>
         <properties><activatedProperties>test</activatedProperties></properties></profile>
```

```
profile → activatedProperties
dev          dev
test         test      ← activeByDefault = true（不写 -P 就是它）
prod         prod
prodhnd      prodhnd
clouddnsprod clouddnsprod
clouddnsdev  clouddnsdev
```

📌 **实测证据**（本机编译产物）：

```
$ unzip -p ~/.m2/repository/com/didi/S-ServiceConfig/1.0-SNAPSHOT/S-ServiceConfig-1.0-SNAPSHOT.jar \
        bootstrap.properties | grep profiles.active
spring.profiles.active=test        ← 占位符已经被替换掉了，环境被"固化"在 jar 里
```

🔑 **这解释了一件很实际的事**：本地起 acl 时**没有**传 `--spring.profiles.active`，但它自动就是 test 环境（TEST_GROUP / `74b75ca6` / `529be423`）—— 因为编译时 `-P` 没写，走了 `activeByDefault=true` 的 **test**。（对照 [[06-启动与部署]]：这就是为什么本地 Nacos 里只有 26 份 TEST_GROUP 配置。）

📌 当年约定：编译期固化环境——同一份代码出 **6** 个 jar，换环境需重编译；好处是发布物与环境一一对应、杜绝启动参数传错。

✅ 规范：配置外部化，启动时 `--spring.profiles.active=xxx` 指定（12-Factor Ⅲ）；取舍背景见 [[12-设计模式、最佳实践与设计缺陷]] §四。

## 四、3 个命名空间是 3 种用途（不是 3 套环境！）

这是最容易搞错的一处。很多人以为 `namespace` 就是按 `dev/test/prod` 分的—— **实测不是**：配置全在 `public`，**靠 group 分环境**。

### 4.1 本项目的真实坐标（📌 全部实测）

下表中的 ns 是 namespace（命名空间）的缩写。

| profile | Nacos 地址 | 配置 group | Spring Cloud 发现 ns | Dubbo ns |
|---|---|---|---|---|
| **dev** | `10.78.128.115:8848` | `DEV_GROUP` | `d77878cb…` | `f5d05fb1…` |
| **test** | `10.78.128.115:8848` | `TEST_GROUP` | `74b75ca6…` | `529be423…` |
| **prod** | `nacos.cmdb.intra.xiaojukeji.com:8848` | `PROD_GROUP` | `c824ad69…` | `36c2b01e…` |
| **prodhnd** | `nacos.cmdb.intra.xiaojukeji.com:8848` | `PROD_HND_GROUP` | `1c58a3c9…` | `4f6ea66c…` |
| **pretest** | `smart-nacos01/02/03.intra…:8000` | `PRETEST_GROUP` | `4ceb8a8b…` | — |
| **canoe** | `10.207.0.254:8051,8052,8053` | `CANOE_GROUP` | `612b7ee3…` | — |

📌 三个观察：
- **配置命名空间从来没被设置**（`spring.cloud.nacos.config.namespace` 在 6 个文件里都不存在），
  所以默认就是 `public`。**分环境靠的是 group**，不是 namespace。
- 发现的命名空间**每个环境都不同**——所以"namespace 按环境分"这句话**只对发现服务成立**。✅ 规范：环境隔离用独立 namespace，或 group + 启动期断言（漏配 fail-fast）。
- dubbo 还有**第三套**命名空间，和上面两套都不一样。

### 4.2 🔑 一个服务会注册两次（这是理解的钥匙）

📌 实测本机 Nacos 三个命名空间的内容：

```
discovery ns (74b75ca6)  → acl, dgw
                           └─ Spring Cloud 服务（HTTP/REST，@EnableDiscoveryClient）

dubbo ns (529be423)      → dubbo-dgw
                           providers:com.didi.dubbo.IDubboDgwService::
                           └─ Dubbo 接口（@DubboService，RPC）

config ns (public)       → 26 份配置（datasource.properties 等，按 group 分环境）
```

🔑 **所以 acl 这一个进程，在 Nacos 里留下了两个足迹**，分别进两个命名空间：

| 谁去注册 | 注册什么 | 进哪个 ns | 由谁触发 |
|---|---|---|---|
| Spring Cloud Discovery | `acl` 这个**服务名**（HTTP） | `74b75ca6` | `@EnableDiscoveryClient` |
| Dubbo Registry | `com.didi.service.XxxService` **接口** | `529be423` | `@EnableDubbo(scanBasePackages="com.didi.service")` |

📌 已核实 `AclApplication` 上三个注解并存：

```java
@SpringBootApplication(exclude = {DataSourceAutoConfiguration.class})
@EnableDiscoveryClient
@EnableDubbo(scanBasePackages = "com.didi.service")
public class AclApplication { ... }
```

⚠️ **这里有个很常见的误解**：以为"注册到 Nacos"是一件事。实际是**两套注册体系**（Spring Cloud 的服务发现 + Dubbo 的接口注册），它们碰巧都用 Nacos 当存储，但走的是**不同的客户端、不同的命名空间、不同的注册内容**。

## 五、收尾动作在时序的哪一步

③ 不是第三个并列阶段，它挂在主容器 refresh 的**尾部**：

```
阶段① Bootstrap 容器
  └─ 拉配置进 Environment

阶段② 主容器
  ├─ 1. 准备 Environment（此时能读到 Nacos 的配置了）
  ├─ 2. 扫描 starter 自动配置 → 建所有 Bean 定义
  ├─ 3. 实例化单例（DataSource / RedisTemplate / ServiceImpl…）
  ├─ 4. AOP 代理、事务管理器就绪
  ├─ 5. ★ Dubbo 导出 provider、订阅 reference
  ├─ 6. ★ 注册到 Spring Cloud Discovery
  └─ 7. 发布 ContextRefreshedEvent → "Started AclApplication in X seconds"
```

🔑 **判据**：你看到日志里出现 `Started AclApplication` 时，① 和 ③ **都已经完成了**。所以三者不是并列关系，而是包含关系：先 ①，再 ②，③ 长在 ② 里面。

## 六、三个常见误解

### 误解 1：「namespace 按 dev/test/prod 分」
📌 **只对了一半**：发现服务确实每环境一个 ns，但**配置在 public，靠 group 分**，Dubbo 又是第三套 ns。**三个 ns 是三种用途，不是三个环境。**

### 误解 2：「扫描所有 jar 的 `META-INF/spring.factories`」
📌 **两个补充**：
- Spring Boot 2.7 同时支持 `META-INF/spring.factories` 和
  `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`（后者是新方式，前者已标记废弃）。
- **本项目的 `S-datasource` 骨架故意没有 `spring.factories`**（见 [[09-Dao 与 Entity 设计]] §三），
  靠主应用的组件扫描（按包路径自动发现类）生效。所以"扫描所有 jar"这句话在本项目**不成立**。

### 误解 3：「拉配置、建 Bean、注册 是三件独立的事」
📌 三者是**串行**的，且**注册本身还分两套**（Spring Cloud 注册 + Dubbo 注册），见 §4.2。

## 七、自己动手验证（4 个方法，都能在 10 分钟内做完）

**方法 1：开 debug，看配置从哪来**

```bash
cd ~/Desktop/learn/podman
NOPROXY=1 EXTRA_ARGS="--debug $(cat localnacos/idea-args.txt)" bash svc.sh start acl
```
日志里搜 `Located property source`，会按先后逐条列出：先 `bootstrap.properties`，再 `bootstrap-test.properties`，然后是 Nacos 的每个 dataId（配置文件名）。**这一条就是"① 早于 ②"的直接证据。**

**方法 2：看 bootstrap 阶段的独立日志**

日志里会有 `Bootstrap` / `spring.cloud.bootstrap` 相关行，出现在 `Starting AclApplication` **之前**。

**方法 3：数 Nacos 里的足迹**（验证"一个服务注册两次"）

```bash
# Spring Cloud 服务
curl -s "http://127.0.0.1:8848/nacos/v1/ns/service/list?pageNo=1&pageSize=50&namespaceId=74b75ca6-80d4-4313-8f49-409d4acefd06"
# Dubbo 接口
curl -s "http://127.0.0.1:8848/nacos/v1/ns/service/list?pageNo=1&pageSize=50&namespaceId=529be423-bf30-4721-a8e1-e9db3422cd19"
```

**方法 4：确认环境是编译时定的**

```bash
unzip -p ~/.m2/repository/com/didi/S-ServiceConfig/1.0-SNAPSHOT/S-ServiceConfig-1.0-SNAPSHOT.jar \
  bootstrap.properties | grep profiles.active
# 输出 test → 说明环境已被写进 jar
```

## 八、一句话总结

```
编译期：mvn -P test    →  spring.profiles.active 固化进 jar
   │
启动期：
   │
   ├─【阶段①】Bootstrap 父容器
   │     读 bootstrap.properties（知道是 test）
   │     读 bootstrap-test.properties（知道 Nacos 在哪）
   │     连 Nacos，按 group=TEST_GROUP 拉 75 份配置
   │     → Environment 装满
   │
   └─【阶段②】主容器（子）
         用 Environment 建 DataSource/Redis/... （@Conditional 决定装不装）
         └─ 收尾【③】：
              ① Dubbo 导出/订阅 → 注册进 dubbo ns 529be423
              ② Spring Cloud 注册服务名 → 注册进 discovery ns 74b75ca6
         → "Started AclApplication in 18.8s"
```

🔑 **记住顺序的唯一方法**：问自己"**谁需要谁**"。建 DataSource 需要 `spring.datasource.*`，这些值在 Nacos 里，所以要先进 Nacos；而进 Nacos 需要地址，地址不能在 Nacos 里。**这个依赖链就是全部答案。**
