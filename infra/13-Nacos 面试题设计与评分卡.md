## 零、先想清楚：问 Nacos 到底在测什么

**不是考"会不会 Nacos"**，而是借 Nacos 这个载体，测三件事：

```
① 有没有独立理解过分布式组件（而不是背八股）
② 遇到"东西挂了"能不能推理（而不是只会背配置）
③ 有没有真实项目上下文（还是只有简历 + 八股）
```

想清楚这个，题就好设计了。

### 大多数面试官只问了第一层

| 层 | 考察 | 典型题 | 大致通过率 |
|---|---|---|---|
| **L1 会不会用** | 概念 | Nacos 能干什么？ | ~90% |
| **L2 懂不懂原理** | 机制 | 配置怎么实时生效？ | ~50% |
| **L3 懂不懂取舍** | 判断 | 为什么选它不选 Eureka？ | ~20% |
| **L4 有没有实战** | 推理 | Nacos 挂了服务会怎样？ | ~10% |

> **L1 是筛子，L2 是及格线，L3 / L4 才是分水岭。** 只问 L1 等于没问。

## 一、L1 · 筛子题（30 秒分流）

### 题

> **"说一下 Nacos 能做什么。"**

### 听什么

| 回答 | 判断 |
|---|---|
| "注册中心 + 配置中心" | ✅ 及格，往下走 |
| 只说"注册中心" | ⚠️ 停留在 Eureka 认知，可引导 |
| "服务治理平台""微服务基础设施" | 🚩 **危险信号：在堆词，可能没真用过** |
| 说不出 | ❌ 到此为止 |

### 面试官笔记

这一步**只为分流，不占时间**。注意那个危险信号——**能说出"两大能力"这种具体表述的，通常比说"服务治理"的更真实**。后者是被 PPT 训练出来的语言。

## 二、L2 · 原理题（核心，一定要追问）

### 主问题

> **"配置改了，客户端怎么知道？"**

预期答案是**长轮询**。但**关键不是他答对，而是接下来追三层**。

> 生活类比：长轮询就像打电话问餐厅「我的菜好了吗」——不是每 30 秒挂断重拨一次，而是服务端不挂电话，等菜好了再答复；等了约 30 秒还没好，才先挂断让你重拨。

### 追问树

```
他答「长轮询」
 │
 ├─ 追① 为什么不用「每 30 秒拉一次」？
 │      ✅ 好答案：定时拉取有窗口期，配置生效延迟不可控；
 │                频繁拉取又浪费服务端资源
 │      ❌ 差答案：「短轮询性能差」（只背了结论，说不出为什么）
 │
 ├─ 追② 长轮询具体「长」在哪？
 │      ✅ 好答案：服务端 hold 住请求不立即返回，有变更才响应；
 │                超时时间 29.5s，略小于客户端 30s 超时，避免客户端先断
 │      ⚠️ 只知道"长轮询"三个字 = 背的
 │
 ├─ 追③ hold 住期间发生了 3 次变更呢？
 │      ✅ 好答案：感知到变更就返回（比对 md5/版本），
 │                客户端拿到最新一次，中间态被跳过是正常的
 │
 └─ 追④（杀手锏）10 万客户端都 hold 住，连接数怎么办？
        ✅ 好答案：Nacos 2.x 用 gRPC 长连接 + 变更合并推送，
                  不是「一请求一连接」；1.x 才是 HTTP 长轮询
        ⭐ 能答出这层，基本确认读过源码或踩过坑
```

> **通用技巧**：任何概念题，**答对了就再追一层"那如果……呢"**。
> 八股背得再熟，也经不起三连追问。**追④ 是分水岭。**

### 变体题（同样考 L2）

- "客户端和 Nacos 断了，配置还会生效吗？"
- "`@RefreshScope` 的原理是什么？"（答案要点：销毁旧的 Spring 管理对象并重建，让新配置生效）
- "配置的 md5 是干什么的？"（md5 是按内容算出的指纹，指纹不同就说明内容变了）

## 三、L3 · 取舍题（测判断力）

### 主问题

> **"你们为什么用 Nacos，不用 Eureka 或 Zookeeper？"**

### 陷阱

这题的陷阱是：**很多人会答"Nacos 更好"——这是错误答案。**

技术选型**没有绝对好坏**。听到"Nacos 功能更全 / 性能更好"，说明他还没有工程判断。

### 听什么

| 回答 | 判断 |
|---|---|
| "Nacos 更好 / 功能全 / 性能好" | ⚠️ 泛泛而谈 |
| 能列功能对比（配置中心、AP/CP 可切） | ✅ 及格 |
| **"取决于场景，我们选它是因为 X"** | ✅✅ 有工程判断 |
| "因为公司都在用" | ⚠️ 诚实但没思考，追问"那你会怎么选" |

### 追问链

```
追① Nacos 是 AP 还是 CP？
   ✅ 标准答案：都有。临时实例用 Distro（AP），持久实例和配置用 Raft（CP）

追② 注册中心你希望它是 AP 还是 CP？为什么？
   ✅ 好答案：AP。服务列表短暂不一致可接受（最终一致即可），
             但如果注册中心不可写，整个集群就瘫痪了 —— 可用性优先
   🚩 答"CP 更安全所以更好" = 没懂 CAP 在注册中心场景的取舍

追③ 配置中心呢？
   ✅ 好答案：偏 CP。配置必须一致，不能出现「A 机器拿到新配置、B 没有」
```

> CAP（分布式系统在一致性、可用性、分区容错之间的取舍）白话版：AP 像连锁便利店的价格表——各分店价格短暂不一致也能继续卖货（可用性优先）；CP 像银行账户余额——所有网点必须看到同一个数，对不上宁可暂停柜台（一致性优先）。注册中心更像价格表，配置中心更像余额。

> **答出"为什么注册中心选 AP"这一层**，说明他真懂 CAP 取舍，而不是背定义。

### 对照表（面试官自用，不必给候选人）

| 维度 | Nacos | Eureka | Zookeeper |
|---|---|---|---|
| CAP | **AP / CP 可切换** | AP | CP |
| 健康检查 | 心跳 + 主动探测 | 心跳 | 会话 |
| 配置中心 | ✅ 内置 | ❌ | ❌ |
| 一致性协议 | Distro(AP) / Raft(CP) | 无（最终一致） | ZAB |
| 长连接 | 2.x gRPC | HTTP | TCP 会话 |

## 四、L4 · 实战题（测真实经历）

### 主问题

> **"如果 Nacos 集群全挂了，你们的服务会怎样？"**

**这题最能分辨"真做过"和"背过"。**

### 预期

服务**还能跑**——客户端有本地容灾：

```
~/.nacos/config/    配置快照
~/.nacos/naming/    实例列表缓存
```

### 追问链

```
追① 那新启动的服务呢？
   ✅ 起不来 —— 拿不到配置（这也是本项目无法脱离内网启动的原因）

追② 为什么已有的服务能跑？
   ✅ 本地缓存 + 启动后不做强校验
   ⭐ 加分：能提到「比的是快照，不是实时拉」

追③（陷阱）Nacos 恢复后返回了空列表，会怎样？
   ✅ 好答案：推空保护 —— 客户端会忽略空列表
   ⭐ 否则会把所有可用实例清空，造成「雪崩式」服务不可用
   ⭐ 能答出「推空保护」= 真在生产上踩过

追④ 配置中心挂了，我现在改配置还生效吗？
   ✅ 不生效，但已有的也不回滚（保持最后一份快照）
```

> **追③是高级考点。** 八股文里一般不写，能答上来说明有真实运维经验。

## 五、进阶：完整推演题（看思维结构）

### 题

> **"你改了配置，发现只有部分机器生效。你会怎么排查？"**

**没有标准答案，看的是排查方法论。**

### 好答案的结构

```
① 先确认范围        —— 是全部还是部分？哪些实例？有没有规律（同机房/同版本）
② 分层定位          —— 客户端没拉到 / 拉到了没刷新 / 刷新了没生效
③ 具体手段
   · 客户端：看 ~/.nacos 快照的时间戳和 md5
   · 配置侧：看 Nacos 控制台是否推送成功、namespace/group/dataId 对不对
   · 代码侧：有没有 @RefreshScope、refresh=true
   · 陷阱：属性注入到了「非 Spring 管理的对象」里，刷新不到
④ 兜底结论          —— 如果是长轮询断连，会退化成定时拉取
```

**加分点**：主动说"**先看日志里配置的 md5 有没有变**"——说明真排查过。

**扣分点**：一上来就猜"重启试试"，没有分层思路。

## 六、高阶：让他现场读代码 ★★

**这是最能拉开差距的一招**——比问八股有效得多。

本项目正好有现成素材：

```
S-starter/S-dubbo-starter/src/main/java/com/didi/NacosRegistry.java   (490 行)
```

给它 5 分钟，然后问下面四题。

### 题 1：`doRegister` 做了什么？

> **考察**：能不能快速定位、读懂调用链。

**答案要点**：

```java
public void doRegister(URL url) {
    final String serviceName = getServiceName(url);   // 拼出服务名
    final Instance instance = createInstance(url);    // URL → Nacos Instance
    execute(namingService -> namingService.registerInstance(serviceName, instance));
}
```

> 关键观察：**它自己没有维护实例列表，而是把注册委托给 Nacos 的 `NamingService`**。
> 说明这个类是一层**适配器（Adapter）**——把 Dubbo 的 `URL` 模型翻译成 Nacos 的 `Instance` 模型。

### 题 2：`doSubscribe` 为什么既"拉"又"推"？

> **考察**：推理解能力，这是全篇最好的一题。

**答案要点**：

```java
for (String serviceName : serviceNames) {
    List<Instance> instances = namingService.getAllInstances(serviceName);  // ① 先拉一次
    notifySubscriber(url, listener, instances);                              //    立即通知
    subscribeEventListener(serviceName, url, listener);                      // ② 再订阅
}
```

> **① 拉 + ② 推，缺一不可**：
> - **只订阅不先拉**：订阅是"之后的变化"，中间若无人变更，你永远拿不到当前实例
> - **只拉不订阅**：拿不到后续变更，等于定时拉取
>
> 这是**分布式订阅的标准模式**：**先建立当前快照，再订阅增量**。

### 题 3：`subscribeEventListener` 里那个 `nacosListeners` map 干什么用？

> **考察**：并发 / 资源管理的敏感度。

**答案要点**：

```java
if (!nacosListeners.containsKey(serviceName)) {   // ← 去重
    EventListener eventListener = ...;
    namingService.subscribe(serviceName, eventListener);
    nacosListeners.put(serviceName, eventListener);  // 缓存，避免重复订阅
}
```

> **防止对同一个 serviceName 重复订阅**——重复订阅会让回调触发多次、浪费连接。
> `ConcurrentHashMap` 说明它预期被多线程访问（Dubbo 订阅发生在并发场景）。

### 题 4：这个类继承了 `FailbackRegistry`，意味着什么？

> **考察**：能不能读出继承背后透露的设计意图。

**答案要点**：

> `FailbackRegistry` 是 Dubbo 提供的**带失败重试的注册中心基类**。
> 继承它意味着：**注册/订阅失败时，会自动记录失败项并定时重试**。
>
> 这是"**注册中心必须最终一致**"这一认识在代码里的体现——不能因为一次网络抖动，
> 服务就再也注册不上了。

### 题 5（反转）：**项目最后弃用了这套自研实现，为什么？**

> **考察**：批判性思维 + 工程判断。**这题在八股里找不到答案。**

**📌 事实**：`NacosRegistryFactory` 整个文件被注释掉了，pom 里改用了官方 `dubbo-registry-nacos`：

```xml
<artifactId>dubbo-registry-nacos</artifactId>
<version>${dubbo.version}</version>
```

**参考答案要点**（开放题）：

- 自研维护成本高：Dubbo 版本升级要跟着改（注意这个类 import 的**还是 `com.alibaba.dubbo`**，即老版包名）
- 官方实现有社区维护，边界情况处理更全
- 自研的收益（定制）不足以覆盖长期维护成本

> **能答出"维护成本 vs 定制收益"这个权衡的，是真有工程判断的人。**

## 七、评分卡（建议直接用）

| 维度 | 权重 | 5 分（超预期） | 3 分（达标） | 1 分（不及格） |
|---|---|---|---|---|
| **概念准确** | 20% | 能讲清 AP/CP 双模式 | 知道两大能力 | 把 Nacos 说成网关/消息队列 |
| **原理理解** | 30% | 长轮询细节 + gRPC 演进 | 知道"长轮询" | 说"定时拉取" |
| **取舍判断** | 25% | 从 CAP / 场景推导选型 | 能列功能对比 | "Nacos 更好" |
| **容灾推理** | 25% | 提本地缓存 + 推空保护 | 知道有缓存 | 认为会全挂 |

### 红线（直接扣分）

- 🚩 把 Nacos 说成"消息队列"或"网关"
- 🚩 坚持"AP 一定比 CP 好"（典型没读懂 CAP）
- 🚩 被追问两次就开始编（**宁可说"这块我没深入"，也不要硬编**）

### 绿灯（加分）

- 🟢 主动区分"临时实例 / 持久实例"的不同一致性策略
- 🟢 能说出 **29.5s**、**推空保护** 这类具体机制或数字
- 🟢 承认边界："这块我没深入，但我推测是……"（诚实 + 有推理）

## 九、一页速查（面试官手上拿这张）

```
L1 筛子  「Nacos 能做什么？」
         → 听到「服务治理平台/基础设施」= 危险信号

L2 原理  「配置改了客户端怎么知道？」
         追：为什么不用定时拉？→ 29.5s 细节？→ 3 次变更？→ 10 万连接？
         → 追④能答出来 = 通过

L3 取舍  「为什么不用 Eureka？」
         追：AP 还是 CP？→ 注册中心该选哪个？为什么？
         → 答"注册中心要 AP" = 通过

L4 实战  「Nacos 全挂了会怎样？」
         追：新服务呢？→ 返回空列表呢？
         → 答出「推空保护」 = 通过

★ 读代码 NacosRegistry.java
         doRegister / doSubscribe（拉+推）/ 为什么去重 / FailbackRegistry / 为什么弃用
```

**三句口诀**：

```
1. 答对了就追一层 —— 八股经不起三连问
2. 问「挂了怎么办」 —— 容灾题最见真章
3. 让他读代码   —— 读得懂才是真懂
```
