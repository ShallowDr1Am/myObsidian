## 🎯 要点

1. **7 个 MDC 字段**；核心关系是 `traceid` 全程不变、`spanid` 每跳都变、`cspanid` 是把**上一跳的 spanid** 传给下游。

## 一、地基：MDC 是什么

MDC（Mapped Diagnostic Context，映射诊断上下文）是 SLF4J（Java 的日志门面，即统一的日志接口层）提供的一个 **ThreadLocal 的 Map**——ThreadLocal 指"线程私有存储"，每个线程各存一份、互相看不到——用来存放"当前线程的上下文"。

生活类比：MDC 像每个办事窗口（线程）桌上的小托盘。把请求编号放进托盘，这个窗口之后开的每张单据（日志）都自动带上编号；窗口接待下一位客户前必须清空托盘（`MDC.clear()`），否则下一位会拿到上一位的编号。

```java
MDC.put("TRACE_ID", "abc123");     // 存进当前线程
log.info("处理订单");               // logback Pattern 里的 %X{TRACE_ID} 会取到 abc123
MDC.clear();                        // 线程复用时必须清，否则会串号
```

**为什么需要它**：日志里要带 traceId，但又不想每个方法都传参 `log.info("...traceId", traceId)`。MDC 让"上下文"对业务代码透明——业务只管 `log.info("xxx")`，Pattern 自动把 traceId 拼上。

**它的边界（重要）**：MDC 是 ThreadLocal，**只对当前线程有效**。跨线程、跨进程都不会自动传，必须手工搬——这正是本项目的三个"透传点"要解决的事。

## 二、字段体系（LogUtils 定义的 7 个 key）

来源：`S-Core/src/main/java/com/didi/utils/log/LogUtils.java`

| 常量 | MDC key | 含义 |
|---|---|---|
| `TRACE_ID` | `TRACE_ID` | **全链路 ID**，一次请求从头到尾不变 |
| `SPAN_ID` | `SPAN_ID` | 当前模块的 span id |
| `CSPAN_ID` | `CSPANID` | **传给下一个服务**的 span id（child span） |
| `DL_TAG` | `DL_TAG` | 日志类型标签，如 `_com_request_in` / `_com_dubbo_success` |
| `CUR_URL` | `CUR_URL` | 当前处理的 URL / 方法 |
| `CUR_SERVICE` | `CUR_SERVICE` | 当前服务名 |
| `PROCESS_ID` | `PROCESS_ID` | 进程号（`ManagementFactory` 取 PID） |

### traceId / spanid / cspanid 的关系（最容易绕晕的点）

```
HTTP 请求进来
  │  traceid=T, 生成 spanid=S_a（本模块）
  ▼
服务 A 处理
  │  要调服务 B 时：把 (traceid=T, cspanid=S_a) 放进 Dubbo attachment 传出去
  ▼  ────────────── RPC ──────────────
服务 B 收到
  │  从 attachment 取出：traceid=T, spanid=S_a ← 注意！B 的 spanid = A 传的 cspanid
  │  B 生成自己的 cspanid=S_b 继续往下传
  ▼
```

**一句话记忆**：**我打印的 spanid，等于上游传给我的 cspanid。** 因为 cspanid 的语义就是"用来当下一跳 spanid 的值"。

### DL_TAG：日志分类标签

`LogUtils` 提供了一组语义化方法，每个内部都先用 `MDC.put(DL_TAG, xxx)` 写入标签，再打日志，最后用 `MDC.remove(DL_TAG)` 移除标签：

| 方法 | DL_TAG | 用途 |
|---|---|---|
| `requestIn(marker)` | `_com_request_in` | 请求进入 |
| `requestOut(marker, procTime, errno)` | `_com_request_out` | 请求返回（带耗时、错误码） |
| `httpSuccess(...)` | `_com_http_success` | 出站 HTTP 成功 |
| `httpFail(...)` | `_com_http_failure` | 出站 HTTP 失败 |
| `dubboSuceess(...)` | `_com_dubbo_success` | Dubbo 调用成功（源码方法名就少个 c，是真实拼写，别当 typo 改） |
| `dubboFail(...)` | `_com_dubbo_failure` | Dubbo 调用失败 |
| `redisSuccess/Fail` | `_com_redis_*` | Redis 访问 |

> 好处：ES（Elasticsearch，日志检索库）里可以直接 `DL_TAG: _com_http_failure` 捞出所有失败的出站调用，不用正则扒日志正文。**这就是"结构化日志"的意义。**

## 三、三个透传入口（traceId 从哪来）

一个服务的 traceId 可能从三条路进来，各有一个"生成/读取"组件。

### 入口 1：HTTP（有上游请求）

**组件**：`S-starter/S-log-starter/.../filter/mvc/LogMvcTraceFilter.java`（Spring MVC HandlerInterceptor）

```java
@Override
public boolean preHandle(HttpServletRequest req, HttpServletResponse resp, Object o) {
    String traceId = req.getHeader(LogUtils.TRACE_ID_HEADER);      // "Didi-Header-Rid"
    String cspanId = req.getHeader(LogUtils.CSPAN_ID_HEADER);      // "Didi-Header-Cspanid"

    if (StringUtils.isBlank(traceId) && StringUtils.isEmpty(MDC.get(LogUtils.TRACE_ID))) {
        MDC.put(LogUtils.TRACE_ID, LogUtils.generateTraceId());    // 没有就生成
    } else {
        MDC.put(LogUtils.TRACE_ID, traceId);                       // 有就沿用（继续传递）
    }
    if (StringUtils.isNotBlank(cspanId)) {
        MDC.put(LogUtils.SPAN_ID, cspanId);                        // ★ B 的 spanid = 上游的 cspanid
    } else {
        MDC.put(LogUtils.SPAN_ID, LogUtils.generateTraceId());
    }
    MDC.put(LogUtils.CUR_SERVICE, curService);
    MDC.put(LogUtils.DL_TAG, LogUtils.REQUEST_IN);
    MDC.put(LogUtils.CUR_URL, req.getRequestURI());
    MDC.put(LogUtils.PROCESS_ID, LogUtils.getProcessID());
    return true;
}

@Override
public void postHandle(...) {
    resp.setHeader(LogUtils.TRACE_ID_HEADER, MDC.get(LogUtils.TRACE_ID));  // ★ 回写 header，前端/上游能看到
}

@Override
public void afterCompletion(...) {
    MDC.clear();   // ★ 线程归还池前必须清，否则下一个请求会串到上一个的 traceId
}
```

**注册方式**（同样靠自动装配）：`LogTraceWebMvcConfig` 实现 `WebMvcConfigurer`，在 `addInterceptors` 里把 filter 挂到 `/**`。

**要点**：
- header 名 `Didi-Header-Rid` / `Didi-Header-Cspanid` —— 上游（网关）带过来的
- `afterCompletion` 的 `MDC.clear()` 是**必须的**，Tomcat 线程池复用线程，不清会串号。✅ 规范：清理放 finally；跨线程搬运用统一 TaskDecorator（本项目 MdcTaskDecorator 已是此思路）

### 入口 2：Dubbo（跨服务调用）

**组件**：`S-starter/S-dubbo-starter/.../log/LogDubboTraceFilter.java`（Dubbo Filter）

```java
@Activate(group = {PROVIDER, CONSUMER})         // 提供方、消费方两侧都激活
public class LogDubboTraceFilter implements Filter {
    public Result invoke(Invoker<?> invoker, Invocation invocation) {
        RpcContext rpcContext = RpcContext.getContext();

        if (rpcContext.isConsumerSide()) {
            // 【消费端】把本地 MDC 的 traceId 塞进 attachment，随请求发给提供端
            rpcContext.setAttachment(LogUtils.TRACE_ID, MDC.get(LogUtils.TRACE_ID));
            String cspanId = MDC.get(LogUtils.CSPAN_ID);
            if (StringUtils.isBlank(cspanId)) {
                cspanId = UUID.randomUUID().toString().replace("-", "");
            }
            rpcContext.setAttachment(LogUtils.CSPAN_ID, cspanId);
        } else {
            // 【提供端】从 attachment 取出来，放进自己的 MDC
            MDC.put(LogUtils.TRACE_ID,  rpcContext.getAttachment(LogUtils.TRACE_ID));
            MDC.put(LogUtils.SPAN_ID,   rpcContext.getAttachment(LogUtils.CSPAN_ID));  // ★ spanid = 上游 cspanid
            MDC.put(LogUtils.CUR_URL,   rpcContext.getUrl().getAbsolutePath() + "." + rpcContext.getMethodName());
            MDC.put(LogUtils.DL_TAG,    LogUtils.REQUEST_IN);
            MDC.put(LogUtils.CUR_SERVICE, rpcContext.getUrl().getParameter("application"));
        }

        Result result = invoker.invoke(invocation);      // ★ 放行，真正执行

        // 清理，防止线程复用串号
        if (rpcContext.isProviderSide()) MDC.clear();
        if (rpcContext.isConsumerSide()) MDC.remove(LogUtils.CSPAN_ID);
        return result;
    }
}
```

**核心原理**：`RpcContext.setAttachment()` 是 Dubbo 的**隐式传参**机制——不走方法签名，挂在 RPC 请求的附件上，跨进程传递。**这就是 traceId 跨服务的载体。**

> 记忆锚点：**HTTP 用 header 传 traceId，Dubbo 用 attachment 传 traceId。**

### 入口 3：定时任务（没有上游）

**组件**：`S-starter/S-log-starter/.../filter/xxljob/XxlJobAspect.java`（Spring AOP）

```java
@Aspect
@Component
public class XxlJobAspect {
    @Around("execution(public * com.didi..task.*.execute(String)))")
    public Object handle(ProceedingJoinPoint point) throws Throwable {
        MDC.put(LogUtils.TRACE_ID, LogUtils.generateTraceId());     // ★ 无上游，自己生成新的
        MDC.put(LogUtils.SPAN_ID,  LogUtils.generateTraceId());
        MDC.put(LogUtils.CUR_SERVICE, "xxlJob:" + applicationName);
        MDC.put(LogUtils.CUR_URL, point.getSignature().getDeclaringType() + "." + point.getSignature().getName());
        Object proceed = point.proceed();
        MDC.clear();
        return proceed;
    }
}
```

**要点**：xxl-job 任务由调度器触发，没有 HTTP/Dubbo 上游，所以**自己生成一个全新 traceId**。切点是"`com.didi..task.*.execute(String)`"，即所有定时任务的 execute 方法。

### 三个入口对比

| 入口 | 组件 | traceId 从哪来 | 传输载体 |
|---|---|---|---|
| HTTP | `LogMvcTraceFilter` | 上游 header，没有则生成 | HTTP header |
| Dubbo | `LogDubboTraceFilter` | attachment，没有则生成 | RpcContext attachment |
| 定时任务 | `XxlJobAspect` | 总是新生成 | （无下游透传） |

## 四、跨线程：MDC 怎么办

线程池里跑的异步任务**拿不到父线程的 MDC**（ThreadLocal 不继承）。项目提供了工具：

```java
// LogUtils.getMdcTread(Runnable)
public static Thread getMdcTread(Runnable runnable) {
    Map<String, String> map = MDC.getCopyOfContextMap();   // 拷贝父线程的 MDC
    return new Thread(() -> {
        MDC.setContextMap(map);                            // 子线程还原
        runnable.run();
        MDC.clear();
    });
}
```

| 场景 | 问题 | 解法 |
|---|---|---|
| 线程池异步任务 | 子线程 MDC 空 | `getMdcTread()` 拷贝传递 |
| Spring `@Async` | 同上 | 需自定义 `TaskDecorator` 传递 MDC |
| 线程复用 | 上个请求的 traceId 残留 | `MDC.clear()`（`afterCompletion` / filter 的 finally） |

## 五、落盘：logback.xml

来源：`conf/log/logback.xml`（`docker_logback.xml` 是容器版，路径不同）

### Pattern —— 从 MDC 取值

```
[%level][%d{yyyy-MM-dd'T'HH:mm:ss.SSS+0800}][%file:%line] \
%X{DL_TAG:-_com_request_in}||pid=%X{PROCESS_ID:-1}||tid=%thread||\
traceid=%X{TRACE_ID:-init}||spanid=%X{SPAN_ID:-init}||uri=%X{CUR_URL:-init}||\
cur_service=%X{CUR_SERVICE:-init}||msg=%m%n
```

关键点：
- `%X{KEY:-default}` —— 从 MDC 取 KEY，没有则用 default（如 `traceid=%X{TRACE_ID:-init}`）
- `%m` = 日志正文，`%n` = 换行
- 输出长得像：`[INFO][2026-10-21T16:00:00.000+0800][AclController.java:42] _com_request_in||pid=1234||tid=http-nio-8074-exec-1||traceid=abc...||spanid=def...||uri=/api/v1/acl||cur_service=acl||msg=收到请求`

> **这条 Pattern 是整个日志治理的出口**：它把 MDC 里的 7 个字段"拍平"成一整行文本，既有可读性，又能被 logstash 正则解析。学习注意：字段拼成字符串后解析靠 grok，两侧格式必须严格对齐（现代替代见 §六）。

### Appender 体系（两个落盘 + 一个异步包装）

| Appender | 文件 | 内容 | 滚动 |
|---|---|---|---|
| `app-log` | `${app.name}.out.log` | 全部业务日志 | 2GB / 保留 7 天 |
| `sql-log` | `${app.name}.out.sql.log` | 仅 `DataChangeLogInterceptor(Trace)` | 2GB / 保留 15 天 |
| `async-log` | （包装 app-log） | 异步输出 | — |

**`async-log`（AsyncAppender）的取舍**：
```xml
<discardingThreshold>0</discardingThreshold>  <!-- 队列满也不丢 DEBUG/INFO/TRACE -->
<queueSize>1024</queueSize>                    <!-- 队列深度 -->
<neverBlock>true</neverBlock>                  <!-- 队列满时丢弃而不是阻塞业务线程 -->
```
- `neverBlock=true`：**宁丢日志不阻塞业务** —— 高并发下的保命设置。✅ 规范：关键审计日志用 neverBlock=false 或独立同步 appender，丢弃加指标告警
- `discardingThreshold=0`：默认队列 80% 满就丢低级别日志，设为 0 表示不主动丢
- 两者合起来：优先保证业务不卡，日志尽力而为

### Logger 分级

```xml
<logger name="com.didi.dao" level="DEBUG"/>                        <!-- DAO 层开 debug -->
<logger name="com.didi.sql.DataChangeLogInterceptor" level="TRACE"> <!-- 数据变更单独走 sql-log -->
    <appender-ref ref="sql-log"/>
</logger>
<root level="INFO">                                                <!-- 其余 INFO -->
    <appender-ref ref="async-log"/>
</root>
<logger name="com.xiaojukeji.carrera.common.disf.EndpointManagerSD" level="OFF"/>  <!-- 屏蔽噪音 -->
```

### ⚠️ 本地启动**看不到** traceId（实测，含修法）

这是"**你在本机永远看不到 MDC 效果**"的易误判点——不是你没找对地方，是它根本没被输出：

| 环境 | 实际用的配置 | Pattern 里有 `%X{}` 吗 | 看得到 traceId 吗 |
|---|---|---|---|
| **线上 / 容器** | `--logging.config=config/logback.xml`（即 `conf/log/logback.xml`） | 📌 7 个字段 | 📌 看得到 |
| **本地（Mac）** | 没传 `--logging.config`，于是用 **Spring Boot 默认日志** | 📌 没有 | 📌 **看不到** |

**两个原因叠在一起**：

1. `conf/log/logback.xml` 把落盘路径**写死成 Linux 路径**：
   ```xml
   <file>/home/data/logs/${app.name}/${app.name}.out.log</file>
   ```
   macOS 上 `/home` 不可写，所以这个 appender 建不出文件（和 `xxl.job.executor.logpath` 是同一个病）。

2. `svc.sh:86` 为本地预留了 `logback-local.xml` 钩子，但那份配置的 Pattern **没有 `%X{}`**：
   ```
   %d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level %logger{50} - %msg%n
   ```
   → 日志写出来了，但**不带 traceId**。

📌 **现场验证**：跑 `grep -c "traceid=" target/logs/start.out`，结果是 **0**。

**修法**：把本地 Pattern 换成带 MDC 的：

```xml
<pattern>%d{HH:mm:ss.SSS} [%thread] %-5level %logger{36} [%X{TRACE_ID:-init}][%X{SPAN_ID:-init}][%X{DL_TAG:-undef}] - %msg%n</pattern>
```

🔑 **换完之后会看到一个反直觉的现象**：启动阶段的日志**全是 `[init]`**。这不是没配好——`TRACE_ID` 只在**请求 / 任务入口**被 `LogUtils` 写入，启动时还没有请求。**它恰好证明了 MDC 的本质：一个"当前没有值就用默认值"的储物柜。**

📌 事实：`LogUtils.java` 有**两份完全相同的 208 行**（`S-Core/src/main/java/com/didi/utils/log/LogUtils.java` 与`S-GatewayProxy/src/main/java/com/didi/utils/LogUtils.java`）。学习注意：改一处要同步另一处，否则两服务 traceId 规则不一致；当年为何复制而非共享见 [[12-设计模式、最佳实践与设计缺陷]]。✅ 规范：跨服务工具沉到单一共享库（S-Core），消除同源副本。

## 六、采集：filebeat → logstash → Elasticsearch

来源：`conf/log/logstash.conf`、`logstash_online.conf`、`logstash_pretest.conf`（三环境各一份）

📌 **入口实测数字（2026-11-20）**：

- filebeat **7.4.0**，由 `conf/bin/prod/startup.sh` L71-74 从 10.86.0.109:8000 wget 并拉起。
- logstash online 的 input beats 监听 **10.74.213.57:8007**（非默认 5044）。
- output ES **10.88.128.149:30963**，online index 固定 **cn_smart_logs**（dev conf 用日志文件名作 index），action=create，带 Basic 鉴权（明文在 conf，见 12 §4.0）。
- filter 里 grok 与 json 分支并存。
- **Kibana 全仓 0 提及**——K 侧入口不在仓库（平台侧）。

```
logback 落盘  ──▶  filebeat (采集)  ──▶  logstash (解析)  ──▶  Elasticsearch
                     │                      │
                （启动脚本里 wget 并拉起）    grok 正则解析
```

### logstash 做了什么

**① grok 正则拆字段**（`logstash_online.conf`）：
```
"^\[%{LOGLEVEL:level}\]\[%{GREEDYDATA:time}\]\[%{GREEDYDATA:class}\] %{GREEDYDATA:tmp_message}"
```
把 `[INFO][时间][类名] 正文` 拆成 level / time / class / tmp_message。

**② ruby 脚本再拆 `||` 分段**（对应 Pattern 里那些 `||pid=..||traceid=..`）：
```ruby
key_array = Array.[]("pid","tid","traceid","spanid","uri")
@msg_array = event.get("tmp_message")
arrayOfEvents = @msg_array.split("||")     # 按 || 切
arrayOfEvents.each do |one_char|
    if one_char.include?"="
        one_split = one_char.split("=")
        if one_split.length>1 and key_array.include?(one_split[0])
            event.set(one_split[0], one_split[1])   # 把 traceid=xxx 变成 ES 字段 traceid: xxx
        end
    end
end
```

**③ 按文件名分索引**：
```
mutate { split => { "[log][file][path]" => "/" }
         add_field => { "[log][file][name]" => "%{[log][file][path][-1]}" } }
output { elasticsearch { hosts => [...] index => "%{[log][file][name]}" } }
```

### 这条管道的当年取舍与学习注意

📌 当年约定：日志先结构化（MDC 7 字段），再由 Pattern 拍平落盘，最后由 logstash 正则解析回结构化（当年 ELK 通用做法）。学习注意：字段改名、Pattern 改动都会让 grok 失配，两侧须同步改。

✅ 规范：直接输出 JSON 日志（logback `LogstashEncoder`/`JsonEncoder`），MDC 字段作为 JSON 字段，logstash/ES 直接消费——零正则、零解析成本；可作为 TODO 里的动手实验。

## 七、附加：数据变更审计日志

这套机制由 `S-starter/.../sql/DataChangeLogInterceptor.java` 实现，它是一个 MyBatis 插件：

```java
@Intercepts({
    @Signature(type = Executor.class, method = "update",
               args = {MappedStatement.class, Object.class})
})
public class DataChangeLogInterceptor implements Interceptor {
    private final String recordSql =
        "INSERT INTO cmdb_operate_log(user_name, operate_date, operate_type, " +
        "operate_table,operate_module_name, content) VALUES (?,?,?,?,?,?);";
    // 拦截 INSERT/UPDATE/DELETE，解析 SQL（Druid SQL parser），记下"谁在什么时候改了哪张表什么内容"
}
```

它靠 MyBatis 的插件机制（`@Intercepts` + `Executor.update`）拦下**写操作**，再用 Druid 的 SQL Parser 解析 SQL AST，提取出表名和变更内容。
- 异步线程池（`ThreadPoolExecutor`）**先发 Kafka topic `cmdb_operate_log`**；发送失败才降级 `INSERT INTO cmdb_operate_log`，再失败发邮件告警（详见 [[09-Dao 与 Entity 设计]] §六）
- 被 `logback.xml` 的 `TRACE` 级别单独导向 `sql-log` 文件

**这是"审计"类系统的标配**：数据变更留痕，可追溯谁改了什么。
