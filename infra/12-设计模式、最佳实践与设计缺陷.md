## 🎯 要点

1. **它的分布式设计确实好**：outbox、内容哈希幂等、租约+CAS、发布前可见性断言——
   这四招把分布式难题逐一降级成"单机数据库能解决"的问题，非常值得学。
2. **它最大的结构性取舍是"共享数据库"**：42 个服务互不依赖 jar，但**有 3 个域共用同一个 schema `dev46`**、
   一台 MySQL 实例承载 4 个库。**不依赖代码不等于可以独立演进**——这才是它真正的耦合点。
3. **它的模式用得"够用"（当年交付优先）**：策略/注册表/模板方法/责任链/适配器都在，
   同时存在 **3775 行的大类**、**两代 Mapper 并存**、**37 份同构配置**——各有年代原因，见 §四。

## 一、先建立判断坐标：什么算"好设计"

读一个有年代的系统，最容易犯的错是**用自己熟悉的风格当唯一标准**。用三个可操作的判据更稳：

| 判据 | 问法 | 为什么它比"风格"可靠 |
|---|---|---|
| **可独立演进** | 改 A 服务要不要动 B 服务的代码/数据？ | 微服务的唯一硬指标。**共享数据库会直接推翻它** |
| **可测试** | 不依赖外部中间件能验证核心逻辑吗？ | 决定你敢不敢改。靠"跑起来才能验"的系统没人敢重构 |
| **改动影响面** | 改一处，要同步改几处？ | 复制粘贴和隐式约定会放大它 |

🔑 **本文后面所有取舍分析都挂在这三条上**，而不是"这个写法我不喜欢"。

## 二、这套代码里真实用到的设计模式

### 2.1 ✅✅ 策略 + 注册表（用得最漂亮的一处）

主例在 `S-WrokOrder/S-dns-order`（✅ 工单主链），两处活代码：

```java
// 处 1：LinePercentScheduler（每分钟第 30 秒跑一次，@Scheduled）
@Autowired
private List<ITrafficLinePercentProcessor> processorList;   // Spring 把全部实现交进来

// 建注册表时显式给了 merge 函数：重复 key 保留前者，不在启动时爆炸
public Map<String, List<TrafficLinePercentVo>> get() {
    return processorList.stream().collect(Collectors.toMap(
        ITrafficLinePercentProcessor::name, ITrafficLinePercentProcessor::percent, (k1,k2) -> k1));
}
```

```java
// 处 2：TrafficScheduleRecordProcessorImpl L89，按类型查对应实现
Optional<IWorkorderModifyRecordProcessor> workorderProcessor =
    workorderModifyRecordProcessorList.stream()
        .filter(processor -> zoneType.equals(processor.type())).findFirst();
```

🔑 这个模式的精髓在于：`@Autowired List<T>` 让 Spring 自动收集**所有实现**，再按每个实现自报的 key 建索引（toMap 或 filter）。**加一种新策略只需要新增一个类，不改调用方**——这就是开闭原则（对扩展开放、对修改关闭）的落地。面试问"你在项目里怎么用策略模式"，这就是标准答案。多实现的体量见本章 §2.2（dns-order 多云，每接口 14~24 个实现）。

✅ 规范在这里有活的正确示范：dns-order 的 toMap **显式给了 merge 函数** (k1,k2)->k1，把重复 key 变成显式决策而不是启动爆炸。

> 📌 历史对照（⚠️ 转冷、已冻结）：`S-ServicesCmp/S-cvm-service` 的 CvmEvent 是同款模式、体量更大（16 个实现、每个负责一种事件），但它的 `Collectors.toMap(event -> event.event().name(), Function.identity())` **没有 merge 函数**——两个实现返回同一枚举名就在启动时抛 IllegalStateException。
> ✅ 规范：`toMap(k, v, (a,b)->a)` + 启动期重复 key 校验（fail-fast），dns-order 是活样板。

### 2.2 ✅ 适配器 / 多实现策略（多云厂商）

这处在 `S-WrokOrder/S-dns-order/src/main/java/com/didi/component/event/`，按云厂商或场景把同一件事拆成多个实现：

| 接口 | 实现数 | 面向 |
|---|---|---|
| `IOfficeBaseMode` | **24** | Office 办公网 |
| `IAXCustomerOfficeMode` | 21 | 客户办公网 |
| `ICustomerOfficeBaseMode` | 19 | 客户基础 |
| `IAliDnsBaseMode` | **18** | 阿里云 DNS |
| `IAwsBaseMode` | **16** | AWS |
| `IInternetBaseMode` | 14 | 公网 |
| `IIdcBaseMode` | 14 | 自建 IDC |

🔑 改 DNS 记录、开通网络这些事，在不同云厂商下走不同实现，但**调用方只看统一接口**——这是"用多态代替 if-else 判断云厂商"的教科书场景。 📌 反过来说：7 个接口、每个 14~24 个实现，加起来超过 **100 个类**，改一处规则要横扫一大批。**下次看到"多云支持"需求，先想清楚会不会变成这个体量。**

### 2.3 模板方法（抽象类，107 个）

模板方法在框架层和业务层都有。框架层的例子是 MyBatis-Plus 的扩展点：`ExtLogicSqlInjector extends DefaultSqlInjector`（重写 `getMethodList`，调 `super` 后再追加）；`MysqlInsertAllBatch extends AbstractMethod`（实现 `injectMappedStatement`，父类负责把它注册进 MappedStatement）。业务层则有全项目 **107 个抽象类**，命名多为 `AbstractXxx` / `XxxHandle`。

🔑 模板方法和策略怎么分？**"骨架在父类、步骤由子类填"的是模板方法**，特征是 `super.xxx()` 之后插入逻辑；**"整体算法可替换"的是策略**，特征是接口 + 多实现。上面的 `DefaultSqlInjector` 是典型的模板方法。

### 2.4 责任链（MyBatis 插件链）

全项目只有 **2 个** `@Intercepts` 拦截器（实测）：

| 拦截器 | 作用 |
|---|---|
| `S-starter/S-datasource/.../sql/DataChangeLogInterceptor` | 抓写操作做变更审计（374 行，本层最大类） |
| `S-starter/S-pii-starter/.../interceptor/PiiInterceptor` | PII 字段**国密 SM4 加解密**（`Sm4Util.encryptWithCbc` / `decryptWithCbc`） |

🔑 MyBatis 的 `Interceptor` 链天然是责任链：多个插件按注册顺序包裹`Executor` / `StatementHandler`。这两个拦截器把"审计"和"加密"做成了横切能力，新服务只要有依赖就自动获得——**能在拦截器层解决的问题，就不要散到业务里**。

📌 `PiiInterceptor` 的签名叫得很准：拦 `Executor.update` 和 `Executor.query`，在**写库前加密、读库后解密**，字段级国密 SM4（`Sm4Util.encryptWithCbc`）。 🔑 **这是"敏感数据加密"的正确位置**——放进业务代码必然有人漏，放进持久层是唯一可靠的收口。代价也要知道：加密字段不能做模糊查询和范围比较，索引基本失效，设计表时就要想清楚。

### 2.5 路由 / 动态策略（本仓库最有特色的一处）

这处在 [[09-Dao 与 Entity 设计]] §二，那个 13 行的`DynamicDataSource extends AbstractRoutingDataSource`。

🔑 它其实是"策略模式 + 注册表"在框架里的实现：`targetDataSources` 是注册表，`determineCurrentLookupKey()` 是运行时选策略的钩子。**记住这个模式名，面试常问。**

### 2.6 代理（AOP 切面，面向切面编程）

看 5 个 `XxxDataBaseAspect`（`@Aspect @Order(-9)`），外加事务和 Dubbo 的代理。

🔑 `@Order(-9)` 为什么重要：切库必须**早于**事务和 SQL 执行。顺序错了就会出现"事务已经绑定了连接，切库才发生"——**切库失效但不报错**。这是 AOP 排序的机制易误判点。

### 2.7 装饰器

logback 的 `async-log` 就是：`AsyncAppender` **包装** `app-log`，见 [[08-日志治理]]。

🔑 装饰器的标志是"**持有同一个接口的另一个实现**"。`AsyncAppender` 不产生新日志格式，只是给已有 Appender 加上"异步"这一层能力。

### 2.8 分布式模式（这部分比 GoF 经典设计模式更值钱，GoF 即 Gang of Four）

| 模式 | 出处 | 解决什么 |
|---|---|---|
| **Transactional Outbox** | `rack_metric_outbox`（[[10-指标上报链路]]） | 让"发消息"和"写数据库"最终一致 |
| **幂等键 = 业务内容哈希** | 接收端 `receive_record`，SHA256 | 重发天然去重，不要 UUID |
| **租约 + CAS** | `rack_metric_job` 状态机 | 多实例抢任务，不用分布式锁 |
| **发布前可见性断言** | 回读 ES 核对摘要 | "发了"不等于"能查到" |

🔑 这四者和语言、框架都无关，换个技术栈照样能用。

## 三、✅✅ 值得抄的最佳实践（13 条）

这 13 条是这套代码里做对了的地方，可以直接抄。

### 3.1 把分布式事务降级成单机事务

不引入 Seata/2PC，而是把"发 Kafka"改成"**同事务写 outbox 表 + 后台轮询投递**"。好处是唯一需要的原子性落在**一个库里的一张表**上，这是真正能做到的；把"分布式"换成了"延迟"，用秒级延迟换掉了一整套分布式协调。代价是消息延迟，以及需要清理已投递记录。**这笔交易在这个业务下是赚的。**

### 3.2 幂等键用"业务内容哈希"，不用 UUID

用 `SHA256(业务身份字段)` 作为唯一键。UUID 需要调用方保证不重发；内容哈希则**把幂等性变成了数据的属性**——同一个内容算两次必然相等，数据库的 UNIQUE 约束自动兜底。 ⚠️ 前提是参与哈希的字段必须能唯一代表"同一次业务"，而且不能包含时间戳之类的噪音。

### 3.3 抢任务用"租约 + CAS"，不用分布式锁

`UPDATE ... SET owner=?, lease_token=? WHERE status=? AND lease_expire < now()`，然后判断 `affected rows == 1` 才算抢到——这就是 CAS（Compare-And-Swap，比较并交换）。这样做没有引入 Redis 或 ZK（ZooKeeper）锁，**没有锁超时释放的边界问题**，而且"进程崩了"由租约自动兜底。 🔑 判据是：能用"一条带条件的 UPDATE 的返回行数"表达互斥时，就不要上分布式锁。

### 3.4 动态数据源用**栈**而不是单值

用 `ThreadLocal<Deque<String>>`，`addFirst` 进、`removeFirst` 出，好处是支持**嵌套切库**。若用单值，内层切完会把外层覆盖，退出之后就回不去了。 ⚠️ 代价是必须保证进出配对，而且异步线程不继承上下文。

### 3.5 自定义 SQL 注入器做"真"批量插入

`MysqlInsertAllBatch` 生成 `insert into t (a,b) values (..),(..),(..)` 这样一条 SQL，比"循环单条加 jdbc batch"少一次 SQL 解析，也少反复往返。

### 3.6 审计日志"Kafka 主 + MySQL 兜底 + 邮件告警"

源码注释：*「操作日志直接写入公司 kafka，异常后写入 mysql，并发送邮件」*。好处是把"高吞吐主路径"和"绝不丢的兜底"分开了——**主路径追求性能，兜底追求不丢**。 ⚠️ 但这是多级降级，要保证兜底路径本身不会再失败。

### 3.7 starter 拆两层 + `@ConditionalOnBean` 显式 opt-in

`S-datasource` 是骨架（无 `spring.factories`），按域的 5 个 starter 才注册`XxxDruidMyBatisAutoConfig`，而且带 `@ConditionalOnBean(DruidDataSourceProperties.class)`。好处是**没配数据源的服务不会误加载数据源自动配置**，避免"引入依赖就必须配库"。

### 3.8 配置热更新（`@RefreshScope`）

`DataSourceProperties` 和 `DruidDataSourceProperties` 都带 `@RefreshScope`，于是改连接池参数**不需要重启**。对"改一个阈值就要发版"的团队，这是刚需。

### 3.9 日期/时区用 TypeHandler 收口

`DateTypeHandler` / `DateTimeTypeHandler` / `CalendarTypeHandler` 集中处理， JDBC URL 统一 `serverTimezone=Asia/Shanghai`。时间问题一旦散落到业务代码里就再也收不回来，**收口在持久层是正解**。

### 3.10 测试用 H2 + `MODE=MySQL`，不依赖中间件

`S-network-device-service` 用 H2 加 `data-h2.sql`、`@MybatisTest` 分层，好处是**能在 CI 里秒级验证 SQL**，不用起 MySQL。

### 3.11 零空 `catch`（工程纪律）

📌 实测 `catch (...) {}` **0 处**，`catch` 里只有注释的也是 **0 处**。这一点值得肯定——很多遗留项目的头号问题就是吞异常，这个项目没有。

### 3.12 每个服务显式声明自己的数据源

37 个服务各有一份 `DataSourceConfig`，`@Primary` 只给动态路由。好处是**"这个服务用哪几个库"一眼可见**，比隐式自动装配更好审查（代价见 §4.6）。

### 3.13 线程池上下文透传，用 `TaskDecorator`

实现在 `S-ServiceConfig/src/main/java/com/didi/manage/MdcTaskDecorator.java`（由 `ThreadPoolTaskConfig` 的 `executor.setTaskDecorator(new MdcTaskDecorator())` 接上）：

```java
public Runnable decorate(Runnable runnable) {
    Map<String, String> map = MDC.getCopyOfContextMap();   // ① 提交时抓一份快照
    return () -> {
        try {
            if (Objects.nonNull(map)) MDC.setContextMap(map);  // ② 在池线程里装回去
            runnable.run();
        } catch (Exception e) {
            log.error(getStackTrace(e));
        } finally {
            MDC.clear();                                        // ③ 一定清理
        }
    };
}
```

🔑 这三步是上下文透传的**标准答案**：**抓快照、装回去、finally 清理**。少第三步就是内存泄漏加数据串号。而且 `TaskDecorator` 是 Spring 专门留的钩子，不用自己包 `Runnable`。

⚠️ 但它只解决了 MDC：`DataBaseContextHolder`（切库栈）和 `MysqlChangeContext`（审计主体）**不在 MDC 里**，所以**没有被透传**——这正是 §4.9 那条取舍的机制落点。

## 四、设计取舍与年代背景（14 条）

下面 14 条每条四段：**现象（实测）、当年为什么、学习注意、✅ 新项目规范**。不打分、不指责，只给事实与选择。

### 4.0 凭据随仓库分发：明文凭据在 git 里

📌 现象（实测 `git ls-files` + 逐文件扫描）：当年为什么——bootstrap 在阶段①就要读（鸡生蛋），配置随仓库分发是当年默认，内网隔离（L1）被视为足够兜底。

| 文件 | 凭据字段 | 说明 |
|---|---|---|
| `S-ServiceConfig/bootstrap-prod.properties` | `nacos.password` | 生产 Nacos 口令；该文件 **26 次提交**，早已在历史里 |
| `S-ServiceConfig/bootstrap-prodhnd.properties` | `nacos.password` | 与 prod **完全相同**（同一套口令复用） |
| `S-ServiceConfig/bootstrap-{dev,test}.properties` | `spring.cloud.nacos.discovery.password`、`dubbo.registry.password` | 5 字符 |
| `S-WrokOrder/S-dns-order/bootstrap-clouddnsprod.properties` | **7 个** `spring.datasource.*.password` + Kafka / Elasticsearch 口令 + `workflow.dns.record.internet.api.secret` | 生产库口令 |
| `S-WrokOrder/S-dns-order/bootstrap-clouddnsdev.properties` | 同上（dev 侧，共 10 处） | |

📌 合计 **24 处明文凭据**，全部落在 `bootstrap-*.properties`——而这类文件**必须**进仓库，因为它在启动最早期（阶段①）就要被读到（见 [[05-服务是怎么启动的]]）。

很多人会觉得"反正是内网地址，写明文无所谓"。这里要把两件事分开。`nacos.server-addr=10.78.128.115:8848` 是**地址**，相当于门牌号——明文无妨，知道它不等于能进门（还要在内网、还要有账号）。而且它**结构上必须**明文写在 `bootstrap.*`：鸡生蛋，它没法从 Nacos 里拿到自己。

**密码是钥匙，性质完全不同。** 它一旦进 git 就等于**永久泄露**：就算明天把文件删了，历史里仍然有，任何拿到 clone 的人都能翻出来。实测这些也不是占位符——长度 5~20 都是真实值，其中 `nacos.password` 在 prod 与 prodhnd 两处**完全一致**，口令复用，一处泄露等于两处。

学习注意：git 历史永久留存，删文件不等于撤回，需轮换全部已入库口令。✅ 规范：占位符 `${DB_PWD}` + 环境变量/启动参数注入；长期接 KMS/Vault（本项目已有 `Sm4Util` + `PiiInterceptor` 可复用）。

#### 业内的分层做法：内网只是第一层，不是解法

| 层 | 做法 | 代表 | 防住什么 |
|---|---|---|---|
| **L1 网络隔离** | 内网 / VPC / 安全组 / 零信任 | 现在的做法 | **外部人**连不上 |
| **L2 认证 + 授权** | 登录、RBAC、最小权限 | Nacos `auth.enabled`、LDAP | 内部人**越权**读 |
| **L3 加密存储** | 应用层加密后入库 | jasypt、AES-GCM | **拖库**后看不懂 |
| **L4 密钥管理** | KMS / Vault：主密钥永不落地 | AWS KMS、阿里云 KMS、Vault | 密钥**本身**被偷 |
| **L5 免长期密钥** | 工作负载身份、动态短期凭据 | K8s Workload Identity、SPIFFE、OIDC 联邦、DB IAM 认证 | **根本没有钥匙可偷** |

⚠️ 内网（L1）只挡住"外面的人"，剩下的它一个都挡不住：内部人员、一台机器沦陷之后的横向移动、日志 / 仓库 / 备份泄露。业内叫纵深防御（defense in depth）——**每一层都假定上一层已经被突破**。

真正起作用的是三个机制。**信封加密**让主密钥（CMK，客户主密钥）**永不离开 KMS（密钥管理服务）**，只用它加密"数据密钥"，数据密钥再加密数据；好处是泄露一个数据密钥只影响一份数据，换主密钥也不必重加密全库。**动态短期凭据**让 Vault 按需现场生成数据库账号，TTL（有效期）1 小时、到期自动删除，没有长期口令可偷——这是它和"把口令存好"的本质区别。**密钥生命周期**是签发、分发、轮换、吊销、审计这五步，而配置中心只做了"分发"，其余四步一步都没做，这就是它和密钥管理系统的分界线。

#### 本项目已有的加密样本与它的边界

`S-ServicesCmdb/S-ops-tool-service` 的 `AesGcmLlmCredentialCipher`：

| 做对的 | 细节 |
|---|---|
| 算法 | `AES/GCM/NoPadding`（认证加密，防篡改） |
| nonce | 每条记录用 `SecureRandom` **独立随机**生成，绝不复用 |
| 密钥版本 | `encryptionKeyVersion` 字段 → **具备轮换能力** |
| 展示脱敏 | 只存 `maskedSuffix`（尾部几位），前端永远拿不到原文 |

📌 边界：主密钥 `dd.llm.credential-secret` 明文在 `application.properties` 且已进 git——密钥与密文同处，加密只防"仅拿到库备份"一种场景。

学习注意：拿到仓库即可解开全部 LLM 凭据。✅ 规范：主密钥走环境变量（`DD_LLM_CREDENTIAL_SECRET`），利用已有 `keyVersion` 字段做轮换。

### 4.1 共享数据库：耦合点在数据不在代码

实测 Nacos 里的 `datasource.properties`：

```
8 个逻辑数据源 → 落在一台 MySQL 实例的几个 schema 上
  10.74.0.30:8088  承载：dev46 / sys_base3 / sys_it / metric-monitor
  10.74.0.29:8088  承载：base3
  127.0.0.1:13306  本地化后的 stable（原为 10.74.0.30 的 dev46）

⚠️ dev46 这一个 schema 被 3 个逻辑数据源指向（intra / stable / …）
```

表面上看，服务之间**确实**不互相依赖 jar（实测 38 个服务模块只有 1 个被别的 pom 引用），很容易得出"这是松耦合微服务"的结论。但**它们读写同一个 schema**。于是改一张表的字段，就要同时改多个服务，**无法独立发布**；一个服务写脏数据，其他服务直接受害，**没有接口边界**；想做分库分表或迁移，也会牵扯所有服务。 🔑 **判据一（可独立演进）直接不成立**——这是"分布式单体"的典型特征。当年为什么：42 服务由单体按域拆出，拆代码先于拆数据（拆库需组织级推动）。✅ 规范：按服务划 schema，跨服务只走 API/Dubbo。

学习注意：改一张表字段要同步多服务、无法独立发布；别把"不依赖 jar"当松耦合证据。存量系统先加读写边界清单（哪张表归谁写、禁跨域写），逐步收口。

### 4.2 一个服务承载 14 个业务域

`S-WrokOrder/S-dns-order` 的一级包（实测）：

| 包 | 有无 DDD 四层 | java 文件 |
|---|---|---|
| `workorder` | 4/4 | 310 |
| `subdomain` | 4/4 | 249 |
| `traffic` | 4/4 | 115 |
| `gtm` | 4/4 | 106 |
| `bpm` | 4/4 | 99 |
| `starter` | 1/4 | 68 |
| `outside` | 3/4 | 65 |
| `component` | 0/4 | 51 |
| `domain` | 4/4 | 44 |
| `local` / `cloud` / `switching` / `combo` / `diagnostic` | 混杂 | 88 |

📌 **合计 1196 个 java 文件在一个服务里**，14 个一级包，7 套完整 DDD（领域驱动设计）四层。

📌 现象：所有上下文共享 Spring 容器/事务/jar——分层成立、上下文边界未拆。当年为什么：工单域按业务包渐进演进，拆服务成本高于包内分层。学习注意：DDD 四层分层不等于限界上下文（按业务边界划出的独立单元）低耦合。✅ 规范：一个限界上下文一个部署单元，或至少独立事务边界。

### 4.3 大类：3775 行的 ServiceImpl

排除生成的 `*Example` 之后，最大的几个类：

| 类 | 行数 |
|---|---|
| `S-server-ops-service/.../life/packagepublish/service/impl/PackagePublishServiceImpl` | **3775** |
| `S-dgw-service/.../service/impl/LoadBalanceApplyServiceImpl` | **2984** |
| `S-idc-ops-service/.../cabinetInventory/.../ProcessCabinetInventoryServiceImpl` | **2708** |
| `S-device-assets-service/.../server/.../ServerDevicesServiceImpl` | 2441 |
| `S-server-ops-service/.../life/arrival/.../ServerArrivalProcessServiceImpl` | 2407 |
| `S-idc-meta-data-service/.../base/.../IdcRackPositionServiceImpl` | 2401 |

🔑 这里用的是**判据三（改动影响面）**：3000 行以上的类，任何改动都要通读、无法安全测试、git blame 全是同一个人的多年提交。**这通常意味着里面混了 5~10 个职责**（校验、编排、落库、通知、重试）。当年为什么：多年单人累积提交，职责随需求自然堆积。

学习注意：改动需通读、难安全测试。✅ 规范：按方法聚类抽协作者（"发通知""算位置""写流水"各抽一个），每抽一个补测试，不重写。

> 📌 参照 [[10-指标上报链路]] 的 `MetricPipelineService`（实测 **1084 行**）——也是超大类，
> 但它**把一个状态机的所有迁移收在一个类里**，这种"大"是**内聚**，和上面那种"什么都干"不同。
> **看大小时要区分"内聚的大"和"杂糅的大"。**

### 4.4 两代 Mapper 风格并存

165 个 `*Mapper.java` 里，**51 个**是 MyBatis Generator 风格（`selectByExample`），**58 个**是 MyBatis-Plus（`extends BaseMapper`），另有 **117 个 `*Example.java`**。详见 [[09-Dao 与 Entity 设计]] §五。

当年为什么：MBG 是老生成器、MyBatis-Plus 后来引入；存量不重写、增量用新框架（当年普遍做法）。学习注意：新人要认两套写法；`Example` 的 `${}` 见 §4.8。✅ 规范：单一 ORM 风格 + 统一生成器；存量按域渐进迁移。

### 4.5 三代包结构并行

`dns-order` 里 `workorder/`（老）、`subdomain/`（中）、`domain/`（新）**三套树并存**，每套都有 `application/domain/infrastructure`。

当年为什么：渐进式重构分期推进、未做收尾（业务不停摆优先）。学习注意：同一逻辑可能三处影子实现，改需求先全树搜。✅ 规范：重构设收尾里程碑——旧树删除作为验收项。

### 4.6 37 份同构的 `DataSourceConfig`

`find -name DataSourceConfig.java` 找到 **37 个**（42 个服务里），逻辑同构，差异只在"声明接哪几个数据源"。于是改动路由骨架（比如加一个库）要改 37 处。

当年为什么：显式声明优先（§3.12 取舍的另一面）——每服务一眼可见用哪几个库。学习注意：改路由骨架要同步 37 处。✅ 规范：骨架 `@Configuration` + `@ConfigurationProperties`，服务侧只给字符串列表（声明式代替样板）。

### 4.7 两种装配路径并存（`spring.factories` 有无不一）

`S-datasource`（骨架）**没有** `META-INF/spring.factories`，5 个按域 starter **都有**。而 `@MapperScan` 的包名在三处又各不相同（`com.didi.dao` / `com.didi.**.dao` / `com.didi.*.infrastructure.mapper`）。

当年为什么：骨架层刻意不自动装配（§3.7 opt-in 取舍），域 starter 才注册；`@MapperScan` 包名随三代包结构演进。学习注意：⚠️ "Mapper 为什么没扫到"先确认走哪条装配路径 + 哪个包名约定。✅ 规范：统一装配入口 AutoConfiguration.imports + 文档化 `@MapperScan` 权威清单。

### 4.8 `${}` 动态 SQL：116 个 XML，848 次 `${criterion.condition}`

S-Dao 下有 **116 个** XML 含 `${}`，出现最多的是 `${criterion.condition}`（**848** 次），其次是 `${limit}`（155）、`${orderByClause}`（153）、`${offset}`（78）。

`#{}` 是预编译参数（安全），**`${}` 是字符串直接拼接（危险）**。 MBG 生成的 `Example` 正是靠 `${criterion.condition}` 拼 WHERE 子句—— 值本身由 MBG 转义，但**一旦有人把用户输入塞进 `orderByClause` 或 `limit`，就是 SQL 注入**。

当年为什么：MBG Example 靠 `${criterion.condition}` 拼 WHERE（生成器约定），值由 MBG 转义。学习注意：⚠️ 用户输入进 `orderByClause`/`limit` 即注入面。✅ 规范：入口白名单（列名枚举 + 数值范围），永不接受原始用户字符串；条件查询用 LambdaQueryWrapper。

### 4.9 两个自研 ThreadLocal 未纳入透传

📌 精确核对后的结论是：**MDC 已经做了透传，两个自研 ThreadLocal 没有**。

| 上下文 | 存在哪 | 是否透传到线程池 | 依据 |
|---|---|---|---|
| MDC（traceId 等 7 个字段） | slf4j 的 MDC | **📌 有**（`MdcTaskDecorator`） | `ThreadPoolTaskConfig:37` |
| `DataBaseContextHolder`（切库栈） | 自研 ThreadLocal | **📌 没有** | 无处 copy/set |
| `MysqlChangeContext`（审计主体） | 自研 ThreadLocal | **📌 没有** | 无处 copy/set |

🔑 准确说法：**MDC 管到了、业务上下文未覆盖**——部分覆盖比全不覆盖更易误判（traceId 对得上但 operator 空/偶发默认库）。当年为什么：透传钩子（TaskDecorator）只接了 MDC 这一路；自研上下文走独立 ThreadLocal，未走同一钩子。✅ 规范：统一 TaskDecorator 纳管所有上下文，或把库名/操作人放进 MDC 继承透传。

学习注意：现象与排查见 [[09-Dao 与 Entity 设计]] §七 机制警戒清单。

### 4.10 默认库静默兜底（fail-open）

`ds.setDefaultTargetDataSource(stableDataSource)` 意味着方法上**没有任何注解**时不报错，而是**静默走 stable**。

🔑 机制：fail-open 的错误会潜伏（数据看起来"对"），fail-fast 立刻暴露。当年为什么：默认 stable 让无注解方法可跑（降低接入门槛）。学习注意：以为读 A 实际读 B 时不报错。✅ 规范：默认库显式声明，或启动期校验 Mapper 包归属。

### 4.13 测试分布：单测厚、集成薄

📌 732 个测试文件、3451 个 `@Test`，**总量不低**，但分布很偏：`S-network-device-service` **一个模块就占了 605 个 `@Test`（约 17%）**，而全项目只有 **49 个 `@SpringBootTest`**。

🔑 判据二（可测试）：局部可测成立、集成验证薄——"改完不敢发"源于安全网缺口而非测试数量。当年为什么：`@SpringBootTest` 需起容器与中间件，成本高；单测无此门槛。学习注意：看测试数先看分布与类型。✅ 规范：CI 备 H2/testcontainers（§3.10 已有样本），集成测试进流水线。

## 五、如果重来一次：按性价比排序的改造建议

**先做小成本项**——结构性项成本最高。按"收益/成本"排序：

| 优先级 | 动作 | 成本 | 收益 |
|---|---|---|---|
| 1 | **把 `${orderByClause}`/`${limit}` 入口加白名单** | 小 | 直接关掉注入面 |
| 2 | **同名 `CvmEvent` 枚举去重 + 启动期校验**（`toMap` 加合并函数） | 小 | 防住一类启动崩溃 |
| 3 | **文档化 `@MapperScan` 的权威清单**（哪个服务扫哪些包） | 小 | 定位最常见的启动问题 |
| 4 | **默认数据源改成显式声明**，或加启动期校验 | 中 | 把 fail-open 变 fail-fast |
| 5 | **`DataSourceConfig` 改声明式**（37 份 → 1 份骨架 + 声明） | 中 | 改一处即可加库 |
| 6 | **给两个 ThreadLocal 加统一的上下文透传（如 `TaskDecorator`）** | 中 | 补齐异步上下文透传 |
| 7 | **大 Service 按方法聚类拆协作者**（不重写，只抽） | 大 | 真正提升可维护性 |
| 8 | **按服务划 schema，禁止跨域写表** | 很大 | 治本，但需要组织级推动 |

🔑 **判断改造是否值得的唯一标准：它能不能让你"更敢改代码"。** 只重构不写测试 = 白做。

## 六、评审/面试时怎么讲这些取舍

讲法的关键是**指出代价与取舍、并给出自己新项目的选择**，而不是评价好坏：

| 说法 | 效果 |
|---|---|
| ❌ "用了 MyBatis Generator，很老土" | 显得只认工具 |
| ✅ "MBG 的 `Example` 让 `${criterion.condition}` 出现 848 次，把 SQL 结构变成了字符串拼接，**注入面取决于有没有人把用户输入传进 orderByClause**——这是我要加的校验点" | 显得能定位风险 |
| ❌ "3000 行的类，应该重构" | 空话 |
| ✅ "`PackagePublishServiceImpl` 3775 行，我数了下里面至少有 5 类职责（校验/编排/落库/通知/重试）；**拆的时候要先把测试补上，否则没法验证行为不变**" | 显得知道怎么落地 |
| ❌ "共享数据库，这不是微服务" | 结论对，但没信息量 |
| ✅ "42 个服务不依赖彼此 jar，但 `dev46` 这个 schema 被 3 个逻辑数据源共用、一台实例承载 4 个库——**它是分布式单体，字段变更无法独立发布**" | 有证据有后果 |
