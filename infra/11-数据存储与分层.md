## 🎯 要点

1. **七类存储，MySQL 是中心**；MySQL 靠「分域 / 分表 / 读写分离 / 冷热快照」四招扛住体量。
2. **"不存明细"是这套设计的核心取舍**——明细进了 VictoriaMetrics / StarRocks，所以**不需要 Hive**。
3. **配置项存在不等于有人在用**（`S-hbase-starter` 就是活例子），判断要三个信号：依赖 + 配置 + 调用方。

## 一、先纠正一个直觉

"项目看起来就是一堆 MySQL"是错觉。真实情况是**七类存储各管一段**，MySQL 再靠分域、分表、读写分离、冷热快照四招扛住体量。

```
                      ┌─────────────────────────────────────────┐
   写路径             │  MySQL（OLTP + 报表快照）               │
                      │  多库分域 / 分表 / 读写分离 / 日快照     │
                      └─────────────────────────────────────────┘
                                    ▲                    ▲
                                    │ 物化聚合            │ 状态与清单
        ┌───────────────────────────┘                    │
        │                                                │
┌───────┴────────┐   ┌──────────────────┐   ┌───────────┴──────────┐
│ 时序数据库      │   │ 检索/聚合存储     │   │ 消息层                │
│ InfluxDB(旧)    │   │ Elasticsearch    │   │ Kafka / DDMQ         │
│ VictoriaMetrics │   │ 指标文档、日志     │   │ 异步解耦、投递重试     │
│ (现行)          │   │                  │   │                      │
└────────────────┘   └──────────────────┘   └──────────┬───────────┘
                                                       │
                                                       ▼（仓库外）
                                              StarRocks（分析型数仓）
```

## 二、七类存储的职责边界

| 层 | 技术 | 存什么 | 查询特征 | 延迟 | 项目落点 |
|---|---|---|---|---|---|
| **OLTP（在线事务处理）** | MySQL | 业务实体、工单、状态、配置 | 按主键/索引取几行，带事务 | ms | 全项目主体 |
| **时序** | VictoriaMetrics / InfluxDB | 使用率原始打点 | 时间范围 + PromQL/InfluxQL（两种时序查询语言）聚合 | 秒级 | `userate-*` |
| **检索** | Elasticsearch | 指标快照文档、操作日志、报废记录 | documentId 精确查、条件过滤 | 近实时 | `report` / `server-ops` / `device-assets` |
| **消息** | Kafka / DDMQ | 事件流、待投递数据 | 不查询，只消费 | — | 54 / 50 个文件 |
| **分析** | StarRocks | 预聚合的利用率宽表 | 大范围多维聚合 | 秒~十秒 | `userate` 下游（仓库外加载） |
| **缓存** | Redis（Codis） | 热点数据、分布式状态 | 点查 | μs | 26 处依赖 |
| **向量/AI** | PostgreSQL | AI 相关数据（库名 `ai_cmdb`） | 语义检索 / 结构化查询 | ms | `ops-tool`（nl2sql） |

**选型判据不是"数据量大不大"，而是"你要找几行、扫全量、还是近实时查结果"。**

> **数据来源**：以上落点与地址来自 Nacos 配置导出（`TEST_GROUP/datasource.properties`），第 3.1 节的分域表同源。

## 三、MySQL 撑住体量的四个手段

### 3.1 分库分域：一个领域一个库

`S-datasource-*-starter` 的存在就是为了这个——每个 starter 绑定一套连接配置，服务按需引入。

| Starter | 配置前缀 | 典型库 | 使用者 |
|---|---|---|---|
| `S-datasource-base-starter` | `spring.datasource.base` | `base3` / `sys_base3` | `idc-meta-data` |
| `S-datasource-intra-starter` | `spring.datasource.intra` | `dev46` | `userate` |
| `S-datasource-it-starter` | `spring.datasource.it` | `sys_it` | IT 资产 |
| `S-datasource-stable-starter` | `spring.datasource.stable` | `stable`（**独立实例**） | `report` / `server-ops` |
| `S-datasource-stable-r-starter` | `spring.datasource.stable.read` | `stable` 只读副本（独立账号） | `ops-tool` |

> **`stable` 是独立实例**（与 `dev46` 不在同一台机器），不是同库的另一套配置。
> 另有 `spring.datasource.metric`（`metric-monitor` 库）与 `spring.datasource.vector`（PostgreSQL `ai_cmdb`），
> 分别服务监控指标与 AI 场景。

> 一个服务可以同时引入多个（如 `idc-meta-data` 同时用 base + stable），由 `@MapperScan` 包名区分归属。
>
> **注**：`S-network-device-service`（Kotlin）已剥离 intra 数据源，只保留 base 系。数据源收敛是持续进行的，读代码时以该服务当前的 `pom.xml` 为准。

### 3.2 读写分离：分析查询不碰主库

`S-datasource-stable-r-starter` 提供独立的 `stableReadDataSource` + `stableReadJdbcTemplate`，用单独只读账号。

实际使用在 `ops-tool-service` 的 nl2sql：

```java
@Qualifier("stableReadDataSource")
private DataSource stableReadDataSource;
// SqlExecutor.java:40
```

> **模式**：让 AI/报表这类"不知道会扫多少行"的查询走只读副本，主库只服务事务。这是最省事的一道保护。

### 3.3 分表：ShardingSphere

`S-datasource-base-starter` 内置了完整分表能力：

```
shardingsphere/
├── ShardingTableConfig   分表配置（表名、分片列、表数）
├── TableAlg1~5           分片算法
├── MonthShardingUtil     按月分片
├── DataSourceAlg         数据源路由
└── HashUtil
```

配置示例（DNS 成本库，`bootstrap-clouddnsdev.properties:38`）：

```properties
spring.datasource.mds.sharding.tables=[
  {"tableName":"mds_metering","shardingColumn":"service_code","tableNum":64},
  {"tableName":"mds_charge_detail","shardingColumn":"service_code","tableNum":64},
  {"tableName":"mds_charge_dept","shardingColumn":"cost_day","tableNum":60},
  {"tableName":"mds_charge_dept_month","shardingColumn":"cost_month","tableNum":5}
]
```

**注意分片键的选择**：按 `service_code` 哈希（均匀打散），按月（时间归档）。两种策略对应两种查询模式。

> 📌 仓库内仅 clouddnsdev 显式配置了分表，其他环境的分表配置在 Nacos 中。

### 3.4 冷热分层：明细不入库，快照入库存

这是**最重要的一招**。大数据量不是靠"存得下"，而是靠"不存明细"。

| 表 | 粒度 | 生成方式 |
|---|---|---|
| `idc_cabinet_utilization_snapshot` | 每天每机柜一行 | `cabinetDailySnapshotTaskJobHandler`（cron `0 0 0 * * ?`） |
| `server_physical_stat_snapshot` | 每天每区域一行 | 定时任务 |
| `report_userate_one_machine` / `_group` / `_ptn` | 聚合结果 | `userate` 定时任务 |
| `*_hist`（工单/操作历史） | 事件后归档 | 业务写入时同步 |

任务处理器代码注释写得很直白（`CabinetDailySnapshotTaskJobHandler.java`）：

> *每天凌晨 00:00 执行，将全量实时数据落库，供历史日期查询使用。*

> **核心思想**：**查询走快照，不回扫明细。**页面要"上个月某机柜利用率"，直接读一行快照，而不是去扫一个月的原始数据。这是关系库 + 定时任务模拟数据仓库的经典做法。

生活类比：这像便利店每天打烊后把当天营业额记成一行台账（快照）——月底想看"上月某天卖了多少"，直接翻台账那一行，而不是把那天每一笔小票重新加一遍。明细（每笔小票）另存别处，台账只留算好的结果。

## 四、三条端到端数据流

> **这一节是重点。** 理解数据流转比读代码更重要——代码是"怎么实现"，数据流是"为什么这么实现"。

### 4.1 流 A：IDC 资源指标（详见 [[10-指标上报链路]]）

```
idc-meta-data-service                      report-service                      查询
┌──────────────────┐   Dubbo 分页          ┌──────────────────┐              ┌────────┐
│ 全量机柜快照      │ ──────────────────▶  │ receive_record   │              │ Metric │
│ 分页 + 完成清单   │                       │ (MySQL 归档)      │              │ Query  │
└──────────────────┘                       └────────┬─────────┘              │  API   │
                                                    │ 状态机 + 投影           └───▲────┘
                                                    ▼                            │
                                           ┌──────────────────┐              │
                                           │ outbox (MySQL)    │              │
                                           └────────┬─────────┘              │
                                                    │ Kafka                  │
                                                    ▼                        │
                                              Flink ──▶ Elasticsearch ────────┘
```

**存储分工**：MySQL 只存**状态与清单**（小体量、强一致），ES 存**指标文档**（大体量、按 documentId 查）。中间用 outbox + Kafka 保证不丢不重。📌 代码侧入口：`S-starter/S-elasticsearch-starter`（DidiEsService：search/bulk/count/sql/scroll，ES_MAX_SIZE=10000；客户端为内部 fork `elasticsearch-didi-java-client` **6.6.1.500**），**6 个 pom** 依赖；配置键 `spring.didi.elasticsearch.server/port/app_id`（实测 10.88.128.149:30963）；典型消费者 S-auth-service `SmartLogServiceImpl`（操作日志检索）。

### 4.2 流 B：使用率（本项目最复杂的一条）

```
① 采集写入
   raw usage  ──▶ VictoriaMetrics（线协议写入，主路径）
                        │ 写失败
                        └──▶ Kafka（retry 队列）
   InfluxDB（旧）──dataTransfer──▶ VictoriaMetrics（历史迁移）

② 日聚合（xxl-job，T+1）
   VictoriaMetrics ──PromQL──▶ useRate{Cloud,Idc,Luban}Kfk2SrHandler
                                        │
                    ┌───────────────────┴───────────────────┐
                    ▼                                       ▼
        Kafka（userate_cloud_aggregated /              MySQL report_userate_*
               userate_idc_aggregated /                 （页面直接查）
               userate_luban_instance_detail）            （intra 库）
                    │
                    ▼（仓库外，平台侧消费）
              StarRocks（分析型宽表）
```

关键类：

| 环节 | 类 | 说明 |
|---|---|---|
| 写入 VM | `UsageDataKeeperServiceImpl.insertLineProtocolData` | 失败自动转 Kafka 重试 |
| 旧库迁移 | `UsageDataKeeperServiceImpl.dataTransfer` | 用 InfluxQL（InfluxDB 的查询语言）读出，转成时序数据点，再写入 VictoriaMetrics |
| PromQL 聚合 | `UsageQueryEngineService` / `UsageQueryVmService` | 按时间跨度动态算 step |
| 日聚合任务 | `UseRateCloudKfk2SrHandler` 等三个 | 每天跑前一天，分批 100 投 Kafka |
| 落 MySQL 报表 | `report_userate_*` Mapper | 供页面直接查 |

> **`Kfk2Sr` = Kafka to StarRocks。** 仓库内只做到"把聚合结果发进 Kafka"，真正装载进 StarRocks 的消费者在平台侧（Flink 任务或数据平台），不在本仓库。

**这条流最能体现"分层"**：原始打点永远不进 MySQL；MySQL 只存聚合后的报表行；超大规模的明细交给 Kafka，再进 StarRocks。

### 4.3 流 C：日志与审计

```
应用 logback ──▶ app-log 文件 ──filebeat──▶ logstash(grok) ──▶ ES（检索）
                                    │
业务审计 ──异步线程池──▶ Kafka topic（失败才落 cmdb_operate_log 表，再失败发邮件）
```

详见 [[08-日志治理]]。

## 五、为什么不引入 Hive

**结论**：这个项目不需要 Hive。原因不是"数据量不够大"，而是**查询形态不匹配**。

三个原因，都是按**查询形态**判的，不是按数据量：

1. **指标是预聚合的**。`report_userate_*` / `*_snapshot` 已经算好了结果，查询只需要"取某一行"，不需要扫 TB 级明细。
2. **要近实时**。报表页面点开就要有结果，Hive 的 T+1 周期等不起。ES 和 MySQL 快照都能秒级响应。
3. **明细已经在别处**。原始打点进了 VictoriaMetrics / StarRocks，MySQL 只留聚合行。**"不存明细"本身就消除了对 Hive 的需求。**

> **判据总结**（这张表比 Hive 本身有用）：
>
> | 你要什么 | 选什么 |
> |---|---|
> | 精确找几行 | MySQL |
> | 秒级查聚合结果 | ES / MySQL 快照 / StarRocks |
> | 扫 TB~PB 明细做离线分析 | Hive / Spark / Trino |
>
> 本项目只命中前两种。

> 📖 Hive 自身的机制（SQL→MR/Spark、HDFS 列式文件、Metastore 常在 MySQL、与 MySQL 的九维对比）
> 属于**通用知识**，和判断这个项目无关，需要时查资料即可。

## 六、需要留意的"看着有、其实没用"

研究对象代码时最容易误判的一点：**配置和工具类存在，不代表链路在跑。**

| 组件 | 表面证据 | 实际情况 |
|---|---|---|
| `S-hbase-starter` | root `pom.xml:421` 声明了依赖，还定义了 `hbase.didi.version` | ⚠️ **模块目录不存在**，也没有任何 HBase 客户端代码。搜索命中全是 `authBase`（其中的 Base 不是 HBase）等误报。**死配置** |
| `StarRocksStreamLoadUtils` | `S-Core` 里有完整的 Stream Load HTTP 客户端（含分区删除、任务查询） | ⚠️ **仓库内无任何调用方**。它更可能是给外部/历史任务用的工具。StarRocks 的真实装载在平台侧 |
| `spring.datasource.starrocks.*` | Nacos `datasource.properties` 里**真实存在**（dev 与 test 端口不同） | 📌 **补充**：配置侧是在维护的真实数据源，分环境存在。但仓库内**仍无查询代码**——写入走 Kafka（`Kfk2Sr`），读取在平台侧 |
| `S-influxdb-starter` | 23 个文件在用 | 📌 真在用，但**处于迁移期**：`dataTransfer` 明确在做从 InfluxDB 迁往 VictoriaMetrics |
| `S-vm-starter` | 在 `userate-*` 中使用 | 📌 **这是现行的时序库**（VictoriaMetrics，兼容 PromQL） |

> **方法论**：判断一个组件是否真的在用，要满足三件事——**依赖声明 + 配置项 + 有调用方**。缺一个都可疑。✅ 规范：定期清理死配置/死代码（三信号缺即删），别让"看起来在"误导读者。

## 七、怎么啃这部分

**五步啃法和五道自检题在 [[07-技术TODO]] 的 L8.3 / L8.4**，这里不重复。

补一条容易混淆的辨析：

> **快照是"每天一个截面"，指标文档是"每次采集的一代"。**
> 前者服务"历史趋势"，后者服务"当前状态 + 发布审计"。
> 同一个业务概念，服务两种查询模式，所以存两份——**这不是冗余，是物化视图（把计算结果预先算好存成表，查时直接读）**。

## 八、一图总览

```
                        ┌──────────── 业务查询 ─────────────┐
                        │ 页面 / 报表 / nl2sql              │
                        └───────┬──────────────┬────────────┘
                                │              │
                     ┌──────────▼───┐   ┌──────▼─────────┐
                     │ MySQL 快照表  │   │ ES 指标文档     │
                     │ 日粒度、预聚合 │   │ 代粒度、可检索   │
                     └──────▲───────┘   └──────▲─────────┘
                            │ 定时聚合          │ Kafka→Flink
                     ┌──────┴───────┐   ┌──────┴─────────┐
                     │ MySQL 业务表  │   │ 指标 outbox     │
                     └──────▲───────┘   └──────▲─────────┘
                            │                  │
        ┌───────────────────┴──────────┐       │
        │                              │       │
┌───────▼────────┐          ┌──────────▼───┐   │
│ MySQL 多库分域  │          │ Kafka / DDMQ │◀──┘
│ 分表 / 读写分离 │          └──────┬───────┘
└────────────────┘                 │
                          ┌────────▼─────────┐
                          │ StarRocks（外部） │
                          └──────────────────┘

时序数据旁路：VictoriaMetrics（原始打点）──PromQL──▶ 日聚合 ──▶ Kafka / MySQL 报表
```

**一句话总结**：**明细不落 MySQL，MySQL 只留状态和快照；查询按"找几行 / 查聚合 / 扫全量"分到 MySQL / ES+StarRocks / Hive 类引擎。**
