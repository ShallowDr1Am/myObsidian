## 一、线上部署全流程（主路径）

```
① mvn clean package -P{profile}    →   ② 产出 tar.gz   →   ③ 上传解压   →   ④ control.sh start
       build.sh 干的事                     assembly.xml 打的包      部署目录         解压 + 拉起 java
```

### 步骤 ①：构建

`build.sh`：

```bash
profile_new=${profile:-prod}                 # 默认 prod
service_name=${output_service:-all}          # 默认打全部服务

export JAVA_HOME=/usr/local/jdk1.8.0_65      # ⚠️ 写死 Linux JDK 路径
export PATH=$JAVA_HOME/bin:$PATH

mvn clean package -P${profile_new} -Dmaven.test.skip=true

# 把找到的 *.tar.gz 收集到 output/
rm -rf output && mkdir output
for i in $(find . -name *.tar.gz); do cp $i output/; done
cp control.sh output/
```

用法：
```bash
profile=prod output_service=acl ./build.sh        # 只打 acl 服务
profile=test ./build.sh                            # 打全部，test 环境
```

> ⚠️ **Mac 上不能直接跑**：脚本写死了 `JAVA_HOME=/usr/local/jdk1.8.0_65`（Linux 路径），且需要命令行 `mvn`。本机用 IDEA 的 Maven 或改掉这两行。

### 步骤 ②：tar.gz 里有什么

`assembly.xml` 定义的包结构：

```
<service>.tar.gz
└── <service>/
    ├── <service>.jar          ← 主 jar（spring-boot rePackage，layout=ZIP）
    ├── libs/                  ← 全部依赖 jar（maven-dependency-plugin 拷的）
    ├── config/                ← logback.xml 等
    ├── bin/                   ← startup.sh / shutdown.sh / docker_startup.sh
    │                            （按 profile 从 ../../conf/bin/${activatedProperties} 拷）
    └── agent/                 ← skywalking-agent.jar
```

**关键点**：主 jar **不含依赖**（`spring-boot-maven-plugin` 的 `layout=ZIP` + `includes` 只打自身），依赖在 `libs/`，靠 `-Dloader.path` 加载。这样依赖层可复用、jar 小。

> 各服务 pom 里用 `maven-resources-plugin` 把 `../../conf/log`、`../../conf/agent`、`../../conf/bin/${activatedProperties}` 拷到 `target/conf`、`target/agent`、`target/bin`，再由 assembly 打包。**这就是 profile 决定用哪套启动脚本的机制。**

### 步骤 ③④：解压启动

`control.sh`（部署目录的最后一层就是服务名）：

```bash
app=${workspace##*/}              # 部署目录名 = 服务名
sh control.sh start
  → tar -zxvf ${app}.tar.gz
  → cd ${app}
  → sh ./bin/docker_startup.sh    # 真正拉 java
  → 循环 ps 检查 pid
```

`control.sh stop` 会先进入服务目录执行 `bin/shutdown.sh`。`shutdown.sh` 的逻辑：先用 `kill $PID` 通知进程退出，然后每 2 秒轮询一次（最多 200 次）确认退出；轮询 120 次后仍不退出，就用 `kill -9` 强制结束。**这是优雅关闭的兜底。**

### 启动脚本的 JVM（Java 虚拟机）参数（`docker_startup.sh`）

```bash
STARTUP_CMD=" -server -Xms4g -Xmx4g -Xmn2g -XX:MetaspaceSize=128m -XX:MaxMetaspaceSize=320m "

JAVA_OPT=" -Dlog4j2.formatMsgNoLookups=true"                        # Log4Shell 漏洞修复
JAVA_OPT+=" -Xloggc:${BASE_DIR}/logs/gc.log -verbose:gc ..."        # GC（垃圾回收）日志
JAVA_OPT+=" -XX:+HeapDumpOnOutOfMemoryError"                       # OOM（内存耗尽）时自动导出内存快照
JAVA_OPT+=" -Dloader.path=${BASE_DIR}/libs"                        # ★ 从 libs/ 加载依赖
JAVA_OPT+=" -Dlog.home=${BASE_DIR}"                                # 日志根目录
JAVA_OPT+=" -Dapp.name=${APPLICATION}"                             # 应用名（日志 Pattern 用）
JAVA_OPT+=" -jar ${JAR_PATH}"
JAVA_OPT+=" --logging.config=${LOG_CONF_NAME}"                     # docker_logback.xml
JAVA_OPT+=" --server.port=${PORT}"                                 # 仅当 -p 指定
```

> `-Dlog.home` 和 `-Dapp.name` 会被 `logback.xml` 的 `<springProperty>` 读到，决定日志写哪。

### ⚠️ dev/test 的隔离程度比想象中低

对照 Nacos 导出（`DEV_GROUP/datasource.properties` vs `TEST_GROUP/datasource.properties`）后确认：

| 维度 | 是否隔离 |
|---|---|
| Nacos namespace | ✅ 不同 |
| 配置 group | ✅ `DEV_GROUP` vs `TEST_GROUP` |
| **MySQL 实例** | ❌ **完全相同**（同一个 `dev46` 库） |
| Redis（codis） | ✅ 不同节点 |
| StarRocks | ⚠️ 仅端口不同 |

> **实操警告**：**在 dev profile 下写数据，test 环境会看到。**本地调试时不要执行写入类操作，或先确认影响范围。

### 配置分布（Nacos 导出实证）

| Group | 数量 | 内容 |
|---|---|---|
| `DEFAULT_GROUP` | 3 | 全局共享（`application` / `cost-config` / `workflow`） |
| `DEV_GROUP` | 19 | 开发环境 |
| `TEST_GROUP` | 19 | 测试环境 |
| `PROD_GROUP` | **9** | 生产（明显更少，走另一套精简配置） |
| `SHARED_GROUP` | 6 | **按服务**共享（`report` / `idcOps` / `network-device` / `omsOps` / `serverLife` / `common`） |

> **两个反常，值得注意**：
> ① `PROD_GROUP` 只有 9 个，而 dev/test 各 19 个——**生产用的不是同一套配置组织方式**。
> ② `SHARED_GROUP` 是**按服务维度**切分的，与 dev/test 的**按环境维度**是两个相互独立的划分。同一个服务的配置可能同时来自两边。

profile 在**两处**发生作用：

- **打包时**，`-P${profile}` 决定 `<activatedProperties>`，它替换掉 `bootstrap.properties` 里的 `spring.profiles.active=@activatedProperties@`，同时把对应的 `conf/bin/${activatedProperties}/` 启动脚本拷进包。
- **启动时**，`bootstrap-${profile}.properties` 决定连哪个 Nacos namespace。

> 根 pom 里 `test` 是 `<activeByDefault>true</activeByDefault>`（第 680 行附近），即**不指定 -P 时默认 test**。

### ⚠️ 先看清一个硬约束：**无法脱离内网 Nacos 启动**

这不是"最好连"，是**硬依赖**，三层阻塞按顺序爆炸：

| 层 | 阻塞 | 何时失败 |
|---|---|---|
| ① **bootstrap** | Nacos 拉 **72 个** `extension-configs`（扩展配置清单）+ 2 个 shared-dataids（共享配置） | **Spring 容器创建之前** |
| ② **Bean 装配** | `DruidDataSource` 拿 `environment.getProperty("spring.datasource.*.url")`，拿不到就是 `null` | 容器启动中 |
| ③ **运行** | 连不上 MySQL / Redis / ES / Kafka | 首次调用 |

**关键事实**：

- 服务自己的 `application.properties` 只有 8 行（端口、应用名），**没有数据库地址**——全在 Nacos
- 项目**没有配置 `spring.cloud.nacos.config.fail-fast=false`**，也没有 `bootstrap-local.properties` 兜底，所以连不上就立刻报错停止（fail-fast）
- 所有 profile 的 Nacos 地址**都是内网 IP 或内部域名**，没有一个指向 localhost

**失败长这样**（发生在 bootstrap 阶段，比 Bean 创建更早）：

```
NacosException: failed to req API:/nacos/v1/cs/configs
  after all servers([10.78.128.115:8848]) tried
```

### 关于"用内存数据库 H2 顶替"

项目里**确实有 H2**，但**只用于测试**，不能让你启动服务：

| 模块 | 声明 | 用途 |
|---|---|---|
| `S-dns-order` | `com.h2database:h2`（compile） | 单测内存库 |
| `S-network-device-service` | `com.h2database:h2` `<scope>test</scope>` | 单测/集成测试 |

用法示例（`SmartDnsWorkorderMapperTest.java`）：

```java
new PooledDataSource("org.h2.Driver",
    "jdbc:h2:mem:smart_dns_workorder;MODE=MySQL;DB_CLOSE_DELAY=-1", "sa", "");
```

**为什么顶不了**：① H2 解决不了 ① 层的 Nacos 阻塞；② 72 个 dataId 里只有 1 个是数据源； ③ 还有三个硬伤——**H2 无 `JSON_EXTRACT` / `JSON_SET` / `JSON_UNQUOTE`**（`MetricJobMapper` 大量依赖），`GROUP_CONCAT`（13 处）语法不同，且项目没有统一的可执行 DDL（建表 SQL）入口。

> **结论**：H2 是**测试替身**，不是**运行时降级方案**。

**为什么必须带 `EXTRA_ARGS`**：`bootstrap-*.properties` 里写的是内网 Nacos（`10.78.128.115:8848`），必须用启动参数覆盖成 `127.0.0.1`，否则会在 bootstrap 阶段就失败。`idea-args.txt` 里是这 **12 个**参数：

| 参数 | 覆盖什么 |
|---|---|
| `--nacos.server-addr=127.0.0.1:8848` | 自研 `NacosRegistry` 的地址 |
| `--spring.cloud.nacos.config.{server-addr,username,password}` | Spring Cloud 配置中心 |
| `--spring.cloud.nacos.discovery.{server-addr,username,password}` | 服务注册发现 |
| `--dubbo.registry.address=127.0.0.1:8848` | Dubbo 注册中心 |
| `--nacos.config.*` / `--nacos.registry.*` | 自研 starter 的账号密码（留空） |

**`NOPROXY=1` 是另一个坑**：开了 Clash 之类系统代理时，JVM 会把 `socksProxyHost` 读进去，项目的端口探测逻辑会误判"所有端口被占用"，空转两万次才随机到一个端口。关掉即可。

**`svc.sh` 到底做了什么**（读源码确认的，别指望它更多）：

| 它做 | 它**不**做 |
|---|---|
| 找模块、找 `target/*.jar`（**没有就报"还没构建"并退出**） | ❌ **不编译** |
| 用 JDK8 + `-Dloader.path=target/libs` 起 jar | ❌ **不注入任何 Nacos 参数** |
| `--server.port` 取 `application.properties` 里的值 | ❌ 不检查 Nacos 连没连上 |
| 等端口就绪（最多 240 秒），超时后先看进程死没死 | |
| `bash svc.sh list` 列出 **41** 个服务、端口、是否已构建 | |


> 这就是我们做过的事。**门槛确实很高**：`bootstrap-dev.properties` 里有 **72 个**
> `extension-configs`，全都要建；而且建全了还不够——配置里写的数据库/ES/Kafka
> 地址**仍是内网地址**，必须逐个改成本地，服务才连得上。
>
> 所以别手搓了，用 `import-configs.py`。它做的就是"建 26 份配置 + 改写内网地址"这件事。

</details>

## 四、常见坑

| 坑 | 表现 | 处理 |
|---|---|---|
| **连不上 Nacos**（硬依赖） | 启动在 **bootstrap 阶段**就失败：`NacosException: failed to req API:/nacos/v1/cs/configs` | 用本地 Nacos（方式 C）；或连 VPN |
| **xxl-job 刷屏**（不是报错） | 服务**启动成功**，但每 60 秒一条 `xxl-job registry error ... 10.78.128.115:8087`，6 小时把日志撑到 **25 MB** | 本地 Nacos 设 `task.enable=false`；或用 `-P dev` 编译（`dev` 不在 `@Profile` 名单里）。详见 [[04-starter 是什么]] §6.3 |
| 想用 H2 脱离 MySQL 启动 | H2 只在 test scope；`JSON_EXTRACT` 等函数 H2 不支持 | **用测试验证逻辑**，不要试图启动 |
| `build.sh` 写死 Linux JDK 路径 | Mac 上跑报错 | 改 `JAVA_HOME` 或用 IDEA 打包 |
| 库模块没 install | 报 `找不到符号 S-Core` / 依赖解析失败 | 对根 pom 执行 `install` |
| 选错 JDK | 编译/启动报模块化、反射错误 | 必须 JDK 8（Homebrew 的 JDK 23 不行） |
| `spring.profiles.active` 没设 | 连到默认 profile（**test**，因为它是 `activeByDefault`）的 Nacos | VM options 加 `-Dspring.profiles.active=dev` |
| 端口冲突 | 启动报 `Address already in use` | `application.properties` 里换端口或释放 |

> **学习建议**：本项目的正确打开方式是"读代码 + 跑单测"，而不是"启动整个服务"。
> 完整方法见 [[07-技术TODO]] 开头的 **"不启动项目怎么学"**。
