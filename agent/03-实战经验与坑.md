# 实战经验与坑

## 经验（做法 → 证据 → 迁移）

| # | 做法 | 证据 | 迁移到自己项目 |
|---|---|---|---|
| 1 | LLM 输出当待校验计划，不当命令 | `ToolGraphCompiler` 拒绝不合规计划 | 执行前过 JSON Schema 校验 |
| 2 | 能确定性解决的不问模型 | 3 个 Deterministic Resolver 在模型之前 | 高频场景规则短路 |
| 3 | 门禁要早、便宜、重复 | 四道门禁 + Gateway/Provider 双检 | 校验前移 + 双层防御 |
| 4 | 先落库再异步 | `admit()` 在 `submit()` 前，避免失败占位消息 | 准入失败不留脏数据 |
| 5 | 密钥加密分层兜底 | AES-GCM + PERSONAL/PLATFORM_DEFAULT | 不进代码/启动参数，换 key 不重启 |
| 6 | 状态分热冷 | Redis 热 + JDBC 冷，焦点双仓库 | 按读写特征选存储 |
| 7 | 跨团队依赖版本化 | 契约版本区间 + toolCatalogVersion | 在途请求不被上游升级打崩 |
| 8 | 输入来源可追溯 | InputSource 四值 + Provenance 快照 | 审计字段说清「值哪来的」 |
| 9 | 人机确认做断点续跑 | interaction 2350 行 + 乐观并发 | 续跑不重规划，防连点竞态 |

## 坑（现象 → 证据 → 规避）

| # | 现象 | 证据 | 规避 |
|---|---|---|---|
| 1 | 渠道各搞一套深逻辑 | webchat/dc/dify 三套 SingleFlightGuard + Redis store + 准入 | 防重/准入/会话只写一份，渠道只做协议转换 |
| 2 | 分层仪式过量 | ai 包 57 个 enum + 35 个 Snapshot/Codec/Policy/Descriptor | 删掉只做转手的类 |
| 3 | 过渡版超出声明范围，文档未良好执行 | 文档说 RabbitMQ+Worker，代码 0 MQ 纯线程池；文档说 NL2SQL「补充」，代码建了 1897 行子系统；目标 Java21+SpringAI 实际 Java8 手写 | 以代码为准，文档当意图；过渡方案写退出条件并守住 |
| 4 | 手写商品化能力 | llm 2161 行 + rag 1352 行，框架均有对应物 | 标准化能力用框架，编排才自研 |
| 5 | 出站 HTTP 不统一 | cmdbtool 混用 HttpURLConnection/HttpClient/RestTemplate | 收敛到一个封装，统一超时/重试/埋点 |
| 6 | 技术栈债 | Java 8 + Boot 2.7（2023 底停维）+ fastjson 1.x | 升级要有排期，决策别停在文档 |
| 7 | 手写向量 SQL | `embedding <-> ?::vector` 裸 SQL，索引/过滤/混合检索全自理 | 规模上来换 VectorStore 抽象 |

## 量化结论

核心代码约 7.9 万行：框架可直接替代的管道约 1 万行（13%），渠道合并+仪式精简再省几千行。**偶然之重约两成，必要之重约八成**。「重建砍一半」不成立。
