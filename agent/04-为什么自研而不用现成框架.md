# 为什么自研（以代码为准）

**方法声明**：设计文档是目标态，实际并未良好执行。本篇结论全部从代码考证，文档只作「声称的意图」对照，不当事实。路径相对 `src/main/java/com/didi/`。

## 硬约束：Java 8 排除了一切现成框架

| 事实 | 证据 |
|---|---|
| 全仓 Java 8 | 根 `pom.xml` 唯一 `<java.version>1.8</java.version>`，ops-tool 经 parent 继承 |
| 0 个 AI 框架依赖 | ops-tool `pom.xml`：spring-ai / langchain4j / langgraph4j 均 0 引用 |
| 现代框架全要 Java 17+ | Spring AI 2.x、LangChain4j、LangGraph4j 基线均 17+；LangGraph 本体是 Python |

**结论**：在 Java 8 运行时上，现代 Java AI 框架一个都装不进来，Python LangGraph 意味着第二语言栈。这才是自研的硬原因——是运行时约束，不是「我们更喜欢工作流」的理念偏好。文档那套「四路线评分选 D」是规划叙事，代码没走到那一步。

## 代码实际的编排形态（考证）

| 形态 | 代码证据 |
|---|---|
| 单编排，无子 Agent | 全模块 5 处 handoff 均为阶段交接（`ToolPlanningStage.TASKGRAPH_HANDOFF`），非 agent 路由 |
| **有界修复循环**（非自由循环，也非纯拒绝） | `CapabilityPlanningService:59` `MAX_PLAN_REPAIR_ATTEMPTS=1`、`MAX_MODEL_TRANSPORT_RETRIES=1`，且受 `request.getDeadlineEpochMillis()` 时限约束 |
| 编译门禁 | `taskgraph/compilation/ToolGraphCompiler` |
| 确定性渲染 | `ai/presentation/` 全包 **0 处 llm 引用**，数字真不过模型 |
| 权限门禁 | `toolruntime/gateway/ToolGateway` + CMDB 角色客户端 |
| 进程内异步 | 线程池 + `@Async`，见下 |

修复循环真实流程（`CapabilityPlanningService:556-580`）：

```
模型提交计划 → 准入校验
  ├ 通过 → 编译执行
  └ 不过 ├ 不可修复 → 拒绝 + 兜底文案
         └ 可修复 且 未超修复次数 且 未超 deadline
              → 构造 repairFeedback 回喂模型 → 重规划 1 次 → 仍不过则拒绝
```

## 结论

- 自研的**硬原因**是 Java 8 排除现成框架；治理层（编译门禁/权限/确定性渲染）无论用什么框架都得自研。
- 文档是目标态（Java 21 + Spring AI + RabbitMQ），代码是过渡态，且已超出文档范围：NL2SQL 真建出来了、异步根本没上 MQ。
- **读这个服务以代码为准**；文档 ADR 当「声称的意图」，遇到与代码冲突一律信代码。
