## 各层职责

### 1. 用户端

| 选项 | 场景 | 你的技术栈 |
|------|------|-----------|
| Web (Next.js/React) | 主力，浏览器直接访问 | ✅ React |
| 移动端 (RN/Flutter) | 可选，后续扩展 | - |
| CLI | 开发调试、本地工具 | ✅ 命令行工具 |

### 2. Nginx — 流量入口

```
用户 → https://yourdomain.com → Nginx (443)
                                 ├─ /api/*     → Node.js :3000
                                 ├─ /ai/*      → Python :8000 (不直接暴露)
                                 └─ /           → Next.js 静态资源
```

做的事：SSL 终止、静态文件服务、反向代理、限流、防 DDoS。**Python 服务绝对不直接暴露公网**。

### 3. Node.js API 服务 — 业务主控

你主力语言，负责一切非 AI 逻辑：

```
职责：
├── 用户系统（注册/登录/JWT）
├── 业务 API（CRUD）
├── 会话管理（Session → Redis）
├── 调用 Python AI 服务（gRPC/HTTP，内部网络）
├── 限流（Redis 计数器）
└── 日志/监控
```

为什么不是 Python 扛在线：Node 事件驱动模型天然高并发，Python 的 GIL 在处理大量并发 I/O 时不占优势。

### 4. Python AI 服务 — 智能核心

你正在学的部分，独立部署，不碰业务逻辑：

```
职责：
├── LangGraph Agent（多轮推理循环）
├── RAG 检索（向量库查询）
├── Tool Calling（调用外部 API）
├── Embedding 生成（文本 → 向量）
├── 文档处理管线（解析 → 切分 → 写入向量库）
└── 定时任务（文档变更检测、索引维护）
```

Node 调 Python 的方式：gRPC（推荐，性能最好）或 HTTP REST（简单，够用）。

### 5. Redis Stack — 共享状态

```
用途：
├── 聊天历史持久化 → RedisChatMessageHistory
├── Session 缓存 → 用户登录态
├── 限流计数器 → 防刷
└── 任务队列 → 异步任务（文档处理）
```

Node 和 Python 都能连同一份 Redis，所以会话状态天然共享。用户登录后 Node 写 session → Python 读历史消息 — 同一个 Redis key。

### 6. 向量数据库 — AI 的"外部记忆"

```
用途：
├── RAG 原文检索
├── 用户上传文档的向量索引
└── metadata 过滤（doc_id、租户ID、时间范围）
```

本地开发 ChromaDB，生产迁移 Milvus 或 Qdrant（支持分布式、更高性能）。

## 服务器部署方案

### 最低配置起步

| 资源 | 规格 | 用途 |
|------|------|------|
| CPU | 4 核 | Node + Python + Nginx + Redis |
| 内存 | 8 GB | Python 加载 embedding 模型占用大 |
| 磁盘 | 50 GB | 向量库 + 文档 + 日志 |
| 带宽 | 按量 | 国内 1M 小水管够测试 |

### 部署方式

```
方案 A: Docker Compose（推荐起步）
├── nginx container
├── node container
├── python container
├── redis container
└── 向量库 container (可选，或用 ChromaDB 嵌入 Python)
一条命令：docker-compose up -d

方案 B: 云服务（规模大了再考虑）
├── 各组件拆成独立实例
├── K8s 编排
└── 数据库上云托管
```

### 关键安全原则

```
- Python 服务不暴露公网端口（只监听 127.0.0.1）
- Nginx 做 SSL 终止
- Redis 设密码 + 不暴露公网
- API key 走环境变量，不入镜像
- 日志不记录用户原始输入
```
