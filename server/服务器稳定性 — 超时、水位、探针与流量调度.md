# 服务器稳定性 — 超时、水位、探针与流量调度

> 从 audit-server（NestJS 工单审计平台）出发聊出来的后端稳定性知识地图。
> 记录时的角色：前端工程师学后端。**核心方法论：所有概念都先找到前端世界的对应物。**

---

## 〇、总览：今天聊出来的知识版图

按依赖顺序重排（每个概念建立在前一个之上）：

```
1. 一个服务是什么      → 进程同时扮演 API + Worker 两个角色
2. 请求的生死          → 实例重启 = 页面刷新，在途请求全断
3. LB（负载均衡）      → 流量分配员 + 一份带 TTL 的"活实例"名单缓存
4. 探针（健康检查）    → 实例在"拉模式"世界里唯一的发声渠道
5. 优雅关闭 & 排水     → 先挂牌"暂停接待"，让在途客人买完单，再锁门
6. readiness 窗口     → 活着 ≠ 能服务（后端版白屏问题）
7. resilience 模式    → 假设失败是常态来组织代码（超时/重试/降级/熔断）
8. 容量水位            → 已用量/总容量，70/80 双阈值
9. 探知边界            → 自适应并发（AIMD），让容量边界自己浮现
10. 稳定性优先级       → 先堵级联入口，再谈压榨容量
```

**一句话主线**：依赖活着 ≠ 请求不丢；"监控"只负责看见，"闸门"负责挡住——闸门必须代码自己写。

### 压缩认知：10 个名词 = 3 个根思想

| 根思想 | 一句话 | 覆盖 |
|---|---|---|
| **① 信息会过期** | 世界是分布式的，没有任何一方拥有实时真相——LB 名单是几秒前的快照、"进程还活着"可能是过期真相（假死） | LB、探针、readiness 窗口、优雅关闭为何需要配合 |
| **② 死亡是常态** | 进程会重启、依赖会挂，所以请求必须有界、失败有预案、死亡有仪式 | 请求的生死、排水、resilience 四件套、稳定性优先级 |
| **③ 反馈优于预测** | 容量边界测不出来，只能靠响应信号逼近；监控看过去，闸门保现在 | 水位、探知边界/AIMD |

（第 1 条是架构事实，第 10 条是工程判断，不是名词。）

**翻译题 vs 新知识**：readiness/优雅关闭/探针/重试退避/降级/超时——前端早有对应物（白屏、SW 生命周期、controllerchange、请求层重试、兜底渲染、AbortController），只是拿到官方名称。真正的新物理只有四条：① 在途请求与进程绑定（重启发生在用户背后）② 队列改变失败语义（写路径有安全网、读路径没有）③ cgroup 可读自身配额 ④ 被动健康检查拿真实用户当探针。

## 一、先搞清楚：这个服务到底是什么

audit-server 的部署形态（[ecosystem.config.js]）：

```
PM2 cluster 模式，6 个实例，同一个 main.js
└── AppModule
    ├── HTTP Controllers（tickets、statistics、audit...）  ← 同步读写路径
    └── WorkerModule（BullMQ Workers）                     ← 异步任务路径
```

**关键事实：HTTP 服务和 Worker 跑在同一个进程里。**

```
用户/前端 ──HTTP──> audit-server（同时是 API 服务 + Worker）
                      │
                      ├─ GET /tickets、/statistics/summary   ← 直连查库，无队列兜底
                      └─ POST /submit ──add()──> Redis 队列 ──> Worker 消费
```

- **写路径**（submit → 队列 → worker）：天然有缓冲。实例挂了，BullMQ 会把 stalled 任务重新投递，配合 `attempts: 5` + backoff 自愈
- **读路径**（GET 接口）：用户直连，**没有任何队列兜底**。实例死了，请求就是死了

> 为什么重要：后面所有稳定性话题，主要保护的都是**读路径**——因为它没有重试机制这个安全网。

## 二、请求的生死：实例重启 = 页面刷新

**误区**："重启进程不意味着 MySQL/Redis 关闭，数据都在，怕什么？"

**正解**：死的不是依赖，是"拿着你请求的那个进程"。用前端现象类比：

> 浏览器按 F5：MySQL 挂了吗？没有。但页面里所有进行中的 `fetch()` 全部被取消，pending 的 Promise 永远不会 resolve。

从单个 HTTP 请求的视角，处理它的实例就是"页面"：

| 死掉的东西 | 类比 | 后果 |
|---|---|---|
| TCP 连接 | fetch 被中止 | 响应永远写不回去 |
| 算到一半的上下文 | 组件 state 清空 | SQL 查完了也白查，JSON 组装到一半也没了 |
| 依赖活着 | MySQL 活着 | **帮不上任何忙**——刷新页面救不了那个 fetch |

**依赖活着只保证数据不丢，不保证请求不丢。** 这是整场讨论的基石认知。

## 三、LB（Load Balancer）：流量分配员

解决的问题：6 个实例，谁接这个请求？

```
用户浏览器 ──HTTP──► LB ──┬──► 实例1
                          ├──► 实例2
                          └──► ...共6个
```

前端工程师熟悉的"分流"角色都是 LB：Nginx 反向代理、公司统一网关、DNS 轮询。你写 `fetch('/api/tickets')` 时，域名 → 网关 → 某个具体实例，中间那跳就是 LB。**它对前端透明**——这是前端不知道它存在的原因。

### LB 最重要的特性：名单是缓存，实例发不出私信

```
PM2/运维 ──SIGTERM──► 旧实例      ← 私信！LB 不在抄送名单里

用户 ──HTTP──► LB ──按"成员列表"转发──► 实例们
                 │
                 └──周期性轮询──► 各实例   ← LB 了解实例的唯一方式：主动去问

旧实例 ────✗───► LB                ← 这条信道不存在！实例无法主动上报
```

- LB 脑子里的"活着的实例列表"是**带 TTL 的缓存**（健康检查周期）
- 实例下线这件事，LB 只能等缓存过期才知道
- **探针的本质：实例对 LB 的唯一发声渠道**——实例推不了消息，但可以让 LB 的下次拉取失败。拉模式下的"伪推送"

> 前端同构经验：发布了新版前端，但已打开的页面还在跑旧 bundle——你没有信道"通知所有浏览器刷新"。DNS 靠 TTL、CDN 靠缓存失效，同一个问题。

## 四、没有探针的发布会：两个事故窗口

滚动发布时，重启不是原子操作，是三件**互不同步**的事：旧实例退出 + 新实例启动 + 网关切流。

```
t=0s   PM2 给旧实例发 SIGTERM，旧实例停止监听
t=0~2s LB 不知道！名单里旧实例还在
       → 用户请求路由过去 → 502                    ← 坏窗口A：流量切晚了
t=2s   LB 探测失败/被动发现 → 摘除旧实例
t=3s   新实例 bind 端口成功，LB 立刻导流
t=3~5s 但 DB 连接池/Redis/Apollo 还没就绪 → 首批请求 500  ← 坏窗口B：流量切早了
t=5s   新实例真正就绪 → 恢复正常
```

你在 Network 面板里偶见发布瞬间一串 502 然后自愈——不是前端 bug，就是这两个窗口。

**探针把"网关猜"变成"实例说"**，完整舞步：

1. 新实例启动 → 探针答"DB 还没连上" → LB 不导流（消灭切早了）
2. 新实例就绪 → 探针答 OK → 开始导流
3. 旧实例收 SIGTERM → **主动把探针置为失败** → LB 几秒内摘除（消灭切晚了）
4. 旧实例等在途请求处理完 → 退出
5. 全程 0 失败请求

### 优雅关闭只写了一半 = 白写

```ts
// main.ts 里已有的代码
process.on('SIGTERM', () => shutdown('SIGTERM'));
// shutdown: app.close() → 处理完在途请求 → exit(0)
```

`app.close()` 处理的是**存量**（在途请求做完），探针处理的是**增量**（新请求别进来）。没有探针配合：

- LB 继续往正在关闭的实例导流
- keep-alive 长连接不消亡，`app.close()` 可能一直挂着不返回
- 最后 PM2 等不及直接 SIGKILL → 连"存量处理完"这半都没兑现

**关店的正确顺序：先在门口挂"暂停接待"的牌子（探针失败），让店里正在点单的客人买完单（优雅关闭），再锁门（exit）。**

## 五、readiness 窗口：活着 ≠ 能服务

### 前端版（你天天见的）

```
t=0.0s  HTML 到达，页面空白          ← 活着（有页面）
t=0.5s  JS bundle 下载执行
t=1.2s  React 挂载，发首批请求
t=2.8s  数据回来，渲染完成           ← 能服务（可交互）
```

白屏期你不敢把用户点击派给页面——事件处理器还没绑上。骨架屏/loading/SSR 全是在回答同一个问题：**"活着"和"能用了"之间的空隙怎么熬过去**。

### 后端版（同一个窗口）

```
t=0s    进程起来，端口开始监听        ← liveness = true（活着）
t=0.3s  连 MySQL、Redis、拉 Apollo
t=2s    连接池建好、规则引擎初始化完   ← readiness = true（能服务）
```

t=0~2s 端口通了但查库必挂——**后端的白屏时间**。

| | 前端 | 后端 |
|---|---|---|
| 活着 | HTML 到了 | 端口通 |
| 能服务 | JS 执行完可交互 | 依赖连上可处理请求 |
| 空隙 | 白屏 | readiness 窗口 |
| 空隙中硬接请求 | 点击没反应 | 用户拿到 500 |
| 解法 | loading/骨架屏/SSR | 探针：ready 前报"没准备好" |

**readiness 探针就是后端的骨架屏。** liveness 和 readiness 是两个独立探针，防的病不同：liveness 防进程死，readiness 防"进程在但脑子不在"。

### 实例假死：为什么流量照样进来

假死 = 进程活着（端口监听、TCP 握手成功）但事件循环卡死（大查询、疯狂 GC、无超时的外部调用挂满）。两种探针测的东西不同：

- **进程级探测**（端口能通吗）：假死时**依然通过**——内核代答 TCP 层
- **应用级探测**（自己在进程内真实执行检查：事件循环延迟/Redis ping）：假死时**检查本身也卡住，超时即失败** ✅

只有应用级探针能发现假死。典型成因：axios 没配 timeout，下游挂起 → pending Promise 堆满事件循环 → 全站慢。

## 六、resilience 模式：失败是常态

**Resilience = "失败是常态"这个假设下的代码写法**。四件套：

| 模式 | 前端形态（你可能写过的） | 后端形态 |
|---|---|---|
| 超时 | AbortController / fetch timeout | axios `timeout: 10_000` |
| 重试+退避 | 请求层 for 循环 + sleep(1s→2s) | BullMQ `attempts: 5, backoff` |
| 降级 | catch 后用兜底数据渲染 | fallback 配置 / 默认值 |
| 熔断 | （少见）连续失败后暂停请求一段时间 | Hystrix / resilience4j circuit breaker |

```ts
// 前端工程师写的重试——你其实早就会了
for (let i = 0; i < 3; i++) {
  try { return await fetch(url); }
  catch (e) {
    if (i === 2) throw e;
    await sleep(1000 * (i + 1));   // 退避：越失败等越久
  }
}
```

退避的直觉：对方 502 大概率是忙不过来，立刻重试 = 往拥挤的门口再挤一个人。

**核心心法：resilience 代码不问"会不会失败"，只问"失败时用户看到什么"。**

反面是"幸福路径假设"：`const data = await api.getUser()` 完事，失败 = bug 修掉就行。两种世界观写出的代码完全不同。

## 七、容量水位：70/80 的含义

水位（water level）借水库的比喻 = **已用量 / 总容量** 的百分比。CPU 水位 = 集群分配率/利用率；GPU 水位 = 显存占用率/算力分配率。

### 为什么是 70/80 双阈值

- **< 40-50%**：资源闲置，预算白花 → 平台想"提水位"（超卖、混部）
- **~70%**：健康区间——省钱且有余量
- **> 80%**：风险区。留 20-30% 余量的原因：流量毛刺、机器故障时分摊、故障恢复需要空位。**水位打满时任何抖动都会雪崩，70/80 是成本和抗风险能力的折中**

### 超过 80% 会发生什么（按系统类型）

| 系统类型 | 动作 |
|---|---|
| 调度型（K8s/GPU 集群） | 新任务排队不调度；已运行任务被 throttle（变慢不报错）；极端触发驱逐/抢占 |
| 容量管理型 | 告警 + 自动生成扩容/采购单 |
| 接入型（网关/配额） | 限流、拒绝新请求、降级 |

### 接口文档里写"水位 70/80"的真实含义

不是让你实现监控，而是**容量责任边界的声明**："我方承诺水位 80% 以内服务可用；超出后要么平台扩容，要么调用方必须自限"。如果你是调用方，下游水位就是你的代码要配合的约束。

### 监控 ≠ 闸门

- **监控**（平台/运维侧）：采集、告警、扩容——分钟级反应链路
- **闸门**（应用代码侧）：限流、排队削峰、降级、超时退避——秒级生效

流量风暴是秒级的，等监控告警生效时服务已经挂了。**"超过 80% 会发生什么"的第一道防线不在监控，而在代码自身的限流和排队。**

代码侧配置清单：入站限流 / 出站限流 / 超时+重试退避 / 队列消费速率控制 / 有界资源池 / 健康检查+优雅退出。

## 八、探知边界：代码能感知容量吗

能，但精度分层——**离自己越近越准，离自己越远越只能推断**：

| 层级 | 可见性 | 信号 |
|---|---|---|
| 进程内 | 完全可见，微秒级 | `monitorEventLoopDelay()`（**Node 最重要的自感知信号**）、`process.memoryUsage()`、队列深度 `getWaitingCount()`、连接池占用 |
| 容器/宿主 | 自己的配额可见 | cgroup：`/sys/fs/cgroup/cpu.max`、`cpu.stat` 的 `nr_throttled`（被内核限流次数 = CPU 水位超标的直接证据）；看不到邻居和整机 |
| 下游/依赖 | 不可见，只能反馈逼近 | RT 上升 → 接近饱和；超时/429/503 → 已越界 |

### 核心思想转变：从"探测边界"到"逼近边界"

生产系统很少真的去探测边界（那意味着故意打挂自己），而是**自适应并发**让边界自己浮现：

| 算法 | 思路 | 代表 |
|---|---|---|
| AIMD | 正常 +1（线性增），失败 ÷2（乘性减） | TCP、Netflix concurrency-limits |
| 梯度 | RT 当前值 vs 最小值的梯度，恶化就收缩 | Netflix gradient2 |
| Little 定律 | 最大并发 = 目标 QPS × 实测 RT | gRPC retry budget |

> Netflix concurrency-limits 不监控 CPU，只盯每个请求的成功/失败/延迟，动态调并发数——不需要知道链路带宽，靠反馈就能逼近最优速率（TCP 拥塞控制的思路）。

## 九、稳定性建设的正确顺序（重要性 > 边界感知）

**原则：先堵级联失效入口 → 再让平台能正确对待你 → 最后才自适应压榨容量。**

audit-server 的体检结果（按性价比排序）：

### 第一优先级：出站请求无超时 —— 真实存在的雪崩入口

四个 axios 实例全没配 timeout（order / main-data / sso / perm）。后果链：

```
下游 SSO 挂起 → axios 默认无超时 → 请求全挂住
→ pending Promise 堆满事件循环 → 内存涨、响应全慢
→ 6 个 PM2 实例同时中招 → 一个依赖的故障变成整个平台的故障
```

修复成本：每个实例加一行 `timeout: 10_000`。**全仓库性价比最高的稳定性改动。**

### 第二优先级：没有健康检查端点

`app.controller.ts` 只有 hello。没有 `/health` 意味着优雅关闭白写（无探针配合）、假死实例持续接流量。

### 第三优先级：失败任务无人认领

BullMQ `attempts: 5` 重试耗尽后，任务留在失败列表里只有一行日志。缺死信告警（可复用 mailer 队列）。审计任务静默丢失 = 第二天有人来问数据为什么对不上。

### 最后才是：边界感知

前三项解决"别挂"，边界感知解决"别浪费"。且做它的前提是先有反馈通道（健康端点、指标、告警）。

**顺序反了 = 用高级手段装饰一个会因依赖挂起而全站瘫痪的系统。**

## 十、我们项目的真实流量路径（LB 没有消失，只是降级了）

```
浏览器
  │ DNS
  ▼
容器 VIP（平台分配的虚拟 IP，背后是平台的 LB——第一层，平时无感）
  ▼
Nginx（upstream 配置——第二层，唯一能摸到的）
  ▼
本机 6 个 PM2 实例（cluster 模式，master 分发——第三层）
```

直觉"没有 LB"通常意味着"没有主动健康检查"——这正是现状：

### 开源 nginx 的残酷现实：没有探针，只有死后验尸

`upstream` 里的 `max_fails=2 fail_timeout=10s` 是**被动健康检查**：

```
请求 → 转给实例 → 连接被拒/超时 → 记一次失败
攒到 max_fails=2 → fail_timeout 内不再发新请求
10s 后 → "也许活了？" → 再试
```

**用真实用户的请求当探针。摘除实例的学费 = 2 个真实用户的失败请求。**（主动 `health_check` 指令是 nginx 商业版才有的）

### 无基础设施改动的最优解：发布器自己当探针

改 deploy 脚本：重启每个实例后 `curl -f http://127.0.0.1:$PORT/health` 轮询到 200 才继续下一个；stop 改成真正的 SIGTERM + 等待退出。两个窗口压到接近零。

## 十一、Service Worker：前端工程师早就见过的一切

新 SW 安装后不立即接管，旧 SW 继续服务已打开页面，所有 tab 关闭才 activate（= 排水）；
`skipWaiting()` 强行立即接管会腰斩进行中请求（= 硬重启）；
`controllerchange` 事件（= 探针通知）。

**LB + 优雅关闭 + 探针 = 服务端版本的 SW 生命周期管理。新旧交接的时序控制，两个世界是同一门课。**

| 名词 | 一句话 |
|---|---|
| LB (Load Balancer) | 流量分配员；成员名单是带 TTL 的缓存 |
| liveness probe | 进程活着吗（端口/进程级） |
| readiness probe | 能服务吗（依赖+事件循环级）；后端版骨架屏 |
| drain（排水） | 摘流量 → 处理完在途请求 → 退出 |
| graceful shutdown | 优雅关闭 = 处理完存量 + 拒绝增量 |
| resilience | 失败是常态假设下的代码组织方式（超时/重试/退避/降级/熔断） |
| backoff | 失败后等待重试，越失败等越久 |
| AIMD | 线性增、乘性减的自适应并发算法 |
| readiness 窗口 | "活着"和"能服务"之间的空隙（后端白屏） |
| 假死 | 进程在、端口通、事件循环卡死；只有应用级探针能发现 |
| 水位 | 已用量/总容量；70/80 = 成本与抗风险的折中 |
| stalled job | worker 处理中被中断的任务，BullMQ 会重新投递 |
