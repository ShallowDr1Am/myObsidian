# 服务器稳定性 — 超时、水位、探针与流量调度

> 📌 以原项目 audit-server（工单审计平台）为样本的后端稳定性知识地图。
> **核心方法论：每个概念先找一个生活场景锚点，再看机制和代码。**

---

## 〇、总览：知识版图（按依赖顺序）

每个概念建立在前一个之上：

```
1. 一个服务是什么      → 进程同时扮演 API + Worker 两个角色
2. 请求的生死          → 实例重启时在途请求全断，依赖活着也救不了
3. LB（负载均衡）      → 流量分配员 + 一份带 TTL 的"活实例"名单缓存
4. 探针（健康检查）    → 实例在"拉模式"世界里唯一的发声渠道
5. 优雅关闭 & 排水     → 先挂牌"暂停接待"，让在途客人买完单，再锁门
6. readiness 窗口     → 活着不代表能服务（开门却做不了菜的空隙）
7. resilience 模式    → 假设失败是常态来组织代码（超时/重试/降级/熔断）
8. 容量水位            → 已用量/总容量，70/80 双阈值
9. 探知边界            → 自适应并发（AIMD），让容量边界自己浮现
10. 稳定性优先级       → 先堵级联入口，再谈压榨容量
```

**一句话主线**：依赖活着，不代表请求不丢；「监控」只负责看见，「闸门」负责挡住——闸门必须代码自己写。

### 压缩认知：10 个名词背后的 3 个根思想

| 根思想 | 一句话 | 覆盖 |
|---|---|---|
| **① 信息会过期** | 世界是分布式的（多台机器各持一部分状态，谁都没有实时全貌），没有任何一方拥有实时真相——LB 名单是几秒前的快照、"进程还活着"可能是过期真相（假死） | LB、探针、readiness 窗口、优雅关闭为何需要配合 |
| **② 死亡是常态** | 进程会重启、依赖会挂，所以请求必须有界、失败有预案、死亡有仪式 | 请求的生死、排水、resilience 四件套、稳定性优先级 |
| **③ 反馈优于预测** | 容量边界测不出来，只能靠响应信号逼近；监控看过去，闸门保现在 | 水位、探知边界/AIMD |

（第 1 条是架构事实，第 10 条是工程判断，不是名词。）

**真正的新物理只有四条**：① 在途请求与进程绑定（重启发生在用户背后）② 队列改变失败语义（写路径有安全网、读路径没有）③ cgroup（Linux 给容器划资源配额的机制）可读自身配额 ④ 被动健康检查拿真实用户当探针。其余概念大多是给早已存在的工程常识一个官方名称。

## 一、先搞清楚：这个服务到底是什么

📌 audit-server 的部署形态（见项目里的 ecosystem.config.js）：

```
PM2 cluster 模式，6 个实例，同一个 main.js
└── AppModule
    ├── HTTP Controllers（tickets、statistics、audit...）  ← 同步读写路径
    └── WorkerModule（BullMQ Workers）                     ← 异步任务路径
```

名词白话：PM2 是进程守护器，负责拉起、重启实例；cluster 模式指它用同一份代码启动多个实例分摊流量；Worker 是消费队列任务的后台工人。

**关键事实：HTTP 服务和 Worker 跑在同一个进程里。**

```
用户/前端 ──HTTP──> audit-server（同时是 API 服务 + Worker）
                      │
                      ├─ GET /tickets、/statistics/summary   ← 直连查库，无队列兜底
                      └─ POST /submit ──add()──> Redis 队列 ──> Worker 消费
```

- **写路径**（提交后进队列、再由 worker 消费）：天然有缓冲。实例挂了，BullMQ 会把 stalled（卡在半途）的任务重新投递，配合 `attempts: 5`（最多重试 5 次）和 backoff（越失败等越久再重试）自愈
- **读路径**（GET 查询接口）：用户直连，**没有任何队列兜底**。实例死了，请求就是死了

> 为什么重要：后面所有稳定性话题，主要保护的都是**读路径**——因为它没有重试机制这个安全网。

## 二、请求的生死：实例重启，在途请求全断

**⚠️ 误区**："重启进程不意味着 MySQL/Redis 关闭，数据都在，怕什么？"

**正解**：死的不是依赖，是"拿着你请求的那个进程"。

> 📌 生活类比：你在银行柜台办业务，柜员突然下班、窗口关闭——金库（数据库）完好，你的存款一分没少，但柜员手里那张办了一半的单据作废了，你只能重新取号排队。

从单个 HTTP 请求的视角，处理它的实例就是那个"柜员"：

| 死掉的东西 | 生活类比 | 后果 |
|---|---|---|
| TCP 连接（请求走的网络通道） | 正在通话的电话线被剪断 | 响应永远写不回去 |
| 算到一半的上下文（内存里的中间结果） | 柜员手里填了一半的单据被收走 | SQL 查完了也白查，JSON 组装到一半也没了 |
| 依赖活着 | 金库完好 | **帮不上任何忙**——金库救不了那笔被中断的业务 |

**依赖活着只保证数据不丢，不保证请求不丢。** 这是整篇笔记的基石认知。

## 三、LB（Load Balancer）：流量分配员

解决的问题：6 个实例，谁接这个请求？

```
用户浏览器 ──HTTP──► LB ──┬──► 实例1
                          ├──► 实例2
                          └──► ...共6个
```

Nginx 反向代理、公司统一网关、DNS 轮询，扮演的都是 LB 这个"分流"角色。浏览器访问一个域名时，请求先经网关、再落到某个具体实例，中间那一跳就是 LB。**它对调用方透明**——这是平时感觉不到它存在的原因。📌 生活类比：LB 像政务大厅门口的取号机，决定每位客人去哪个窗口。

### LB 最重要的特性：名单是缓存，实例发不出私信

```
PM2/运维 ──SIGTERM──► 旧实例      ← 私信！LB 不在抄送名单里

用户 ──HTTP──► LB ──按"成员列表"转发──► 实例们
                 │
                 └──周期性轮询──► 各实例   ← LB 了解实例的唯一方式：主动去问

旧实例 ────✗───► LB                ← 这条信道不存在！实例无法主动上报
```

- ⚠️ LB 脑子里的"活着的实例列表"是**带 TTL（有效期，过期作废）的缓存**，有效期约等于健康检查周期
- 实例下线这件事，LB 只能等缓存过期才知道
- **探针的本质：实例对 LB 的唯一发声渠道**——实例推不了消息，但可以让 LB 的下次拉取失败。这是拉模式下的"伪推送"

> 📌 生活类比：餐厅换了新菜单，但手里还拿着旧菜单的客人不会自动知道——你没有信道挨个通知他们，只能等他们下次进门换菜单。DNS 靠 TTL、CDN 靠缓存失效，都是同一个问题。

## 四、没有探针的发布会：两个事故窗口

滚动发布时，重启不是原子操作（不可分割的整体，要么全做完要么没发生），是三件**互不同步**的事：旧实例退出 + 新实例启动 + 网关切流。

```
t=0s   PM2 给旧实例发 SIGTERM，旧实例停止监听
t=0~2s LB 不知道！名单里旧实例还在
       → 用户请求路由过去 → 502                    ← 坏窗口A：流量切晚了
t=2s   LB 探测失败/被动发现 → 摘除旧实例
t=3s   新实例 bind 端口成功，LB 立刻导流
t=3~5s 但 DB 连接池/Redis/Apollo 还没就绪 → 首批请求 500  ← 坏窗口B：流量切早了
t=5s   新实例真正就绪 → 恢复正常
```

发布瞬间偶见一串 502（网关报错：转发到的实例没应答）然后自愈——不是调用方的 bug，就是这两个窗口。图中名词：SIGTERM 是 Linux 的「请退出」信号；bind 端口指开始监听端口；Apollo 是配置中心；500 是服务内部错误。

**探针把"网关猜"变成"实例说"**，完整舞步：

1. 新实例刚启动，探针回答"数据库还没连上"，LB 不导流（消灭切早了）
2. 新实例就绪，探针回答 OK，LB 开始导流
3. 旧实例收到 SIGTERM，**主动把探针置为失败**，LB 几秒内摘除它（消灭切晚了）
4. 旧实例等在途请求处理完，再退出
5. 全程 0 失败请求

### ⚠️ 优雅关闭只写一半，等于白写

```ts
// main.ts 里已有的代码
process.on('SIGTERM', () => shutdown('SIGTERM'));
// shutdown: app.close() → 处理完在途请求 → exit(0)
```

`app.close()` 处理的是**存量**（在途请求做完），探针处理的是**增量**（新请求别进来）。没有探针配合：

- LB 继续往正在关闭的实例导流
- keep-alive（复用同一条连接的长连接）不消亡，`app.close()` 可能一直挂着不返回
- 最后 PM2 等不及直接发 SIGKILL（强制击杀信号），连"存量处理完"这半都没兑现

**✅ 关店的正确顺序：先在门口挂"暂停接待"的牌子（探针失败），让店里正在点单的客人买完单（优雅关闭），再锁门（退出进程）。**

## 五、readiness 窗口：活着不代表能服务

### 生活版（一眼就懂）

```
t=0    店门开了，灯亮了              ← 活着（有店面）
t=...  后厨备菜、收银机联网
t=...  菜能上桌、能结账              ← 能服务（可接待）
```

开门但做不了菜的那段时间，你不敢放客人进来点单。**"活着"和"能用了"之间的空隙怎么熬过去**——门口挂一块"备餐中"的牌子就是答案。

### 后端版（同一个窗口）

```
t=0s    进程起来，端口开始监听        ← liveness = true（活着）
t=0.3s  连 MySQL、Redis、拉 Apollo
t=2s    连接池建好、规则引擎初始化完   ← readiness = true（能服务）
```

t=0~2s 端口通了但查库必挂——这段「开门却做不了菜」的空隙，就是 readiness 窗口。

| | 生活类比（新开的餐厅） | 后端 |
|---|---|---|
| 活着 | 店门开了灯亮了 | 端口通 |
| 能服务 | 后厨备好菜能出餐 | 依赖连上可处理请求 |
| 空隙 | 开门了但做不了菜 | readiness 窗口 |
| 空隙中硬接请求 | 客人点了单上不了菜 | 用户拿到 500 |
| 解法 | 门口挂"备餐中"牌 | 探针：就绪前报"没准备好" |

**readiness 探针就是门口那块"备餐中，请稍候"的牌子。** liveness 和 readiness 是两个独立探针，防的病不同：liveness 防进程死，readiness 防"进程在但脑子不在"。

### 实例假死：为什么流量照样进来

⚠️ 假死指进程活着（端口监听、TCP 握手成功）但事件循环（进程里排队干活的主循环）卡死：大查询、疯狂 GC（垃圾回收）、无超时的外部调用挂满，都会造成。两种探针测的东西不同：

- **进程级探测**（端口能通吗）：假死时**依然通过**——操作系统内核替进程应答了连接握手，进程本身没参与
- **应用级探测**（自己在进程内真实执行检查：事件循环延迟、Redis ping）：假死时**检查本身也卡住，超时即失败** ✅

只有应用级探针能发现假死。典型成因：HTTP 客户端（如 axios）没配超时，下游挂起，等待中的请求越堆越多、占满事件循环，全站变慢。

## 六、resilience 模式：失败是常态

**Resilience（韧性）指在"失败是常态"这个假设下组织代码的写法**。四件套：

| 模式 | 生活类比 | 后端形态 |
|---|---|---|
| 超时 | 打电话响铃太久就挂断，不无限等 | HTTP 客户端配 `timeout: 10_000`（10 秒） |
| 重试+退避 | 占线就过会儿再拨，越打不通间隔越长 | BullMQ `attempts: 5, backoff` |
| 降级 | 招牌菜卖完了，给客人推荐替代菜 | fallback（兜底）配置 / 默认值 |
| 熔断 | 某家店连续出问题，暂停给它派单一段时间再试 | Hystrix / resilience4j 的 circuit breaker（熔断器） |

```ts
// 重试加退避的最小示例（机制与语言无关）：最多试 3 次，失败后越等越久
for (let i = 0; i < 3; i++) {
  try { return await fetch(url); }
  catch (e) {
    if (i === 2) throw e;
    await sleep(1000 * (i + 1));   // 退避：越失败等越久
  }
}
```

退避的直觉：对方报 502 大概率是忙不过来，立刻重试就像往拥挤的门口再挤一个人。

**核心心法：resilience 代码不问"会不会失败"，只问"失败时用户看到什么"。**

反面是"幸福路径假设"：写下 `const data = await api.getUser()` 就完事，认为失败只是 bug、修掉就行。两种世界观写出的代码完全不同。

## 七、容量水位：70/80 的含义

水位（water level）借水库的比喻，指**已用量占总容量**的百分比。CPU 水位看集群的分配率或利用率；GPU 水位看显存占用率或算力分配率。

### 为什么是 70/80 双阈值

- **低于 40% 到 50%**：资源闲置，预算白花，平台会想"提水位"，比如超卖（一份资源许诺给多家）或混部（不同任务混跑在同一批机器上）
- **70% 左右**：健康区间——省钱且有余量
- **超过 80%**：风险区。留 20% 到 30% 余量的原因：流量毛刺、机器故障时分摊、故障恢复需要空位。**水位打满时任何抖动都会雪崩，70/80 是成本和抗风险能力的折中**

### 超过 80% 会发生什么（按系统类型）

| 系统类型 | 动作 |
|---|---|
| 调度型（K8s/GPU 集群） | 新任务排队不调度；已运行任务被 throttle（变慢不报错）；极端时触发驱逐（把任务请出去腾位置）或抢占（高优任务挤掉低优任务） |
| 容量管理型 | 告警 + 自动生成扩容/采购单 |
| 接入型（网关/配额） | 限流、拒绝新请求、降级 |

### 接口文档里写"水位 70/80"的真实含义

不是让你实现监控，而是**容量责任边界的声明**："我方承诺水位 80% 以内服务可用；超出后要么平台扩容，要么调用方必须自我限流（主动控制自己的请求速率）"。如果你是调用方，下游水位就是你的代码要配合的约束。

### ⚠️ 监控不是闸门

- **监控**（平台/运维侧）：采集、告警、扩容——分钟级反应链路
- **闸门**（应用代码侧）：限流、排队削峰（洪峰请求先排队、慢慢消化）、降级、超时退避——秒级生效

流量风暴是秒级的，等监控告警生效时服务已经挂了。**"超过 80% 会发生什么"的第一道防线不在监控，而在代码自身的限流和排队。**

✅ 代码侧配置清单：入站限流、出站限流、超时加重试退避、队列消费速率控制、有界资源池（连接池等设上限，不许无限增长）、健康检查加优雅退出。

## 八、探知边界：代码能感知容量吗

能，但精度分层——**离自己越近越准，离自己越远越只能推断**：

| 层级 | 可见性 | 信号 |
|---|---|---|
| 进程内 | 完全可见，微秒级 | `monitorEventLoopDelay()`（事件循环延迟，**原项目运行时最重要的自感知信号**）、`process.memoryUsage()`（内存占用）、队列深度 `getWaitingCount()`、连接池占用 |
| 容器/宿主 | 自己的配额可见 | cgroup（Linux 给容器划资源配额的机制）：`/sys/fs/cgroup/cpu.max` 是配额上限，`cpu.stat` 里的 `nr_throttled` 是被内核限流的次数，也就是 CPU 水位超标的直接证据；看不到邻居和整机 |
| 下游/依赖 | 不可见，只能反馈逼近 | RT（响应时间）上升说明接近饱和；出现超时、429（请求太多被拒）、503（服务不可用）说明已越界 |

### 核心思想转变：从"探测边界"到"逼近边界"

生产系统很少真的去探测边界（那意味着故意打挂自己），而是**自适应并发**让边界自己浮现：

| 算法 | 思路 | 代表 |
|---|---|---|
| AIMD | 正常时并发数加一（线性增），失败时减半（乘性减） | TCP、Netflix concurrency-limits |
| 梯度 | 比较响应时间当前值与最小值的变化趋势，恶化就收缩并发 | Netflix gradient2 |
| Little 定律 | 最大并发等于目标 QPS（每秒请求数）乘以实测响应时间 | gRPC retry budget |

> Netflix concurrency-limits 不监控 CPU，只盯每个请求的成功/失败/延迟，动态调并发数——不需要知道链路带宽，靠反馈就能逼近最优速率（TCP 拥塞控制的思路）。

## 九、稳定性建设的正确顺序：先保不挂，再谈压榨容量

**原则：先堵住级联失效（一个依赖挂掉拖垮全站）的入口，再让平台能正确对待你，最后才谈自适应压榨容量。**

📌 audit-server 的体检结果（按性价比排序）：

### 第一优先级：出站请求无超时 —— 真实存在的雪崩入口

四个 axios（HTTP 客户端）实例全没配超时（order / main-data / sso / perm）。后果链：

```
下游 SSO 挂起 → axios 默认无超时 → 请求全挂住
→ pending Promise 堆满事件循环 → 内存涨、响应全慢
→ 6 个 PM2 实例同时中招 → 一个依赖的故障变成整个平台的故障
```

修复成本：每个实例加一行 `timeout: 10_000`。**全仓库性价比最高的稳定性改动。**

### 第二优先级：没有健康检查端点

`app.controller.ts` 只有 hello。没有 `/health` 意味着优雅关闭白写（无探针配合）、假死实例持续接流量。

### 第三优先级：失败任务无人认领

BullMQ `attempts: 5` 重试耗尽后，任务留在失败列表里只有一行日志。缺死信（重试耗尽仍失败的任务）告警，可复用 mailer 队列来发。审计任务静默丢失，意味着第二天有人来问数据为什么对不上。

### 最后才是：边界感知

前三项解决"别挂"，边界感知解决"别浪费"。且做它的前提是先有反馈通道（健康端点、指标、告警）。

**⚠️ 顺序反了，就是用高级手段装饰一个会因依赖挂起而全站瘫痪的系统。**

## 十、我们项目的真实流量路径（LB 没有消失，只是降级了）

```
浏览器
  │ DNS
  ▼
容器 VIP（平台分配的虚拟 IP，背后是平台的 LB——第一层，平时无感）
  ▼
Nginx（upstream 配置——第二层，唯一能摸到的）
  ▼
本机 6 个 PM2 实例（cluster 模式，master 分发——第三层）
```

直觉"没有 LB"通常意味着"没有主动健康检查"——这正是现状：

### 开源 nginx 的残酷现实：没有探针，只有死后验尸

`upstream`（Nginx 里登记后端实例名单的配置块）里的 `max_fails=2 fail_timeout=10s` 是**被动健康检查**：

```
请求 → 转给实例 → 连接被拒/超时 → 记一次失败
攒到 max_fails=2 → fail_timeout 内不再发新请求
10s 后 → "也许活了？" → 再试
```

**⚠️ 用真实用户的请求当探针：摘除一个坏实例的学费，是 2 个真实用户的失败请求。**（主动 `health_check` 指令是 nginx 商业版才有的）

### 无基础设施改动的最优解：发布器自己当探针

✅ 改 deploy 脚本：重启每个实例后 `curl -f http://127.0.0.1:$PORT/health` 轮询到 200（HTTP 成功状态码）才继续下一个；stop 改成真正的 SIGTERM 加等待退出。两个窗口压到接近零。

## 十一、新旧交接是同一门课

📌 生活类比：餐厅换厨师——新厨师先备好料、试好火（readiness 就绪），老厨师把手头点单的菜做完（排水），门口挂牌暂停接新单（探针失败），最后才换人。客人全程无感；反过来，新厨师还没备好料就抢着上灶，就是硬重启腰斩在途请求。

**LB 加优雅关闭加探针，就是服务端的新旧交接时序控制；和生活里换班、换厨师、换窗口是同一门课。**

## 名词速查

| 名词 | 一句话 |
|---|---|
| LB (Load Balancer) | 流量分配员；成员名单是带 TTL 的缓存 |
| liveness probe | 进程活着吗（端口/进程级） |
| readiness probe | 能服务吗（依赖加事件循环级）；像门口"备餐中"的牌子 |
| drain（排水） | 先摘流量，再处理完在途请求，最后退出 |
| graceful shutdown | 优雅关闭：处理完存量、拒绝增量 |
| resilience | 失败是常态假设下的代码组织方式（超时/重试/退避/降级/熔断） |
| backoff | 失败后等待重试，越失败等越久 |
| AIMD | 线性增、乘性减的自适应并发算法 |
| readiness 窗口 | "活着"和"能服务"之间的空隙（开门却做不了菜） |
| 假死 | 进程在、端口通、事件循环卡死；只有应用级探针能发现 |
| 水位 | 已用量占总容量的比例；70/80 是成本与抗风险的折中 |
| stalled job | worker 处理中被中断的任务，BullMQ 会重新投递 |
