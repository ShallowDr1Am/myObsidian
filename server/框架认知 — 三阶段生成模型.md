## 一、三个常见错误簇

| 簇 | 典型误解 | 根因 | 纠正 |
|---|---|---|---|
| A 生成时机 | 「类是运行时自动冒出来的」「动态生成的类会合并进实体类」 | 习惯以为一切都在程序跑起来后才发生 | 三阶段表（§二）：Lombok 在编译期生成，代理和 SQL 注入在启动期完成，反射和类型转换发生在运行时 |
| B 禁令背反 | 「Service 里不许写调用」「Mapper 里不许写方法」这类背反的禁令 | 背禁令没锚正面职责 | 职责表（§三）：禁令是职责的推论 |
| C 表面判据 | 「看继承关系就能判断用途」 | Java 的信息在**元数据（注解这类附加说明）和使用处**，不在语法表面 | 三问（§四）：对着谁 / 继承谁 / 注解被谁读 |

## 二、三阶段表（簇 A 的解药）

| 阶段 | 生成者 | 生成什么 | 证据动作 |
|---|---|---|---|
| 编译期 | Lombok 注解处理器（AP）/ MyBatis Generator（MBG）/ mvn install | getId 字节码（2677 个文件）/ 117 个 Example 类加 139 个 XML / 本地仓库 ~/.m2 里的 jar 包 | `javap Workday.class` 看 getId |
| 启动期 | Spring 扫描 / XML 解析 / MP 的 TableInfo 收集与 SQL 注入 / MapperProxyFactory | Bean 的存在 / MappedStatement 登记项 / 58 个 Mapper 的 SQL / 代理对象 | 启动 SQL 日志看注入 SQL |
| 运行时 | 代理截获 / ObjectFactory / TypeHandler 加 MetaObject | 把方法调用变成 SQL / 每行新建一个空对象 / 逐列填充（一行 4 列就填 4 次） | 断点 DefaultResultSetHandler |

表中名词白话版：

- 编译期相关：AP 是注解处理器，编译时读注解、补代码的小程序；MBG 是 MyBatis 官方代码生成器；Example 类是 MBG 生成的查询条件构造器；jar 是打包好的依赖成品，~/.m2 是 Maven 在本机存放它们的仓库目录。
- 启动期相关：MP 是 MyBatis-Plus；Bean 是交给 Spring 统一保管的对象；MappedStatement 是 MyBatis 给每条 SQL 建的登记条目；TableInfo 是 MP 给每张表建的字段档案；MapperProxyFactory 是生产 Mapper 替身（代理）的工厂。
- 运行时相关：ObjectFactory 负责新建空对象；TypeHandler 负责把数据库值转成 Java 类型；MetaObject 是反射读写字段的工具。

📌 生活类比：编译期像开工前的代写员，照着注解把样板代码补进成品，补完就不再出现；启动期像开工时的管理员，组建部门、配好工具、给接口配替身、备好登记簿；运行时是干活现场，替身查登记簿执行 SQL，再把返回的一行填进空对象。懵的时候先问一句：这件事发生在开工前、开工时、还是干活时？

## 三、层正面职责（簇 B 的解药：禁令是推论）

| 层 | 正面职责 | 推论禁令 |
|---|---|---|
| Controller | 协议适配：校验入参、整理格式、处理 HTTP 请求响应语义 | 不写业务逻辑 |
| Service | 业务编排：调 Mapper、发 MQ（消息队列，像把任务放上传送带交给别的工人）、组合多个步骤 | 不写 SQL |
| Mapper | 数据访问：声明方法签名，并把方法映射到 SQL | 不写业务逻辑 |

## 四、判据三问（簇 C 的解药）

1. **对着谁**：对着数据库表的是 Entity（实体类），对着接口入参的是 DTO（入参对象），对着页面展示的是 VO（展示对象）。继承不是判据，它们都是普通类。
2. **继承（extends）谁**：继承老式自定义接口的，去 XML 里找 SQL；继承 MP 的 BaseMapper 的，SQL 由 MP 在启动期注入，没有 XML。
3. **注解被谁读**：@Data 由 Lombok 注解处理器读，@TableField 由 MP 的 TableInfo 收集器读，@Profile 由 Spring 的条件评估器（ConditionEvaluator）读——注解自己什么都不做，读它的人才干活。
